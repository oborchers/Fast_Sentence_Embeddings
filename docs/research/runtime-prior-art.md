# Runtime state of the art: parallel encoding with static embeddings

Historical note (31.10.2026): MLX was removed from fse. These research findings describe the earlier investigation.

Research date: 2026-10-28. All code claims come from the source at the commit given in each permalink, read directly. "Unverified" marks anything I did not confirm in a primary source.

Commits read: model2vec `dc1ff382f279`, sentence-transformers `145ef47d5a4b` (latest release v6.2.0, 2026-10-21), tokenizers `d9a5e8af4b58` (main = 1.0 line; latest tags v1.0.0-rc.3 2026-10-19 and stable v0.23.3 2026-10-09), fastText `1142dc4c4ecb` (repository archived, last push 2024-03-22), WordLlama `ee2b5302451d`, Polars `f78c80cb96b8`, Arrow `fc390cd3442b`, spaCy `7ff14d4da848`, gensim `37f90ec121eb`, joblib `878c9e05995b`, loky `d749ac8bdafc`, CPython `e35424611f81`.

## 1. model2vec (MinishLab)

- **Concurrency:** joblib threads, not processes, despite the parameter name `use_multiprocessing`: `ProgressParallel(n_jobs=-1, backend="threading", ...)` ([model.py L280-L287](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L280-L287)). `ProgressParallel` is a `joblib.Parallel` subclass that adds a tqdm bar ([utils.py L17](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/utils.py#L17)). joblib's threading backend is meant for work that releases the GIL, for example a Cython `with nogil` block or a large NumPy call ([joblib _parallel_backends.py L554-L566](https://github.com/joblib/joblib/blob/878c9e05995b/joblib/_parallel_backends.py#L554-L566)).
- **GIL release:** comes from the Rust tokenizer (`encode_batch_fast`, [model.py L170-L187](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L170-L187)) and from NumPy fancy indexing plus `mean`. When there are no weights or mapping, the pooling groups sentences into buckets by token count and runs one `embedding[id_matrix].mean(axis=1)` per bucket. Otherwise it loops over sentences in Python ([model.py L457-L482](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L457-L482)).
- **Batching:** fixed slices of `batch_size=1024` sentences ([L303-L306](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L303-L306), [`_batch` L487](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L487)). No memory-based bound.
- **Small-input path:** runs sequentially unless `len(sentences) > multiprocessing_threshold`, which defaults to 10,000 ([L280](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L280), [L306](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L306)).
- **Nested parallelism:** sets `os.environ["TOKENIZERS_PARALLELISM"] = "false"` before the parallel path and never restores it ([L281-L282](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L281-L282)), so this is a process-wide side effect.
- **Order:** results are concatenated in batch order (`np.concatenate`). joblib's default `return_as="list"` returns results in order ([joblib parallel.py L1019-L1025](https://github.com/joblib/joblib/blob/878c9e05995b/joblib/parallel.py#L1019-L1025)).
- **Streaming and back-pressure:** none. The input must be a `Sequence`, and all outputs stay in memory until the final concatenation. joblib's default `pre_dispatch="2 * n_jobs"` limits how many tasks are dispatched at once ([parallel.py L1048](https://github.com/joblib/joblib/blob/878c9e05995b/joblib/parallel.py#L1048), [L1227](https://github.com/joblib/joblib/blob/878c9e05995b/joblib/parallel.py#L1227)). model2vec still materializes the full list of batch slices first (`list(self._batch(...))`).
- **Worker count:** `n_jobs=-1` resolves through joblib's `cpu_count`, which uses loky ([joblib _parallel_backends.py L33, L59](https://github.com/joblib/joblib/blob/878c9e05995b/joblib/_parallel_backends.py#L33)). loky takes the minimum of `os.cpu_count()`, the affinity set, the cgroup quota (`ceil(quota/period)` from v2 `cpu.max`, falling back to v1 `cfs_quota_us`) and `LOKY_MAX_CPU_COUNT` ([loky context.py](https://github.com/joblib/loky/blob/d749ac8bdafc/loky/backend/context.py)). I verified the summary of that file and did not quote it line by line.
- **Errors:** joblib re-raises the worker's exception. I did not check whether it is the first failure in input order (unverified).
- **Backend:** NumPy only, with no device abstraction.

## 2. sentence-transformers (v6.2.0 / main)

- **Single-process `encode`:** sorts inputs by descending length (character count as a proxy), then splits them into batches of `batch_size=32`. When inputs can be flattened (flash attention without padding), it interleaves long and short inputs to even out the token count per batch. After the last batch it restores the original order ([sentence_transformer/model.py L947-L995](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/sentence_transformer/model.py#L947-L995), [base/model.py L519-L560](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L519-L560)). Normalization and truncation run per batch inside the loop.
- **Multi-process:** `encode_multi_process` is deprecated. `encode(pool=...)` or `encode(device=[...])` is used instead ([model.py L887-L891](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/sentence_transformer/model.py#L887-L891), [L1094-L1098](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/sentence_transformer/model.py#L1094-L1098)). The pool consists of `spawn` processes, one per target device, fed by one shared input queue and one output queue. The model is moved to CPU and put in shared memory first ([base/model.py L1833-L1862](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L1833-L1862)).
- **Default worker count on CPU:** a hard-coded `["cpu"] * 4`. There is no CPU detection ([L1839-L1840](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L1839-L1840)).
- **Chunking:** `chunk_size = max(1, min(ceil(n / processes / 10), 5000))`, which gives about 10 chunks per process, capped at 5000 inputs ([L1912-L1913](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L1912-L1913)).
- **Back-pressure:** none. All chunks go onto an unbounded `ctx.Queue()` in one loop before any result is read ([L1915-L1919](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L1915-L1919)). The input must be a sliceable sequence, so there is no streaming.
- **Order and errors:** results are stored by `chunk_id` in `outputs[chunk_id]`. After all chunks arrive, the code iterates in chunk order and raises the first exception, so the error is the first failing chunk in input order. It waits for every chunk first ([L1921-L1931](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L1921-L1931)). Workers catch exceptions and send them as results ([L1949-L1957](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L1949-L1957)). The parent polls the queue with a 1 s timeout and raises if a worker died ([L1960-L1975](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L1960-L1975)).
- **Device abstraction:** PyTorch device strings (cuda, npu, hpu, cpu). There is no separate backend contract.

## 3. Hugging Face tokenizers

**Stable 0.23.x**
- `encode_batch` uses `inputs.into_maybe_par_iter().map(encode).collect::<Result<Vec<_>>>()` on rayon's global pool ([tokenizer/mod.rs L1308-L1320 @v0.23.3](https://github.com/huggingface/tokenizers/blob/v0.23.3/tokenizers/src/tokenizer/mod.rs#L1308-L1320)).
- The Python binding releases the GIL with `py.detach` ([bindings tokenizer.rs @v0.23.3](https://github.com/huggingface/tokenizers/blob/v0.23.3/bindings/python/src/tokenizer.rs)) and declares `gil_used = false` for free-threaded Python ([lib.rs L50 @v0.23.3](https://github.com/huggingface/tokenizers/blob/v0.23.3/bindings/python/src/lib.rs#L50)).
- `TOKENIZERS_PARALLELISM` set to false, f, off, no, n, 0 or empty disables parallelism ([utils/parallelism.rs @v0.23.3](https://github.com/huggingface/tokenizers/blob/v0.23.3/tokenizers/src/utils/parallelism.rs)).
- A `pthread_atfork` child handler turns parallelism off after a fork, but only if parallelism was already used and the variable was not set explicitly. This prevents deadlocks under `multiprocessing` fork ([lib.rs L36-L47, L90-L97 @v0.23.3](https://github.com/huggingface/tokenizers/blob/v0.23.3/bindings/python/src/lib.rs#L36-L47)).
- The thread count comes from rayon's global pool, so `RAYON_NUM_THREADS` applies. I did not verify this in source for 0.23 (unverified).
- With several errors, `collect` into `Result` returns an arbitrary one. rayon documents: "If there are multiple errors, the one returned is not deterministic" ([rayon FromParallelIterator](https://docs.rs/rayon/latest/rayon/iter/trait.FromParallelIterator.html)).

**main / 1.0.0-rc (new `tk-encode` pipeline)**
- Own rayon pool (threads named `tk-encode-{i}`), sized by `std::thread::available_parallelism()` unless `set_num_threads` overrides it. No pool is built when the count is 1. The pool is invalidated after a fork through a generation counter in `pthread_atfork`, and an inherited pool is leaked with `mem::forget` to avoid a deadlock ([parallelism.rs](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/utils/parallelism.rs)).
- **Small-input path:** inputs under `PARALLEL_MIN_BYTES = 8 KiB` in total run serially on the calling thread, and so does a single sequence under 16 KiB ([parallel.rs L25-L29, L442-L460](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L442-L460)). The threshold is in **bytes**, not items.
- **Chunking:** long sequences are split into chunks of at least 8 KiB. Small chunks are grouped into tasks of at least 8 KiB so that workers do not contend on the cursor. Larger chunks are scheduled first to avoid a straggler at the end ([L302-L421](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L302-L421)).
- **Scheduling:** workers take tasks from a shared atomic cursor (`next_task.fetch_add`). The number of threads is `min(tasks, pool threads)` ([L482-L505](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L482-L505)).
- **The calling thread works while it waits:** "instead of parking or empty spinning, we do useful work" ([L249-L268](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L249-L268)).
- **Order:** results arrive in completion order with their sequence index, and `wait()` writes them into `out[seq]` ([pipeline/mod.rs L464-L476](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/mod.rs#L464-L476)).
- **Errors:** a worker panic is caught with `catch_unwind` and becomes an error ([parallel.rs L158-L178](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L158-L178)). `wait()` returns the error of the **first completed** failing sequence, which is not necessarily the first in input order. Dropping the iterator sets a `cancelled` flag that stops the remaining tasks ([L221-L223, L271-L273](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L271-L273)).
- **Back-pressure:** none within a call. The whole batch is planned up front.

## 4. fastText (archived)

- **Training:** `-thread` threads, default 12 ([args.cc](https://github.com/facebookresearch/fastText/blob/1142dc4c4ecb/src/args.cc)). Each thread opens the input file itself and seeks to `threadId * size / thread` ([fasttext.cc L632-L634](https://github.com/facebookresearch/fastText/blob/1142dc4c4ecb/src/fasttext.cc#L632-L634)). Results with more than one thread are not reproducible, as the help text says.
- **Training errors:** stored in `trainException_`. The other threads stop through `keepTraining`, and the main thread rethrows the exception after `join` ([L673, L784-L809](https://github.com/facebookresearch/fastText/blob/1142dc4c4ecb/src/fasttext.cc#L784-L809)).
- **Python training:** `train` releases the GIL (`py::call_guard<py::gil_scoped_release>`) ([fasttext_pybind.cc L160-L169](https://github.com/facebookresearch/fastText/blob/1142dc4c4ecb/python/fasttext_module/fasttext/pybind/fasttext_pybind.cc#L160-L169)).
- **Inference:** `getSentenceVector` and `multilinePredict` are single-threaded per call and do **not** release the GIL ([L299-L306, L410-L440](https://github.com/facebookresearch/fastText/blob/1142dc4c4ecb/python/fasttext_module/fasttext/pybind/fasttext_pybind.cc#L299-L306)). Encoding has no parallelism, batching or streaming. No CPU detection.

## 5. WordLlama

- **No parallelism of its own:** a Python loop over batches of `batch_size=64`, writing into a preallocated output array. Tokenization uses HF `encode_batch` with padding, so the tokenizer's rayon pool provides the only parallelism. Pooling is NumPy fancy indexing plus a masked mean, and normalization or binarization runs per batch ([inference.py L60-L130](https://github.com/dleemiller/WordLlama/blob/ee2b5302451d/src/wordllama/inference.py#L60-L130)).
- **Validation:** out-of-range token ids are **silently clipped** (`np.clip(input_ids, 0, vocab-1)`) ([inference.py](https://github.com/dleemiller/WordLlama/blob/ee2b5302451d/src/wordllama/inference.py)). This is the opposite of fse's strict-validation rule.
- No streaming, back-pressure, device abstraction or CPU detection.

## 6. Polars and PyArrow

**Polars**
- **Pool size:** `POLARS_MAX_THREADS`, default `std::thread::available_parallelism()` with a fallback of 4. It is fixed at process start and cannot be changed afterwards ([polars-config lib.rs L29-L34](https://github.com/pola-rs/polars/blob/f78c80cb96b8/crates/polars-config/src/lib.rs#L29-L34), [thread_pool.py](https://github.com/pola-rs/polars/blob/f78c80cb96b8/py-polars/src/polars/meta/thread_pool.py)). Cgroup handling is therefore whatever Rust std does (section 8).
- **Morsels:** the streaming engine processes morsels with an ideal size of `POLARS_IDEAL_MORSEL_SIZE = 100_000` rows ([lib.rs L36-L37](https://github.com/pola-rs/polars/blob/f78c80cb96b8/crates/polars-config/src/lib.rs#L36-L37)). Each morsel carries a monotone `MorselSeq` for ordering and a consume token "to provide backpressure" ([morsel.rs](https://github.com/pola-rs/polars/blob/f78c80cb96b8/crates/polars-stream/src/morsel.rs)).
- **Channels:** pipes are capacity-one SPSC connectors ([connector.rs](https://github.com/pola-rs/polars/blob/f78c80cb96b8/crates/polars-async/src/primitives/connector.rs)). A `Linearizer` merges N ordered sender streams into one ordered stream with a binary heap and bounded per-sender channels (`buffer_size`) ([linearizer.rs](https://github.com/pola-rs/polars/blob/f78c80cb96b8/crates/polars-async/src/primitives/linearizer.rs)). This is the same bounded reorder buffer that fse's window implements.

**Arrow / PyArrow**
- **CPU pool capacity:** `OMP_NUM_THREADS`, otherwise the affinity core count (`sched_getaffinity`), otherwise `hardware_concurrency`, otherwise 4, capped by `OMP_THREAD_LIMIT`. It reads **no cgroup quota** ([thread_pool.cc L799-L819](https://github.com/apache/arrow/blob/fc390cd3442b/cpp/src/arrow/util/thread_pool.cc#L799-L819)).
- **Back-pressure:** in bytes, with hysteresis. Acero sink nodes pause above 1 GiB and resume below 256 MiB by default ([acero/options.h L353-L397](https://github.com/apache/arrow/blob/fc390cd3442b/cpp/src/arrow/acero/options.h#L353-L397)).
- **Dataset scanner:** `batch_size=2**17` rows, `batch_readahead=16`, `fragment_readahead=4` ([_dataset.pyx L48-L50](https://github.com/apache/arrow/blob/fc390cd3442b/python/pyarrow/_dataset.pyx#L48-L50)).

## 7. spaCy `nlp.pipe` and gensim

**spaCy**
- **Defaults:** `n_process=1` and `batch_size=None`, which falls back to `nlp.batch_size`. `n_process=-1` means `mp.cpu_count()`, which ignores affinity and cgroups ([language.py L1543-L1612](https://github.com/explosion/spaCy/blob/7ff14d4da848/spacy/language.py#L1543-L1612)).
- **Multiprocessing:** one input `mp.Queue` and one `mp.Pipe` per process. Input is minibatched lazily from an iterator, so infinite streams work. `_Sender` sends `n_process` batches twice at the start ("send twice to make process busy") and sends `n_process` more each time `n_process` batches have been consumed. That bounds the window to about 2 x n_process batches, which matches fse's 2 x workers ([L1636-L1730](https://github.com/explosion/spaCy/blob/7ff14d4da848/spacy/language.py#L1636-L1730), [`_Sender` L2433-L2460](https://github.com/explosion/spaCy/blob/7ff14d4da848/spacy/language.py#L2433-L2460)).
- **Order:** round-robin dispatch and round-robin receive (`cycle(bytedocs_recv_ch)`) keep input order. The cost is head-of-line blocking on the slowest worker in each round.
- **Errors:** a worker error is serialized and passed to `default_error_handler`, which raises by default. On exit, the parent sends a sentinel and closes the channels.

**gensim (training)**
- **Threads:** `workers=3` threads by default. The Cython inner loops run `with nogil` ([word2vec.py L244](https://github.com/piskvorky/gensim/blob/37f90ec121eb/gensim/models/word2vec.py#L244), [word2vec_inner.pyx L573](https://github.com/piskvorky/gensim/blob/37f90ec121eb/gensim/models/word2vec_inner.pyx#L573)).
- **Producer:** a separate **producer thread** reads the corpus iterator ([L1417-L1430](https://github.com/piskvorky/gensim/blob/37f90ec121eb/gensim/models/word2vec.py#L1417-L1430)).
- **Queues:** bounded, `job_queue = Queue(maxsize=queue_factor * workers)` with `queue_factor=2` ([L1414-L1416](https://github.com/piskvorky/gensim/blob/37f90ec121eb/gensim/models/word2vec.py#L1414-L1416)). This is the same 2 x workers bound. Jobs are bounded by words (`batch_words=MAX_WORDS_IN_BATCH`, 10,000) rather than sentences.
- **Order:** not preserved. Training does not need it.

## 8. Python best practice and CPU detection

- **`Executor.map(..., buffersize=n)` (Python 3.14+):** the built-in bounded ordered map. It keeps at most `buffersize` submitted tasks whose results have not been yielded and pauses iteration of the input while the buffer is full ([concurrent.futures docs](https://github.com/python/cpython/blob/e35424611f81/Doc/library/concurrent.futures.rst#L49-L93)). The implementation is a deque of futures that submits the next task before popping the oldest, so up to `buffersize + 1` tasks can be in flight for a moment. Pending futures are cancelled in `finally` ([_base.py L652-L689](https://github.com/python/cpython/blob/e35424611f81/Lib/concurrent/futures/_base.py#L652-L689)). If `fn` raises, the exception surfaces when that result is reached in order. From 3.16 the iterator is no longer closed automatically on an exception. On 3.11 to 3.13, the equivalent is a hand-written deque window of `submit` futures.
- **`ThreadPoolExecutor` default:** `min(32, (os.process_cpu_count() or 1) + 4)` since 3.13. The `+4` is meant for I/O, which makes this a poor default for CPU-bound native work ([concurrent.futures.rst L223-L233](https://github.com/python/cpython/blob/e35424611f81/Doc/library/concurrent.futures.rst#L223-L233)).
- **`ProcessPoolExecutor`:** defaults to `process_cpu_count()`. Since 3.14 the default start method is no longer fork ([L394, L445-L453](https://github.com/python/cpython/blob/e35424611f81/Doc/library/concurrent.futures.rst#L445-L453)).
- **`os.process_cpu_count()` (3.13+):** returns the "logical CPUs usable by the calling thread of the current process", meaning the **affinity**, not the cgroup quota. `PYTHON_CPU_COUNT` or `-X cpu_count=n` overrides both `cpu_count` and `process_cpu_count` ([os.rst L6270-L6308](https://github.com/python/cpython/blob/e35424611f81/Doc/library/os.rst#L6294-L6308), [cmdline.rst PYTHON_CPU_COUNT](https://github.com/python/cpython/blob/e35424611f81/Doc/using/cmdline.rst)).
- **CPython upstream:** issue [#80235](https://github.com/python/cpython/issues/80235) ("os.cpu_count() should return a count assigned to a container") was closed in 2023-10. The current docs list only affinity and the manual override, so I take that as its resolution (inferred, not quoted). The override came with [#109595](https://github.com/python/cpython/issues/109595). A Kubernetes example shows `cpu.max = 50000 100000` (half a CPU) while `os.process_cpu_count()` still reported 20 ([itnext article](https://itnext.io/what-os-cpu-count-gets-wrong-in-a-cpu-limited-kubernetes-pod-ab57756a9153), a secondary source).
- **Rust `std::thread::available_parallelism`:** takes cgroup quotas and `sched_getaffinity` into account on Linux. It can overcount when the cgroup fs or affinity cannot be read (sandboxing), can undercount with pinned threads, may scan mountpoints for cgroup v1, and ignores ulimit ([std docs](https://doc.rust-lang.org/std/thread/fn.available_parallelism.html)). The `num_cpus` crate also checks sched affinity and cgroups ([docs.rs](https://docs.rs/num_cpus/latest/num_cpus/fn.get.html)).
- **joblib/loky:** `min(os.cpu_count, affinity, ceil(cgroup quota/period), LOKY_MAX_CPU_COUNT)`, reading v2 `cpu.max` first and falling back to v1 ([loky context.py](https://github.com/joblib/loky/blob/d749ac8bdafc/loky/backend/context.py)). This is the most complete pure-Python reference implementation found.
- **PyTorch:** I found no primary source showing that PyTorch reads cgroup quotas (unverified). Third parties report that its default thread count follows host cores inside Docker and patch it themselves by reading `cpu.cfs_quota_us` ([Unity ml-agents PR #4471](https://github.com/Unity-Technologies/ml-agents/pull/4471)). TorchServe saw large slowdowns from the default thread count in containers ([pytorch/serve PR #1138](https://github.com/pytorch/serve/pull/1138)).

| WordLlama | none (tokenizer only) | 64 texts | n/a | yes | no | n/a | n/a, silently clips ids |

## Implications for fse

### Where the design matches common practice
1. **Threads plus a native kernel that releases the GIL** is the pattern of model2vec (joblib threading), tokenizers (rayon with `py.detach`) and gensim (`with nogil`). Processes appear only where the model is Python or PyTorch (sentence-transformers, spaCy) and cost spawn and serialization overhead. Sources: [model2vec](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L280-L287), [tokenizers](https://github.com/huggingface/tokenizers/blob/v0.23.3/bindings/python/src/tokenizer.rs), [gensim](https://github.com/piskvorky/gensim/blob/37f90ec121eb/gensim/models/word2vec_inner.pyx#L573).
2. **A window of 2 x workers** is the de facto standard: gensim `queue_factor=2`, joblib `pre_dispatch="2 * n_jobs"`, spaCy "send twice". Sources: [gensim](https://github.com/piskvorky/gensim/blob/37f90ec121eb/gensim/models/word2vec.py#L1414-L1416), [joblib](https://github.com/joblib/joblib/blob/878c9e05995b/joblib/parallel.py#L1048), [spaCy](https://github.com/explosion/spaCy/blob/7ff14d4da848/spacy/language.py#L1666-L1671).
3. **An inline path for small inputs** exists in model2vec (10,000 sentences) and tokenizers 1.0 (8 KiB). Sources: [model2vec](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L280), [tokenizers](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L25-L29).
4. **Ordered commit through a bounded reorder buffer** is what Polars' `Linearizer` and `Executor.map(buffersize=)` do. Sources: [linearizer.rs](https://github.com/pola-rs/polars/blob/f78c80cb96b8/crates/polars-async/src/primitives/linearizer.rs), [_base.py](https://github.com/python/cpython/blob/e35424611f81/Lib/concurrent/futures/_base.py#L652-L689).

### Where fse goes further than the field
5. **Deterministic first error in input order:** only sentence-transformers does this, and it waits for all chunks first. tokenizers returns the first completed error, and rayon's error is documented as nondeterministic. fse's rule is stricter and better, so keep it and test it with two failing tasks finishing in reverse order. Sources: [ST](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/base/model.py#L1921-L1931), [rayon](https://docs.rs/rayon/latest/rayon/iter/trait.FromParallelIterator.html).
6. **A memory-sized task bound (about 4 MiB of output)** where everyone else counts sentences, rows or words. Only tokenizers 1.0 sizes tasks in bytes (input bytes) and Arrow applies back-pressure in bytes. Sources: [tokenizers](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L302-L421), [Arrow](https://github.com/apache/arrow/blob/fc390cd3442b/cpp/src/arrow/acero/options.h#L353-L356).
7. **Cgroup-aware default.** Python's `os.process_cpu_count()`, Arrow and spaCy are not cgroup-aware. loky and Rust std are. Sources: [os.rst](https://github.com/python/cpython/blob/e35424611f81/Doc/library/os.rst#L6294-L6308), [Arrow](https://github.com/apache/arrow/blob/fc390cd3442b/cpp/src/arrow/util/thread_pool.cc#L799-L819), [loky](https://github.com/joblib/loky/blob/d749ac8bdafc/loky/backend/context.py).

### Risks
8. **Cgroup parsing.** Follow loky: read v2 `cpu.max` first (`max` means unlimited), fall back to v1 `cfs_quota_us/cfs_period_us`, use `ceil(quota/period)`, and take the minimum with the affinity count, with a floor of 1. Find the cgroup's own path through `/proc/self/cgroup`, because nested cgroups do not live at the root. I did not check whether loky does this (unverified). Respect `PYTHON_CPU_COUNT` by building on `os.process_cpu_count()` (3.13+), falling back to `len(os.sched_getaffinity(0))` and then `os.cpu_count()`. Rust std notes that the cgroup fs can be unreadable in a sandbox, so treat read errors as "no quota". This must not be a validation error, because it is environment probing and not user input. Sources: [loky](https://github.com/joblib/loky/blob/d749ac8bdafc/loky/backend/context.py), [Rust std](https://doc.rust-lang.org/std/thread/fn.available_parallelism.html), [os.rst](https://github.com/python/cpython/blob/e35424611f81/Doc/library/os.rst#L6294-L6308).
9. **Nested oversubscription.** If fse's tokenizer stage calls HF tokenizers, its rayon pool and fse's workers multiply. model2vec solves this by setting `TOKENIZERS_PARALLELISM=false` process-wide and never restoring it. A side effect like that conflicts with fse's no-silent-behaviour stance. Prefer calling the tokenizer serially per task, or document the interaction. Source: [model2vec](https://github.com/MinishLab/model2vec/blob/dc1ff382f279/model2vec/model.py#L281-L282).
10. **Fork safety.** A persistent thread pool does not survive `fork`. tokenizers registers `pthread_atfork` and rebuilds or disables its pool in the child. If fse caches a pool across calls, use `os.register_at_fork(after_in_child=...)` to drop it. If the pool is created per call, there is no risk. Python 3.14 moved `ProcessPoolExecutor` away from fork, but `multiprocessing` users on Linux 3.11 to 3.13 still fork. Sources: [tokenizers 0.23](https://github.com/huggingface/tokenizers/blob/v0.23.3/bindings/python/src/lib.rs#L36-L47), [tokenizers 1.0](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/utils/parallelism.rs), [concurrent.futures](https://github.com/python/cpython/blob/e35424611f81/Doc/library/concurrent.futures.rst#L449-L453).
11. **A producer in the caller thread versus a producer thread.** gensim reads the iterator in its own thread, so parsing overlaps with the workers. With fse's design, the calling thread must alternate between pulling input, building tasks and committing. While it parses a large chunk, workers can starve and finished results wait. Because the window is 2 x workers, workers stay busy as long as producing one task takes less time than workers x the time to compute one task. Measure this with `bench_tokenize.py` on raw text. Source: [gensim](https://github.com/piskvorky/gensim/blob/37f90ec121eb/gensim/models/word2vec.py#L1417-L1430).
12. **Head-of-line blocking.** An ordered commit stalls on one slow task. Sizing tasks by output bytes evens the output size per task, but not the token count. Long sentences produce the same output size per row and cost more work. Consider bounding tasks by input tokens (or bytes) as well as output size, as tokenizers 1.0 does by grouping to at least 8 KiB of input and scheduling larger work first. Source: [tokenizers](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L403-L421).
13. **Do not rely on the `ThreadPoolExecutor` default** of `min(32, cpus + 4)`, which is meant for I/O. Pass `max_workers=workers` explicitly. Note that `Executor.map(buffersize=)` exists only from 3.14 and briefly holds `buffersize + 1` tasks, so keep fse's own window to hold the strict 2 x workers bound on 3.11 to 3.15. Source: [concurrent.futures](https://github.com/python/cpython/blob/e35424611f81/Doc/library/concurrent.futures.rst#L223-L233).
14. **Free-threaded Python (3.14t, 3.15t).** fse supports 3.11 to 3.15. tokenizers declares `gil_used = false`. If the Cython extension does not declare itself free-threading compatible, importing it re-enables the GIL on a free-threaded build. I did not check fse's extension, so this is an open item. Source: [tokenizers lib.rs](https://github.com/huggingface/tokenizers/blob/v0.23.3/bindings/python/src/lib.rs#L50).

### Ideas worth adopting
15. **Let the calling thread help.** While the window is full and the head task is not done, the caller can run the next queued task inline instead of blocking, as tokenizers 1.0 does. That removes one idle core when `workers = cpus`. Alternatively, count the caller as a worker and use `cpus - 1` pool threads. Source: [tokenizers](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L249-L268).
16. **Size the inline threshold in work, not items.** tokenizers uses 8 KiB of input bytes and model2vec uses 10,000 sentences. A threshold based on rows x dim, or on input bytes, matches fse's 4 MiB task sizing better. One task's worth of work, run inline, is the natural threshold. Source: [tokenizers](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L442-L460).
17. **Cancel promptly on the first error.** sentence-transformers waits for every chunk before raising. Instead, stop submitting once the head task in order fails, cancel queued futures and drain the running ones, as `Executor.map` does with `fut.cancel()` in `finally` and tokenizers does with its `cancelled` flag. Sources: [_base.py](https://github.com/python/cpython/blob/e35424611f81/Lib/concurrent/futures/_base.py#L686-L688), [tokenizers](https://github.com/huggingface/tokenizers/blob/d9a5e8af4b58/tokenizers/tk-encode/src/tokenizer/pipeline/parallel.rs#L145-L150).
18. **Expose an override environment variable** for the worker count. Polars (`POLARS_MAX_THREADS`), loky (`LOKY_MAX_CPU_COUNT`), Arrow (`OMP_NUM_THREADS`) and CPython (`PYTHON_CPU_COUNT`) all have one. At minimum, honour `PYTHON_CPU_COUNT` through `process_cpu_count`. Sources: [Polars](https://github.com/pola-rs/polars/blob/f78c80cb96b8/crates/polars-config/src/lib.rs#L29-L34), [Arrow](https://github.com/apache/arrow/blob/fc390cd3442b/cpp/src/arrow/util/thread_pool.cc#L799-L819).
19. **No length sorting on CPU.** sentence-transformers sorts by length to reduce padding on GPU batches. fse's ragged kernel needs no padding, so sorting buys nothing on CPU. For a future MLX or CUDA backend that pads, sorting *within* a task (and restoring order) could matter. That belongs inside `rows(...)` of the backend, not in the runtime. Source: [ST](https://github.com/huggingface/sentence-transformers/blob/145ef47d5a4b/sentence_transformers/sentence_transformer/model.py#L947-L995).
20. **Do not copy WordLlama's silent id clipping.** It is a cautionary example for fse's strict-validation rule. Source: [WordLlama](https://github.com/dleemiller/WordLlama/blob/ee2b5302451d/src/wordllama/inference.py).
