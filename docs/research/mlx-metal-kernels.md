# PR 9 research: MLX backend (`fse[mlx]`), Metal kernels, bit-exact contract

Looked at: MLX 0.32.4 (PyPI, uploaded 2026-10-14) and MLX `main` at commit 7d2d94a (2026-10-28, cloned and read); Metal Shading Language Specification 4.1 (document date 2026-06-04); Apple Developer Forums thread 844598 (Sep 2026).
Experiments were run on this machine: Apple M1 Pro (`applegpu_g13s`), macOS 27.0.1, MLX 0.32.4, Python 3.13, numpy. Scripts: `(a local scratch file, not kept)` to `t7.py` (not part of the repository). Everything marked "measured" was measured there on this one machine; M2 to M5 are unverified.

## Summary of findings that most affect the plan

1. **The Apple GPU (M1 Pro) flushes float32 subnormals to zero, as input and as result, in every math mode, including `safe` and with explicit `fma`.** Measured: `0x1 * 1.0f`, `x + 0`, `fma(x, 1, 0)` of a subnormal give 0; `subnormal * 2^30` gives 0 (so inputs are flushed, not just results); `2^-100 * 2^-40` gives 0 (results are flushed). Only plain loads/stores/copies keep subnormal bits. The MSL spec (section 8.1) only says denormals "may be flushed to zero", and Apple DTS states that no API selects or queries denormal handling. The contract ("subnormals kept, no flush to zero") and the conformance suite's subnormal profiles therefore **cannot be met by float32 GPU arithmetic as is**. The plan needs an explicit decision: (a) detect on the device (integer tests on the bit patterns of factors, stored values and accumulators; integers are not flushed) and recompute the affected rows/sentences on the CPU kernel, (b) narrow the contract text for device backends ("normal range; rows touching the subnormal range are computed on the CPU"), or (c) integer emulation (slow). Option (a) keeps "bit-identical" true and costs only on rare rows. Not prototyped.
2. **`math_mode="safe"` is not enough for the contract; add `#pragma METAL fp contract(off)` in the `header` of every kernel.** `safe` "sets the FP contract to on" (spec 1.6.3), so `x*y + z` in one statement is fused. Measured: with `safe`, `x*y+z` gives the fused result (0x33800000), with the pragma the unfused one (0x0); `p = x*y; p + z` is unfused in `safe` but fused in `relaxed` and `fast`. The pragma works at file scope in `header` and in the kernel body, in all three modes. Explicit `fma(a, b, c)` was bit-identical to the `fse._reference` rule in every run.
3. **Use `metal::precise::sqrt` for `normalize@1`; plain `sqrt` and `rsqrt` are not correctly rounded even with `safe`.** Measured over 2^20 random inputs: `precise::sqrt` 0 mismatches against numpy float32 sqrt; `sqrt` and `fast::sqrt` 327,574 mismatches; `precise::rsqrt` 283,396 mismatches against `1/sqrt` (that reference is itself double rounded, but do not use rsqrt anyway). `1.0f/x` and `precise::divide(1.0f, x)` had 0 mismatches for `safe` and for all n = 1 to 2^20-1; in `fast` mode `1.0f/x` is wrong in 19 % of cases. So `1/n` and `1/sqrt(s)` as `1.0f / precise::sqrt(s)` are fine under `safe`; do not rely on this under `fast`.
4. **MLX already compiles custom kernels without fast math, and exposes `compile_options={"math_mode": "safe"|"relaxed"|"fast"}` (default `"safe"`) since 0.32.0.** Before 0.32.0 the library was built with `setFastMathEnabled(false)` (diff of commit 51bef6fc). `"relaxed"` needs macOS 15. There is no `-ffp-contract` or `mathFloatingPointFunctions` option in MLX, so use pragmas and `precise::`.
5. **`dot16` maps exactly onto Metal and was bit-identical to `fse._reference.dot16` in my prototype** (2048 rows x 300, `safe` and `fast`, with the pragma): either one thread per row with 16 register accumulators and an unrolled 8/4/2/1 add tree, or 16 threads per row (thread = lane, `fma` chain over `i += 16`) and `simd_shuffle_down(…, 8/4/2/1)`; 32-wide SIMD-groups hold two rows, shuffles stay inside each half. **Do not use `simd_sum`**: its order is not specified in the spec and it matched neither a shuffle tree nor sequential order on M1 Pro (1513 and 1055 of 4096 equal).
6. **A pooling kernel (`weighted_mean@1`) with a gather is straightforward and was bit-identical** to the `fma32` reference on 40 random sentences: a thread per (sentence, dimension), loop over tokens in order, `acc = fma(w[t], X[t*D+d], acc)`, then `inv * acc` with `inv = precise::divide(1.0f, n)`. Measured: 42 M tokens/s (20,000 sentences, 391k tokens, 200k x 300 float32 table, M1 Pro, 9.3 ms), not tuned.
7. **half to float and int8 to float widening on the GPU is exact**: all 65,536 half bit patterns (non-NaN, including subnormal halves) and all 256 int8 values matched numpy. Float16 subnormals widen to normal float32 numbers, so they are not affected by finding 1.
8. **Threading and streams:** MLX got thread-safety support in 0.31.2 (maintainer closing statement on issue 2133, April 2026). Measured on 0.32.4: 4 Python threads each doing kernel + `mx.eval` on their own default stream, 300 times: no error, identical results, about 4x aggregate throughput of one thread. **A stream made with `mx.new_stream` in one thread cannot be used in another** ("There is no Stream(gpu, N) in current thread"). Design: the device thread creates and uses its own MLX objects; or use `mx.new_thread_unsafe_stream` (documented: usable anywhere, caller must prevent races) or `new_thread_local_stream`. A single device thread with a queue is the safest default, and `capabilities().concurrent` can then be False without much loss, unless pooling kernels are small.
9. **Cost model (measured, M1 Pro):** tiny kernel + `mx.eval` round trip about 205 µs (also with `MLX_METAL_FAST_SYNCH=1`); 100 tiny kernels queued and one `mx.eval`: 4.8 µs per kernel. Unseen kernel source: about 80 ms to build (first call in a process), a repeat in a new process with the same source 3.8 ms for a tiny kernel (probably the OS Metal shader cache; unverified). Python wheel `mx.array(numpy)` copies (29 ms for 64 MB); `mx.asarray(a, copy=False)` adopts a page-aligned (16 KiB) buffer without copy (0.13 ms) since MLX 0.32.1. So: batch many tasks per `mx.eval`, build each kernel once per process (module-level cache), page-align the buffers handed over.
10. **Packaging:** `mlx` 0.32.4 has wheels for CPython 3.10 to 3.15 and free-threaded 3.13t, 3.14t, 3.15t on macOS (arm64 only, `macosx_14_0`, `15_0`, `26_0`), also Linux (x86_64, aarch64) and Windows; `Requires-Python >=3.10`; on Darwin it depends on `mlx-metal==<same version>`. Intel Macs are not supported (CMake: building for x86_64 macOS "is not supported"). Minimum macOS 14. fse's 3.11 to 3.15 range is covered.

## 1. MLX custom Metal kernels

**API.** `mx.fast.metal_kernel(name, input_names, output_names, source, header="", ensure_row_contiguous=True, atomic_outputs=False, compile_options=None)` returns a callable. Call keywords (all keyword-only): `inputs`, `output_shapes`, `output_dtypes`, `grid`, `threadgroup`, `template=None`, `init_value=None`, `verbose=False`, `stream=None` (signature from `python/src/fast.cpp` on main). Introduced in MLX v0.17.0 (commit 0fd2a1f4, 2024-08-22); `compile_options` first in v0.32.0 (commit 51bef6fc, 2026-07-07); zero-copy `asarray(copy=False)` in v0.32.1.

- `source` is only the body; MLX generates the signature. Inputs become `const device T* name` (or `constant` for inputs with at most 8 elements: `max_constant_array_size = 8` in `mlx/backend/common/metal_kernel.cpp`), outputs `device T* name`, scalars may be passed as inputs. Names `<input>_shape`, `<input>_strides`, `<input>_ndim` and the attributes of Table 5.8 of the MSL spec (`thread_position_in_grid`, `threadgroup_position_in_grid`, `thread_position_in_threadgroup`, `threads_per_simdgroup`, `thread_index_in_simdgroup`, …) are added to the signature only if they occur in `source`. Outputs are always row contiguous. `ensure_row_contiguous=True` copies strided inputs first. MLX utility headers (`utils.h`, `elem_to_loc`) are prepended automatically (`metal::utils() + source_`).
- `header` goes before the function: helper functions, `constant constexpr` values, includes, **and file-scope pragmas**.
- `template=[("T", mx.float32), ("N", 16), ("FLAG", True)]` adds template arguments (dtype, int or bool); the kernel name includes a hash of the template, so each combination is its own pipeline. Compile-time constants such as the dimension `D` and the lane count are better as ints in `template` than as inputs (loop bounds known to the compiler), at the price of one pipeline per value.
- `grid` is passed to `dispatchThreads` (total threads, not threadgroups); `threadgroup` is clamped per dimension to the grid (`min(tx, gx)`). If `tx*ty*tz` exceeds `maxTotalThreadsPerThreadgroup` (1024 on M1 Pro) it raises `ValueError` **at `mx.eval`, not at the call** (measured). Because it is `dispatchThreads`, the grid need not be a multiple of the threadgroup size, but then the last threadgroup is partial, so kernels must guard `if (d >= D) return;` and must not use barriers or `simd_shuffle` across inactive lanes (a partially filled SIMD-group is possible). Choose grid sizes that are multiples of 32 (or of 16 lanes per row), or pad.
- `init_value` fills the outputs before the launch (a separate fill op); `atomic_outputs` makes outputs `device atomic<T>*` (not needed for fse: every output element has one owner).
- Limits seen: threads per threadgroup 1024 (M1 Pro, device and pipeline dependent, query by error message only; there is no Python getter that I found), max buffer length 9.5 GB and recommended working set 12.7 GB on a 16 GB M1 Pro (`mx.device_info()`), Metal's own argument-table limit (31 buffers per kernel, Metal feature set tables; not tested). Compile errors surface at `mx.eval` as `RuntimeError: [metal::Device] Unable to build metal library from source`; the Metal compiler message is printed.
- A CUDA twin exists on main (`mx.fast.cuda_kernel`, `python/src/fast.cpp`); I did not read its documentation, so its arguments, math flags and contract guarantees are unverified. For the device thread this suggests one backend-neutral "device kernel" interface and per-backend source strings.

**Caching / not compiling on every import.**
- MLX keeps built libraries in a per-device map keyed by `"{name}_{hash(source)}_{compile_options}"` (`mlx/backend/metal/custom_kernel.cpp`, `device.cpp::get_library`), protected by a shared mutex. The docs say: "Every time you make a kernel, a new Metal library is created and possibly JIT compiled", so build the `metal_kernel` object **once per process** (module level or `functools.cache` keyed by template values) and reuse it. Compilation is lazy: nothing is compiled at import, and nothing is compiled until the first `mx.eval` of a call.
- MLX has no on-disk cache of its own and no precompiled-kernel API for user code (the built-in kernels ship as a prebuilt metallib, compiled with `-fno-fast-math`). In my runs a second process with the same source needed 3.8 ms against about 83 ms the first time ever; that points to the OS Metal compiler cache, but I did not verify its location or lifetime. Plan on 50 to 200 ms per kernel family on the first use, unmeasured on other machines; compile lazily on first use of the backend, and in the test suite share a session-scoped kernel cache.
- Templates change the library: one source string with different `template` values is one library, one pipeline per template hash (kernel names differ).

**Versions.** MLX requires macOS >= 14 (CMake `FATAL_ERROR` below 14.0; release job builds wheels for deployment targets 14.0, 15.0, 26.2). The Metal language version used is picked at runtime (`device.cpp::get_metal_version`): 3.1 on macOS 14, 3.2 on 15, 4.0 on 26, 4.1 on 27. Consequence for the contract: **the same source is compiled by different compiler versions on different macOS versions**; the pragma/`precise::` forms must be tested on the oldest supported macOS (14, Metal 3.1). I could only test macOS 27 (Metal 4.1). Whether `#pragma METAL fp contract(off)` is accepted by the macOS 14 compiler is unverified (I only had the 4.1 spec; Apple's DTS says contraction options are documented in section 1.6.3 of the current spec). Set the `fse[mlx]` pin to at least `mlx>=0.32.1` if zero-copy input is wanted (>=0.32.0 for `compile_options`).

**Wheels (PyPI JSON for 0.32.4):** cp310 to cp315 and free-threaded cp313t, cp314t, cp315t for `macosx_14_0_arm64`, `macosx_15_0_arm64`, `macosx_26_0_arm64`; Linux `manylinux_2_35` x86_64/aarch64; Windows amd64/arm64; metadata extras `cuda`, `cuda12`, `cuda13`, `cpu` for Linux. `release.yml` on main lists `python-version: ['3.10', '3.11', '3.12', '3.13', '3.13t', '3.14', '3.14t', '3.15', '3.15t']`. So the free-threaded interpreters are supported by the wheels; whether the Python bindings are correct without the GIL I did not verify beyond 4-thread test on a normal build. The `mlx` import itself does not claim `Py_mod_gil` status that I checked.

## 2. Bit-exact floating point on Metal

**What the spec says (MSL 4.1):**
- 1.6.3: default `-fmetal-math-mode` is `fast` and `-fmetal-math-fp32-functions` default is `fast`. `fast` allows no-NaN, no-Inf, no-signed-zero, reciprocal, **reassociation** and fast contraction. `relaxed` honours Inf/NaN but keeps no-signed-zeros, reciprocal, reassociation, fast contraction. `safe` "disables unsafe floating-point optimizations by preventing the compiler from making any transformations that might affect the results. This sets the FP contract to on." Legacy `-fno-fast-math` = `-fmetal-math-fp32-functions=precise` + `-fmetal-math-mode=safe`. Contraction: "By default, the compiler allows floating-point contractions… To disable… `-ffp-contract=off`"; pragmas `#pragma METAL fp contract([off | on | fast])`, `#pragma STDC FP_CONTRACT OFF`, `#pragma METAL fp math_mode([relaxed | safe | fast])` (file/namespace scope, or start of a compound statement).
- 6.6: single-precision math functions have `precise::` and `fast::` variants (`metal::precise::sqrt`, `metal::precise::divide`, …); the compile option selects the unqualified variant.
- 8.1: "Denormalized single-precision, half-precision, or brain floating-point numbers passed as input to or produced as the output of … arithmetic operations **may be flushed to zero**." 8.2: "Either round ties to even or round toward zero rounding mode **may** be supported." 8.3: exceptions disabled.
- 8.4 Table 8.1 (precise): `+ - *`, `1/x`, `x/y`, `fma`, `sqrt`, `rsqrt` "Correctly rounded"; Table 8.2 (fast math): `1.0/x` "<= 1 ulp for x in the domain 2^-126 to 2^126", `sqrt` "Implemented as x * rsqrt(x)", `rsqrt` "<= 2 ulp".
- 8.6: float to half rounds to nearest even; half/bfloat to float "lossless"; "fast math does not change the accuracy of conversion operations". Metal 4.1 adds `-fmetal-rtz-fp-conversion` (default stays RTNE).
- 3.1: operators `+ - * /` follow IEEE for division by zero etc.; 5.? matrix multiplication: "order of partial sums … is undefined" (do not use `float` vector/matrix multiply for reductions).

**What MLX does:** `set_compile_options` in `mlx/backend/metal/device.cpp` maps `safe/relaxed/fast` to `MTL::MathModeSafe/Relaxed/Fast` (macOS 15+) or `setFastMathEnabled(bool)` (macOS 14, where `relaxed` raises). It never sets `mathFloatingPointFunctions`, i.e. the unqualified `sqrt`, `rsqrt`, `exp`, … stay the **fast** variants even in `safe` (consistent with my measurement). The test `python/tests/test_fast.py::test_custom_metal_kernel_math_mode` shows the macro `__FAST_MATH__` is defined only for `fast`. No `-ffp-contract` option is exposed.

**Measured on M1 Pro, macOS 27.0.1, MLX 0.32.4 (safe, relaxed, fast unless noted; scripts t1 to t5):**
| Check | Result |
|---|---|
| `fma(a,b,c)` explicit, normal numbers | matches the single-rounding rule (the dot16 prototype is bit-identical in all modes) |
| `x*y+z` in one statement, `safe` | fused (contracted); with `#pragma METAL fp contract(off)` unfused |
| `p=x*y; p+z`, `safe` | unfused; `relaxed` and `fast`: fused |
| header-level pragma vs body-level pragma | both work |
| `x/y` and `1.0f/x`, `safe` | IEEE correctly rounded for normal results (1,523 of 1,048,576 differ, all with subnormal reference results that the GPU flushed); `1/n` for n up to 2^20: 0 mismatches |
| `x/y`, `fast` | 30 % mismatches; `metal::precise::divide(x,y)` stays correct in `fast` mode too; `precise::divide(1.0f, x)` 0 mismatches in both modes |
| `sqrt` / `fast::sqrt` / `rsqrt`, any mode | not correctly rounded |
| `precise::sqrt`, any mode | 0 mismatches |
| subnormal inputs | flushed to zero by `+`, `*`, `-`, `fma`, `max`, `fma(.,.,sub)`; but `==0.0f` is true and load/store keeps the bits |
| subnormal results | flushed to zero (sign kept for `*`, e.g. 0x80000000) |
| `x + 0.0f` | `safe` returns +0 for -0.0 (IEEE); `relaxed` and `fast` drop the add, so `-0.0 + 0.0` stays -0.0 (no-signed-zeros): signed-zero handling of lanes differs by mode, another reason to stay in `safe` |
| half to float, all 65,536 patterns | exact, incl. subnormal halves |
| int8 to float, all 256 | exact |
| float32 to half of a subnormal-half value | correct (0x10, 0x1, 0x2 for 2^-20, 2^-24, 1.5*2^-24) |

**Apple's statement on this** (DTS Engineer, forum thread 844598, Sep 2026): "No API selects or queries the FP32 arithmetic rounding mode, and none controls or queries denormal handling"; the spec wording on denormals and rounding is a permission, not a guarantee; "Selecting safe math is not sufficient on its own" for contraction. The question of which GPU family does what was not answered; the Metal feature set tables "contain no rounding entries". A third-party doc snippet (Modular MAX) mentions "FTZ GPUs, including Apple M5" - I could not retrieve that page (404), so it is **unverified**.

**What this means for the plan.**
- Rounding: round to nearest even for `+ - * fma / sqrt` was observed on M1 Pro (mismatch-free against numpy), but it is only a permission in the spec. The conformance suite is then the only guarantee, run on each GPU generation in CI or on the maintainer's machine; GitHub-hosted macOS runners are VMs, whose GPU may be absent or paravirtual (unverified here; MLX's own loader has a code path for "headless, sandboxed, or virtualized macOS sessions" with no Metal device, in `device.cpp::load_device`).
- Subnormals: see summary item 1. Where can they occur in fse? (a) float32 word vectors with subnormal values (`x` input), (b) a factor `f = weight*scale` that is subnormal, (c) products `f*x` or sums in the accumulator that underflow, (d) the `1/n * acc` product, (e) `dot16` products. Detect-and-fall-back is cheap if the check is on the stored row/factor magnitude; a conservative check such as "the exponent field of f plus that of x is below the smallest normal plus 24, or any input is subnormal" must be derived and tested; I have **not** validated such a check.
- Recommended kernel preamble (all kernels): `header` starts with `#pragma METAL fp contract(off)`; `compile_options={"math_mode": "safe"}` (explicit, even though it is the default); only explicit `fma`, `metal::precise::sqrt`, `metal::precise::divide`; never `simd_sum`, never `rsqrt`, never `a*b+c` expecting a fused op. Consider a `#if defined(__FAST_MATH__) #error` guard in the header (the macro behaviour is demonstrated by MLX's test).
- Because Metal versions differ across macOS 14 to 27 (language 3.1 to 4.1), add a runtime self-check at backend `prepare`: run a small canary kernel (fused vs unfused case, a sqrt case, a division case, a subnormal case) and compare with the reference; refuse to run (raise, naming the check) if it does not match. This also catches the denormal behaviour of future GPUs.

## 3. float16, int8 and float64

- half to float: `float(as_type<half>(bits))` or reading `device const half*` and converting is exact on M1 Pro (all patterns). MLX passes float16 arrays as `float16_t` (`half`); int8 as `int8_t`; the code can read `T` through the template parameter. The Stage 2 factor rules (`f = weight * scale` with one rounding, `g = (1/m) * oov_weight`, each product rounded) are plain float32 multiplies, which are correct unless the result is subnormal (item 1).
- float64: Apple GPUs have no `double` in MSL (the spec's scalar types list `float`, `half`, `bfloat`; no `double`; PyTorch's MPS issue 125051 lists the same limitation). MLX `float64` arrays are CPU-only (MLX raises or runs on `mx.cpu` stream). Options for the Gram sum (later PR): (a) float32 block products on the GPU, float64 sum on the CPU in fixed block order, as in ARCHITECTURE.md (numpy does it today); (b) float32 product blocks with a fixed reduction order in a custom kernel; (c) double-float/two-sum on the GPU: not needed given (a). Note that `mx.matmul` has no documented summation order and, per the MLX precision page, float32 matmul may use reduced precision (TF32-like) on hardware with matrix units unless `MLX_ENABLE_TF32=0`; so if a deterministic block product is wanted, write a custom kernel (e.g. `fma` chains with fixed K order, like `dot16`) instead of `mx.matmul`; for a value that `fit` only needs "deterministic per machine" (ARCHITECTURE.md table) `mx.matmul` might be acceptable but it then depends on MLX version and hardware; that is a decision for that PR, not tested here.

## 4. Deterministic reductions and gather workloads

- **Fixed trees.** `dot16` is a fixed tree by construction; both layouts worked (see summary 5). Prefer the 16-threads-per-row version for d >= 64: it reads `rows[r*D + l + 16*m]` coalesced across the 16 lanes. In my test, B (16 threads/row) 262 µs against A (1 thread/row) 303 µs for 2048 x 300 including `mx.eval`, so launch overhead dominates and neither is tuned. The tail rule (a tail shorter than 16 updates only its own lanes) is automatically satisfied by `for (i = l; i < D; i += 16)`.
- **`simd_sum` order.** The spec (6.10.2, Table 6.15) says only "sum across all active threads", no order; measured equal to neither a pairwise shuffle tree nor sequential order. Likewise matrix/vector multiply in MSL: "the order of partial sums … is undefined". So only shuffle-based trees and register chains.
- **Row-level determinism requires that a row is produced by one threadgroup's fixed layout independent of batch composition.** If the kernel launch geometry for a row depended on the batch size (e.g. different threads per row for small and large batches), results must still be identical: keep the per-row algorithm independent of the grid.
- **Gather.** Layout: row-major `(V, D)` word table, one thread per (sentence, dim) with consecutive `d` in consecutive threads (coalesced 128 B segments per token row); `tokens` and `offsets` read per thread (cached; all threads of a sentence read the same ones). 391k tokens in 9.3 ms (42 M tokens/s) without tuning. Variants to try in the PR: a SIMD-group per sentence with `float4` loads (D=300 is a multiple of 4; D=100 is too; must keep per-element chains), shared `tokens` via threadgroup memory, 2D grid ordering so that the table row stays in cache; none was measured by me.
- **Unified memory.** `mx.array(np_array)` copies (29 ms for 64 MB). `mx.asarray(x)` (default `copy=None`) adopts the numpy buffer without copy when it is **page-aligned** (16,384 bytes on this machine) and otherwise copies; `copy=False` raises if it cannot adopt (`ValueError`), and refuses dtype conversions (MLX 0.32.1+, `python/tests/test_zero_copy.py`). A mutation of the source is visible in the array afterwards (measured), so the Python side must keep the buffer alive and unchanged until the evaluation is done; for reading results, `np.array(out)` copies; a zero-copy view of the result is not something I verified. For the vocabulary table (uploaded once in `prepare`) a copy is fine (240 MB in 28 to 42 ms). Output buffers allocated by MLX each call (and kept in MLX's cache); to avoid per-task allocation churn, MLX's allocator caches freed buffers (see 6).
- **Launch overhead and batching.** 205 µs per (kernel + `mx.eval` + back to Python) round trip; 4.8 µs per kernel when 100 are encoded and evaluated together (per-kernel encode cost). The runtime's tasks of 64 KiB to 1 MiB of text (hundreds to thousands of sentences) are large enough to amortise 0.2 ms, but a latency path (single short sentence) will be slower on the GPU than on the CPU; keep the "inline" CPU path for tiny inputs (the backend choice is explicit anyway).

## 5. Device thread design

- **Prior art.** PyTorch MPS: `MPSStream` has a serial `dispatch_queue_t`; encoders may only be used from blocks running on that queue; `getCurrentMPSStream()` is per thread and other threads can take streams from a round-robin pool of 32; the first asynchronous command-buffer error is stored under a mutex and rethrown "at the next sync point"; `synchronize(COMMIT_AND_WAIT / COMMIT_AND_CONTINUE / COMMIT_ADAPTIVE)`; `commitIfNeeded` commits after enough kernels so the GPU runs while the host keeps encoding (`aten/src/ATen/mps/MPSStream.h`). llama.cpp (`ggml-metal-context.m`): one shared command queue; the graph is encoded into up to 8 command buffers (`GGML_METAL_MAX_COMMAND_BUFFERS`), the main thread encodes the first part, workers via `dispatch_apply` the rest; "tests on M1 Pro and M2 Ultra … show that optimal values for n_cb are 1 or 2" and more "can degrade the performance"; submission is non-blocking and a later `synchronize` waits (`waitUntilCompleted`) and checks each command buffer's status; async copies return without waiting. Both: **one in-order queue per device, many CPU producers, errors reported at sync points**.
- **MLX specifics.** Lazy graph; `mx.eval(outs)` encodes and commits; it blocks until done. `mx.async_eval` exists (starts and returns; check the docs of that call for the memory semantics before using it); `mx.synchronize(stream)` waits. Thread model (MLX 0.32.4): each thread has its own default stream; `new_stream` is bound to the creating thread, `new_thread_unsafe_stream` is usable anywhere but "all nodes in a graph must be evaluated in sequence and it is user's responsibility to ensure there is no race condition", `new_thread_local_stream` makes one per thread (docstrings in `python/src/stream.cpp`). Thread safety was declared in 0.31.2 (issue 2133 closed 2026-04-24: "MLX has thread safety support in 0.31.2 now"; the closing comment does not list what is covered). Before that there were crashes with concurrent `mx.eval` (issues 2067, 3078, 3216). Issue 3727: from 0.31.2 a stream created in the main thread fails in a worker thread (closed as an mlx-lm fix; the cause is the stream thread affinity described above, which still holds in my 0.32.4 test).
- **Recommended shape for fse:** one **device thread** per backend instance (daemon, owns the MLX streams, uploaded tables and kernel objects, runs `prepare` and `mx.eval`); the runtime's workers submit `(inputs, out, Future)` through a queue. The worker does Stage 1 and 2 on the CPU without the GIL, the device thread takes tasks in order, encodes up to N tasks into one `mx.eval` (batching amortises the 0.2 ms; keep N bounded by the runtime window), and completes futures; the worker then copies or reads the output into the sink's target. Keep results ordered per task; "error of the first failing task in order" is natural because futures fail individually, but an asynchronous GPU error aborts the process in MLX (below), so validate on the host first (indices in range, offsets monotone) because an out-of-range read inside a kernel gives no error (measured: reads garbage/zeros silently).
- **Cost of a sync:** about 205 µs per `mx.eval` round trip on this machine (small kernel); `MLX_METAL_FAST_SYNCH=1` did not change it measurably here (205 vs 207 µs).
- **GIL:** `mx.eval` releases the GIL while waiting (nanobind `gil_scoped_release` is used in the stream code; for `eval` I did not read it, but the 4-thread test scaled), so a single device thread does not block Python workers. On free-threaded builds the same structure holds.
- **For CUDA later:** the same thread/queue with per-backend kernel sources; MLX CUDA wheels exist (extras `cuda12`, `cuda13`) but only 0.32.4 on Linux; I did not test.

## 6. Pitfalls

- **Lazy evaluation:** `kernel(...)` returns unevaluated arrays; shape/dtype/threadgroup-size errors and Metal compile errors appear at `mx.eval`. Evaluate before reusing or freeing the host buffer when using `copy=False` adoption.
- **Errors inside kernels:** no bounds checking (an out-of-range `a[t+100000000u]` read returned 0 without error in my test); a failed Metal command buffer (GPU timeout or memory pressure, watchdog) calls `check_error` from a completion handler, which throws on a libdispatch thread and **aborts the process** (MLX issue 3390, April 2026; maintainer: needs exception-safe `CommandEncoder`; workaround env `AGX_RELAX_CDM_CTXSTORE_TIMEOUT=1`; merged into issue 2670, status afterwards unverified). The runtime cannot recover from it, so bound the kernel duration per task (tasks of at most 16 MiB of rows already bound it) and validate all indices on the host.
- **Memory:** MLX caches freed buffers; `mx.get_cache_memory()`, `mx.set_cache_limit(bytes)`, `mx.clear_cache()`, `mx.set_memory_limit(bytes)` (default 1.5 x the recommended working set; allocations beyond raise), `mx.set_wired_limit` (macOS 15+) (`python/src/memory.cpp`). The old `mx.metal.*` names are deprecated aliases. The cache limit defaults to the memory limit, so a long run with changing buffer sizes can keep much memory; a backend should set a modest cache limit around its own run or call `clear_cache()` when a pipeline closes, and count the device memory of the window. The vocabulary table's device copy is an MLX array owned by the prepared object: release on close.
- **Free threading / process model:** forking after MLX use is not safe in general (issue 1231 "Large ops with multiprocess fail"); the fse runtime uses threads, which is fine.
- **Determinism across Apple GPU generations (M1 to M4/M5):** only M1 Pro (g13s) was tested. Apple documents no guarantee (section 8.1 and 8.2 permissions; DTS statements). Add the canary at `prepare` and a CI/manual conformance run on at least one newer chip; there is no way to query denormal mode. MLX's own docs state that float32 matmul-family ops may use reduced precision on hardware with dedicated matrix units (`MLX_ENABLE_TF32`), which shows that Apple generations differ in ways that matter; fse kernels avoid matrix units by writing explicit `fma` chains (note: `simdgroup_matrix` and `mx.matmul` must not be used for contract operations).
- **macOS/compiler differences:** the same source is compiled with Metal 3.1 (macOS 14) to 4.1 (macOS 27); results could differ by compiler version; the canary and the conformance run per macOS version cover this.
- **`ensure_row_contiguous`:** stays `True`; for the vocabulary table, pass the C-contiguous array once.
- **Unsupported platforms:** `import mlx.core` works on Linux CPU builds, but `mx.metal.is_available()` is False and `metal_kernel` raises "No Metal back-end"; the backend should check `mx.metal.is_available()` and raise a clear error naming `mlx` and the platform (the contract says: never fall back silently).

## What I did not verify

- Subnormal/FTZ behavior and rounding on any GPU except M1 Pro (g13s); the M5 claim.
- That `#pragma METAL fp contract(off)` and `precise::` behave identically under Metal 3.1/3.2 compilers (macOS 14/15).
- Whether `mx.eval` releases the GIL in all paths; behavior on free-threaded builds (not run).
- The origin of the fast second-process compile (OS shader cache vs. other).
- Throughput of a tuned pooling kernel versus the CPU kernel (my 42 M tokens/s kernel is an untuned prototype; no CPU comparison was run).
- CUDA kernel API details.
- Whether MLX issue 3390 (command buffer error aborts) has been fixed after April 2026.
