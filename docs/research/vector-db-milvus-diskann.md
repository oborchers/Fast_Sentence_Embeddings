## 1. Summary

1. **Neither project has an optimized exact scan for a larger-than-RAM store. Both solve the problem by not scanning.** Milvus brute force (`FLAT`, and the fallback for growing/unindexed segments) is a simple loop with one task per query that scans the whole segment; for data beyond RAM Milvus tells you to use DiskANN (docs: mmap "not supported for DiskANN", IVF "dropped seriously" under mmap). DiskANN's disk path reads **random 4 KiB sectors** and never streams. fse's design (blocks of rows times blocks of queries, shared floors) is already better than both for an exact scan. [verified, 3.1, 3.5, 4.2]
2. **What transfers to fse is therefore not a kernel trick but an I/O pattern**, and mostly from the DiskANN side: 4 KiB/512 B aligned reads, `O_DIRECT` to keep the page cache for what matters, a deep queue of outstanding reads, buffers owned by the reader. For a *sequential* scan the equivalent is: a prefetcher that runs several blocks ahead of the workers (`madvise`/`posix_fadvise` WILLNEED, or explicit large `pread`s into a ring of buffers), scan-resistant cache handling (`FADV_DONTNEED`/`MADV_COLD`/`O_DIRECT`), and one pass shared by all queries (already done). Expected effect: reach the device's sequential bandwidth instead of the page-fault-driven fraction of it. No published number for this exists in these sources; measure on a cold cache. [derived; 5.1]
3. **Two-stage "small in-memory sidecar, exact rescoring from disk" exists in both** (DiskANN: PQ codes in RAM, `FULL_PRECISION_REORDER_MULTIPLIER 3` x k full vectors re-read from disk; knowhere: `refine`/`refine_k` = `k_factor`, and the `DATA_VIEW` refiner that keeps only codes and reads raw data from the segment). **In both, the candidate count is a heuristic multiplier, so the result is approximate.** DiskANN's own range-query correction is statistical (mean +- k sigma of the distance ratio, RFC 00106), not a bound. No library publishes a worst-case bound that makes the two-stage result provably identical. [verified]
4. **A provable bound is possible in fse (integer sidecar, Cauchy-Schwarz tail, VA-file style) but it is weak at the compression a RAM-resident sidecar needs.** In my toy simulation (synthetic, d=384) a deterministic bound prunes nothing at 1 or 2 bits per dimension and leaves ~22 % of rows at 4 bits; a 50 % PCA prefix leaves ~10 %. A sidecar of 1 bit/dim is 1/8 of an int8 store (37.5 GB for 1B x 384), the only size that fits next to a 300 GB store, and there only probabilistic bounds (RaBitQ) are tight. The classic result (VA-file, VLDB 1998) is that exact methods in high dimensions degenerate toward a scan and only approximation-file filtering stays useful. So: **exact pruning will not give an order of magnitude on 384-dim embeddings; the guaranteed lever is bytes read per row and read bandwidth.** [toy + verified abstract-level claim, 5.4]
5. **Write path:** Milvus and DiskANN offer little that fse lacks. fse's publish protocol (exclusive rename, F_FULLFSYNC, parent sync, xxh3) is stricter than Milvus's (no per-file checksum found in its binlog writer; `O_DIRECT` mode skips `fdatasync`). Worth looking at: optional `O_DIRECT`/`F_NOCACHE` shard writes to avoid dirty-page storms and cache eviction when the store is much larger than RAM, incremental writeback (RocksDB `bytes_per_sync` analog), a write rate limiter if ingest and search share a device, and compaction of many small shards. [5.6]

## 2. fse today (what the comparison is against) [verified]

- Search (`src/fse/_store/_search.py:76-120`, `_tasks` at 247-253): row blocks of 4096 to 65 536 rows (`_TASK_SCORES = 1 << 20` scores per task), query slices of 256; for each row block the tasks of all query slices are consecutive, run by at most `workers` threads with a window of `2 * workers` tasks (`_run`, 256-272); every task starts with the **floors merged so far** (`candidates.floor[qb]`, line 227-228). Blocks are slices of memory-mapped npy files (`_layout.py:216`, `NpyContainer().open(..., mmap=True)`); nothing prefetches, advises or aligns, so each worker faults its own pages in.
- Write path: `_shard.py:110-150`: positional `pwrite` from a commit thread, xxh3 of the vectors in row order, `shrink`, `sync_file` (F_FULLFSYNC on macOS), small tensors each synced, manifest synced, exclusive directory rename, parent directory sync (`_container/_common.py:320-332`, `_npy_inplace.py:104-118`).
- Contract: int8 cosine is `dot16(codes, q) * inv_norm`, scale cancels (ARCHITECTURE.md, "Reading stored rows").

## 3. Milvus and knowhere

### 3.1 Brute-force path (knowhere FLAT and Milvus segment scan)

- **FLAT index** (`src/index/flat/flat.cc:75-157`, knowhere): `Search` pushes **one task per query** to the global search thread pool (`search_pool_->push`, line 100-101); each task sets OpenMP to 1 thread (`ScopedSearchOmpSetter setter(1)`, line 104), calls `checkCancellation(op_context)` first (line 102), then `index_->search(1, query, k, ...)` with `nq = 1` (line 122). Consequence [derived]: each query scans the whole index on its own, so memory/disk traffic is multiplied by the number of queries; there is no sharing of the pass. (fse reads each row block once for up to 256 queries.)
- **Segment brute force without an index** (`internal/core/src/query/SearchBruteForce.cpp`, `src/common/comp/brute_force.cc:685-711`, `300-356`): same shape, one task per query, `knn_inner_product_typed` / `knn_cosine_typed` for fp16/bf16/int8 with `nx = 1`. Cosine uses precomputed **inverse norms** (`GetInverseVecNorms`, `brute_force.cc:77-140`, computed in 8192-row chunks on the pool) and divides the query norm in the apply step (comment: "normalize query vector may cause precision loss", line ~332). fse stores `inv_norms` per row at write time instead of computing them per search.
- **Sealed segment loop** (`internal/core/src/query/SearchOnSealed.cpp:296-372`, milvus): `column->GetAllChunks(op_context)` pins all chunks, then a sequential `for` over chunks: `BruteForceSearch(...)` per chunk and `final_qr.merge(sub_qr)` (`SubSearchResult.cpp:25-99`: merges two k-lists per query). **There is no floor shared between chunks**, and the chunks are scanned one after the other, so with `nq = 1` the scan of a segment is single-threaded; parallelism comes from many segments or many concurrent searches. fse shares the running floor across tasks and across threads.
- **Top-k structure** (`thirdparty/faiss/faiss/cppcontrib/knowhere/utils/distances_typed.cpp:204-254`): `k < distance_compute_min_k_reservoir` (=100, `distances.cpp:806`) uses a binary heap (`HeapBlockResultHandler`), otherwise a **reservoir** (`ResultHandler.h:296-372`): an array of capacity > k filled while a value beats the threshold, then `partition_fuzzy` picks a new threshold. This is the same idea as fse's per-query floor plus `np.partition` in `best()`. [verified]
- **Filtering**: `BitsetViewIDSelector` is passed as `IDSelector` (`flat.cc:108-109`); the `*_ny_if` loops (`distances_if.h:645-690`) apply the filter **before** the distance and gather accepted ids in a buffer of `DEFAULT_BUFFER_SIZE = 8` (`distances_if.h:29`), then compute 4 distances per call (`*_batch_4`, the query vector is loaded once for four rows). Relevant to fse only for a future tombstone bitset: filter first, so deleted rows are not even read.
- **Thread pool**: `knowhereThreadPoolNumRatio: 4` (`configs/milvus.yaml:671`; "if disk is enabled, the pool size will multiply with..."). Search tasks are merged by the scheduler: `queryNode.grouping.maxNQ: 64`, `nqMergeRatio: 16` (`milvus.yaml:787-788`), i.e. several user requests become one task with a larger nq, but knowhere still loops per query.

### 3.2 SIMD distance dispatch [verified]

- Function pointers per operation, defaulted to the `_ref` versions and **overwritten once at startup** by `fvec_hook` (`src/simd/hook.cc:188-356`): a chain AVX-512 (needs F, DQ, BW) -> AVX2 -> SSE4.2 -> reference; separate sets for fp32, `ivec` (int8, legacy HNSW SQ), `fp16_vec_*`, `bf16_vec_*`, `int8_vec_*` and each with a `_batch_4` variant (`hook.h:91-124`). On aarch64: NEON/SVE; also RVV, LSX/LASX, POWER. Milvus exposes a `common.simdType` override (`milvus.yaml:1336-1340`). fse's `_native_kernel.h` does the same with ISA detection at load; nothing new.
- **int8 kernels are plain C loops with int32 accumulation**, no intrinsics: `int8_vec_inner_product_avx512` (`src/simd/distances_avx512.cc:692-699`) is `res += (int32)x[i] * (int32)y[i]` under `FAISS_PRAGMA_IMPRECISE_LOOP`, returned as `float(res)`; `int8_vec_inner_product_batch_4_avx512` (729-747) does 4 rows against one query. The compiler vectorizes it; integer sums are associative so the "imprecise" pragma changes nothing for int8. Knowhere's int8 is a native `Int8Vector` field type (both query and base int8, no per-row scale), not SQ8. This confirms the point in the earlier survey: integer dot products are order-independent, so an integer prefilter does not conflict with fse's float contract as long as the final score is recomputed by the kernel.
- fp16/bf16: widen to float in the kernel (F16C/AVX-512), accumulate in float; `convert_data` in the refiner is a scalar loop with the comment "todo: use simd to convert, these codes cost much cpu time" (`data_view_dense_index/refine_computer.h:25-45`).

### 3.3 SQ8/int8 and "refine" (rescoring) [verified]

- **Knowhere refine** (`src/index/refine/refine_utils.cc:18-187`): `refine_type` in `{sq4u, sq6, sq8, fp16, bf16, int8, fp32/flat}`; `pick_refine_index` wraps a base index in `IndexRefineFlat` (fp32 raw vectors) or `IndexRefine` with an `IndexScalarQuantizer` refine index. Search: `base_index->search(n, x, k_base = k * k_factor, ...)`, then exact (or SQ) distances for those `k_base` candidates, then `reorder_2_heaps` to the best k (`thirdparty/faiss/faiss/cppcontrib/knowhere/IndexRefine.cpp:80-130` and `284-330`). Parameters: build `refine` (bool, default false), `refine_type`; search `refine_k` (float, default 1, range 1..max; `ivf_config.h:127-142`, `hnsw/faiss_hnsw_config.h:37-52`), mapped to `refine_search_params.k_factor` (`ivf/ivf.cc:1029-1052, 1133-1149`; `hnsw/faiss_hnsw.cc:1552`). Applies to IVF_PQ, IVF_SQ, IVF_RABITQ (1-bit codes, `rbq_bits`, `rbq_bits_query`), HNSW. The Milvus doc page for IVF_SQ8 lists only `nlist` and `nprobe` (page fetched, no `refine` there). [verified]
- **`DATA_VIEW` refiner** (`src/index/data_view_dense_index/data_view_index_config.h:20-31, 118-127`; `index_node_with_data_view_refiner.h:478-526`): the index keeps **only the quantized codes**, "not alloc extra memory in refiner"; the raw vectors stay in the segment (mmap/columns) and `refine_offset_index_->SearchWithIds(...)` rescored `k * refine_ratio` candidate ids against it. Options for an in-memory refiner copy: `FLOAT16_QUANT`, `BFLOAT16_QUANT`, `UINT8_QUANT`; `refine_with_quant` trades a little precision for speed. This is exactly the "small sidecar in RAM, exact rescoring from the stored rows" architecture. Milvus sets it for its **growing-segment interim index**: `queryNode.segcore.interimIndex` (`milvus.yaml:673-686`): `denseVectorIndexType: IVF_FLAT_CC`, `nlist 128`, `nprobe 16`, `refineRatio 4.5` (the compiled default is 3.0, `SegcoreConfig.h:357`), `refineQuantType NONE`, `refineWithQuant true`, `indexBuildRatio 0.1`. `IndexConfigGenerator.cpp:97-105` puts `nprobe`, `refine_ratio`, `refine_with_quant` into the search parameters.
- **Exactness: no.** `k_factor`/`refine_ratio` are fixed multipliers; recall is whatever the base index returns within `k * factor`. Published effect: Milvus gives no recall numbers on its IVF_SQ8 page ("The page gives no numeric recall figures"). For the RaBitQ code, the paper claims a sharp theoretical error bound for the estimator and better accuracy/efficiency than PQ (arXiv 2405.12497 abstract, fetched; no numbers in the abstract); the bound is probabilistic.
- **fse relevance:** the sidecar-plus-exact-rescore pattern is universal; the only new element in this section is that Milvus keeps the **raw data in the segment as the single source of truth and the quantized structure separate**, which maps one-to-one onto fse's immutable shards plus an optional derived sidecar tensor.

### 3.4 Segment design: growing, sealed, flush, binlog, WAL, checkpoints, compaction [verified unless marked]

- **Growing segment** (`internal/core/src/segcore/SegmentGrowingImpl.*`): in-memory columns split into chunks of `chunkRows: 128` rows (`milvus.yaml:672`); searched by brute force or by the interim index above (built when `indexBuildRatio` of the max rows is reached); `queryNode.mmap.growingMmapEnabled: false` (`milvus.yaml:759`) can back growing raw data with mmap.
- **Seal rule** (`datacoord.segment`, `milvus.yaml:858-872`): `maxSize 1024` MB, `sealProportion 0.12` (+ jitter 0.1), `maxLife 86400` s, `maxIdleTime 600` s, binlog-count limit. So a segment becomes sealed at about 12 % of 1 GiB (~123 MiB) once it is idle or old, or at max size. fse's shard (256 MiB default) is in the same range.
- **Flush** (`internal/flushcommon/syncmgr/task.go:128-218`, `meta_writer.go:101-160`): a `SyncTask` writes the binlog files (insert, delta, stats, bm25) to object storage with retries, **then** calls `SaveBinlogPaths` (data coord) with the segment's binlog paths and `StartPositions` (the WAL checkpoint) and `Flushed`, **then** updates the in-memory cache. Order: data first, pointer second, which is the same discipline as fse's "files, manifest, rename". Data node buffers: `insertBufSize` 16 MiB, `deleteBufBytes` 16 MiB, `syncPeriod` 600 s, memory-pressure force sync at `forceSyncWatermark 0.5` (`milvus.yaml:1086-1100`).
- **Binlog format** (`internal/storage/binlog_writer.go`, `binlog_reader.go:34-75`): magic number `0xfffabc`, a descriptor event, then event-wrapped Parquet payloads. I grepped `event_writer.go`/`event_header.go` for CRC/checksum and found none [verified absence by grep, not a proof]. Storage V2/V3 use packed Arrow/Parquet column groups and a manifest (`pack_writer_v2.go`, `pack_writer_v3.go`; docs `20260226-manifest-format.md`).
- **WAL / message queue** (`milvus.yaml:179-340`, `1732-1830`): Milvus 2.6 "streaming node" with pluggable WAL (pulsar, kafka, rocksmq, **woodpecker**). Woodpecker settings: client-side **group commit** (`maxBatchEntries 1000`, `maxBatchBytes 2000000`, "opportunistic ... adds no latency at low load", lines 204-205), log-store sync policy `maxInterval 200ms`, `maxIntervalForLocalStorage 10ms`, `maxBytes 256M`, `maxEntries 10000`, `maxFlushThreads 32` (lines 276-285); segment rolling 256 MB / 10 min (208-210). WAL recovery info is persisted every `walRecovery.persistInterval: 10s` or 100 dirty messages (lines 1826-1833) and "doesn't affect the recovery of data flush into object storage". Channel checkpoints are pushed every `updateChannelCheckpointInterval: 60` s (`milvus.yaml:1107`).
- **Compaction** (`internal/datanode/compactor/`): `l0_compactor.go` (delete-only L0 segments applied to others; forced at 64 MB, `milvus.yaml:935`), `mix_compactor.go` (merge segments, drop deleted rows), `clustering_compactor.go` (rewrite by a clustering key, so that segments can be pruned), `merge_sort.go`. Deletes are never in-place: they go to delta logs and are applied as **bitsets** at search (`BitsetView` into knowhere).
- **fse relevance:** (a) fse is "sealed only"; a searchable growing tail is a different feature (out of scope). (b) The only segment-management mechanism that matters for the stated problem is **compaction of small shards** (G) and **clustering compaction** (F). (c) Group commit and WAL matter only for single-row appends, which fse does not have.

### 3.5 mmap for sealed segments and the page cache [verified]

- Configuration (`milvus.yaml:750-761`): `queryNode.mmap.vectorField: true`, `vectorIndex: false`, scalar fields/indexes false, `growingMmapEnabled: false`. Docs (https://milvus.io/docs/mmap.md, fetched): "when the amount of data exceeds memory by too much, search and query performance may suffer serious degradation"; HNSW recommended for mmap, IVF-series "dropped seriously" in Milvus's tests; **mmap not supported for DiskANN** (which does its own `O_DIRECT` I/O); NVMe recommended; the page does not mention the OS page cache.
- Mechanism (`internal/core/src/common/ChunkTarget.cpp:62-100`): a chunk is written to a local file through `FileWriter`, padded to capacity, then `mmap(PROT_READ, MAP_SHARED | (populate ? MAP_POPULATE : 0))`. Warm-up: `queryNode.segcore.tieredStorage.warmup.vectorField: disable` by default (lazy page faults), `vectorIndex: sync` (`milvus.yaml:693-706`). Tiered storage has its own cache with watermarks `memory/diskLow 0.75`, `High 0.8`, `evictionEnabled: false` by default, time-based `cacheTtl` (`milvus.yaml:708-735`).
- **Read-ahead:** `queryNode.cache.readAheadPolicy: willneed` (`milvus.yaml:749`, `pkg/util/paramtable/component_param.go:5483-5488`) is only **plumbed** to a `cache_read_ahead_policy` field (`storage_c.cpp:137-138`, `Types.h:164`); a repository-wide grep finds **no** `madvise`/`posix_fadvise` call that uses it for vector data. The only `madvise` calls are `MADV_SEQUENTIAL` in the bitmap index loader (`BitmapIndexLoader.cpp:923, 1266`) and `MADV_REMOVE/DONTNEED` in `SparseVortexFileSystem.cpp:264-290`. So Milvus **leaves vector pages to the kernel's default fault-driven read-ahead** and does nothing for scan resistance. [verified by grep over the sparse checkout; paths outside the sparse checkout, such as the separate milvus-common caching layer, were not read]
- Page cache vs own cache: Milvus runs both (OS cache under mmap, plus the tiered cache for cell-level load/evict). fse is a library in a user process; the OS page cache is the right single cache; what Milvus teaches is the **watermark-based eviction** idea only if fse ever manages its own cache (it should not).

### 3.6 Write-path settings worth noting [verified]

`FileWriter` (`internal/core/src/storage/FileWriter.cpp`):
- Two modes, `diskWriteMode: buffered|direct` (`milvus.yaml:1343`), buffer `diskWriteBufferSizeKb: 64` (4..65536), high-priority writes always buffered (`FileWriter.cpp:111-114`).
- `direct`: `O_DIRECT` (Linux) or `fcntl(F_NOCACHE)` (macOS) (lines 134-155); an `aligned_alloc` buffer; unaligned tails go to the buffer, the final partial block is zero-padded, written, then `ftruncate` to the real size (296-318). **No `fdatasync` in direct mode** (`Finish`, lines 333-355: `fdatasync_on_finish_ && !use_direct_io_`). These are re-downloadable local cache files, so durability is not needed; **fse's shards are the source of truth, so the same trick would need an explicit fsync.**
- Buffered: `pwrite` loop with a **token-bucket write rate limiter** (`diskWriteRateLimiter.avgKBps 262144` = 256 MB/s average, burst 512 MB/s, 100 ms refill; `milvus.yaml:1353-1356`; `FileWriter.cpp:60-100` waits with exponential backoff, and gives up the limit after `MAX_EMPTY_LOOPS`), `fdatasync` on non-Apple, `fsync` on Apple (215-220) when `SetFdatasyncOnFinish` was called, and a global write-permit pool `LocalFileIOPool` (`diskWriteNumThreads`) bounding concurrent file writes.
- RocksDB (not Milvus, for comparison) documents the incremental writeback option: `bytes_per_sync` "Allows OS to incrementally sync files to disk while they are being written, asynchronously, in the background ... smooth out write I/Os over time. Users shouldn't rely on it for persistence guarantee"; `strict_bytes_per_sync` caps pending writeback to avoid "a huge sync when the file is finished" (rocksdb `include/rocksdb/options.h:1341-1373`, commit `302eaa8b1f5b04ee56c9d79236c514fcd9f413fc`). [verified]

## 4. DiskANN

### 4.1 SSD layout [verified]

- Original C++ (`cpp_main`, `src/disk_utils.cpp:918-1062`, `src/pq_flash_index.cpp:102-111`): file of 4096-byte sectors (`defaults::SECTOR_LEN`), sector 0 = metadata (including `max_node_len`, `nnodes_per_sector`, reorder flag). Node = `(degree + 1) * 4` bytes of neighbor ids + `ndims * sizeof(T)` bytes of the **full-precision vector**: `max_node_len = ((width+1)*4) + ndims*sizeof(T)`; `nnodes_per_sector = 4096 / max_node_len` (0 if a node is larger than a sector, then a node takes `ceil(max_node_len/4096)` whole sectors). `node_id -> sector 1 + node_id / nnodes_per_sector`, offset `(node_id % nnodes_per_sector) * max_node_len`. **A node never straddles a sector**, so one node is one aligned read.
- Optional **reorder section** after the graph: full-precision `float` vectors packed `SECTOR_LEN / (ndims * sizeof(float))` per sector (`disk_utils.cpp:945-948`, `pq_flash_index.cpp:22-26` `VECTOR_SECTOR_NO`/`VECTOR_SECTOR_OFFSET`). Used when the nodes themselves hold only a disk PQ code.
- Memory: PQ-compressed vectors of **all** points in RAM (`_pq_data`), a cache of hot node neighborhoods (BFS levels from the medoid). Rust: same layout versioned as `GraphLayoutVersion(major, minor)`, `num_nodes_per_block`, `DEFAULT_DISK_SECTOR_LEN = 4096` (`diskann-disk/src/data_model/graph_layout_version.rs`, `search/provider/disk_sector_graph.rs:19-150`, commit `1e906aa`).

### 4.2 Search I/O: beam width, aligned reads, async [verified]

- C++ reader (`cpp_main` `src/linux_aligned_file_reader.cpp`; knowhere copy `thirdparty/DiskANN/src/linux_aligned_file_reader.cpp:21-120, 146-153, 177-265`): **libaio** (`io_setup`, `io_prep_pread`, `io_submit`, `io_getevents`), file opened `O_DIRECT | O_RDONLY | O_LARGEFILE`, each request `{offset, len, buf}` must be **512-aligned in offset, length and buffer** (debug asserts at lines 23-31), requests chunked into batches of `MAX_EVENTS = 1024` (`cpp_main`) per `io_context`, one context per thread (`register_thread`, `get_ctx`). Knowhere's fork adds a context pool and a split API: `submit_req` (post the reads) and `get_submitted_req` (collect) at lines 177-265, i.e. **overlapping I/O with compute is possible**, but the beam search itself calls the synchronous `reader->read(frontier_read_reqs, ctx)` ("synchronous IO linux", `pq_flash_aisaq_index.cpp:1525-1531`; `cpp_main pq_flash_index.cpp:1473-1481`).
- Beam search (`pq_flash_index.cpp:1238-1620`): `beam_width` (default 8: `DEFAULT_DISKANN_BEAMWIDTH`, knowhere `defaults.h:30`) unexpanded nodes are read **in one batch of aligned sector reads**, then expanded; neighbor distances come from the in-RAM PQ table. `MAX_N_SECTOR_READS = 128` (256 in knowhere's fork) bounds the scratch. `io_limit` stops a query after a number of reads (Rust `search_io_limit`, `disk_provider.rs:95, 894-920`; graceful recall loss tested at 3057-3132).
- **Overlap in the original is across queries, not within one**: each search thread has its own context and blocks on its own reads; concurrency of many query threads fills the SSD queue. PipeANN (OSDI 2025, Guo and Lu) replaces the synchronous beam with an asynchronous pipeline that overlaps CPU and I/O; reported by the authors: latency 1.14x to 2.02x of in-memory Vamana and ~35 % of DiskANN's on billion-scale data (abstract as summarized by papers.cool via search; **[unverified]**, not read in full; others report GIST-like high dimensions become compute-bound).
- **Rust rewrite** (`diskann-disk/src/search/provider/aligned_file_reader/reader/linux.rs:21-123`, commit `1e906aa`): **io_uring**; `IoUring::new(128)` (`MAX_IO_CONCURRENCY = 128`), file opened `O_DIRECT`, `register_files` (fixed-file slot 0), `A512` aligned buffers, per batch of <= 128 `opcode::Read` entries submitted with `submit_and_wait(batch_size)`, then the completion queue is drained ("N.B.: Flushing the completion queue appears to be important for proper operation"). Still a **submit-batch-and-wait** structure; no registered buffers (`iov` is built but passed as a plain pointer), no SQPOLL.
- **Rerank with full vectors from disk** (`cpp_main pq_flash_index.cpp:1616-1668`): after the beam search, `full_retset` is cut to `k_search * FULL_PRECISION_REORDER_MULTIPLIER` (**3**, `pq_flash_index.h:19`), one 4096-byte aligned read **per candidate** (`VECTOR_SECTOR_NO`), exact distances, sort. Rust: `RerankAndFilter::post_process` (`disk_provider.rs:450-513`) collects candidate ids not in the distance cache (`uncached_ids`), `ensure_vertex_loaded(...)` loads them as one batch, then exact distances (`distance_comparer.evaluate_similarity`) and sort. So the rerank is **one batch of aligned reads for the whole candidate set**, issued only after the traversal.
- **Flat scan exists in the Rust DiskANN** (`SearchMode::FlatScan`, `search_mode.rs:22-72`; `flat_search`, `disk_provider.rs:1157-1210`): a brute-force pass over the **in-memory quantized data**, top `neighbors_before_reranking`, then the same `RerankAndFilter` against full-precision vectors read from the disk index. Doc comment: "The top `neighbors_before_reranking` candidates from the quantized scan will be provided to full-precision reranking." This is the closest existing implementation of the two-stage scan; it is a **recall baseline**, not exact, and candidate count is a user parameter. The design RFC (`rfcs/00983-flat-search.md`, 2026-04-24) states the scan is sequential, single-threaded per query (`DistancesUnordered` takes `&mut self`, "precluding internal parallelism ... left for future work"), and lists batched distance computation "for better cache utilization" as an open alternative. Post-processing/rerank for flat search was still "planned" in the RFC.
- **Statistical, not provable, bounds** (`rfcs/00106-quantized-range-query-correction.md`): range queries on quantized data are corrected with ratio statistics, `T_q = T / (mu - k sigma)` (upper bound query) or `T / (mu + k sigma)`, k = 2 for 95 %, then full-precision rerank; measured ratios on openai-v3 1M: PQ 384 chunks mean 1.185, sd 0.0237; 1-bit spherical mean 1.0005, sd 0.024; 2-bit sd 0.0133 (RFC tables). So even DiskANN's authors do not claim a worst-case bound. [verified]
- Published effect of the whole design: DiskANN NeurIPS 2019 abstract: index, store and search a **billion points on one workstation with 64 GB RAM and an SSD**, ">5000 queries a second with <3 ms mean latency and 95 %+ 1-recall@1 on a 16 core machine" for SIFT1B, 5 to 10 times more points per node than HNSW/NSG (https://papers.nips.cc/paper_files/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html, fetched). **Not exact.**

### 4.3 Fresh and Filtered variants: write path [verified from paper text and README]

- Fresh-DiskANN (arXiv 2105.09613; PDF text extracted locally): a long-term SSD index (LTI) plus in-memory TempIndexes (one read-write, several read-only snapshots) and a DeleteList; updates go to a **redo log** and TempIndex snapshots; **StreamingMerge** periodically folds them into a new LTI. Section 5.4: "The procedure does exactly two sequential passes over the SSD-resident data structure in the Delete and Patch Phases", plus about 100 random 4 KB reads per inserted point in the insert phase; memory ~`O(|N| R)` (~7 GB for 30 M points, R = 64). Evaluation: "StreamingMerge with 40 threads takes around 16000 seconds to merge 30M inserts and deletes into a 800M point LTI (a 7.5% change), which is 8.5% of the ~190000 seconds it would take to rebuild the index from scratch"; 3600 updates/s need 40 threads; with 10 threads, 1000 updates/s with more predictable search latency. Abstract: 5-10x lower cost of maintaining freshness than periodic rebuilds.
- Rust README (`README.md:16`): real-time updates "using logic from IP-DiskANN and Fresh-DiskANN ... no merges, rebuilds, patches needed"; dynamic in-memory index is separate (`diskann-inmem`), and the disk index is still built offline.
- Filtered-DiskANN (label-aware graph build and search; Rust `InlineFilter` search mode, `search_mode.rs`; `adaptive_l` widens the beam when few results match): affects graph traversal only; **nothing transferable to an exact scan** beyond "apply the predicate before computing/reading".
- Relevance to fse: the write path of a *rebuilt-in-batches* immutable file set with a sequential merge pass is exactly fse's model (immutable shards, appends add shards). The merge lesson is **throughput predictability**: the number of merge threads is chosen to meet an update rate while keeping search tails stable (paper sec. 6), analogous to the write-rate limiter in 3.6.

## 5. What applies to fse

### 5.1 I/O pattern for the exact scan (A, B, C) [mostly derived]

What fse does: `blocks()` hands out `(shard, begin, end)` row ranges in store order; up to `2 * workers` tasks are in flight; each worker's first touch of its block triggers page faults. What the sources do differently:

| Source | Pattern | Why it matters for a scan |
|---|---|---|
| DiskANN `linux_aligned_file_reader.cpp` / Rust `linux.rs` | explicit aligned reads, `O_DIRECT`, many in flight (128 to 1024), per-thread context | queue depth is chosen by the program, not by fault-around; no page-cache copy |
| Milvus mmap | pages left to the kernel (no madvise on vectors, 3.5) | fault-driven read-ahead; same as fse today |
| `madvise` / `posix_fadvise` man pages (fetched) | `POSIX_FADV_SEQUENTIAL` "doubles" the read-ahead size; `POSIX_FADV_WILLNEED` "initiates a nonblocking read of the specified region into the page cache" (may load less under memory pressure); `POSIX_FADV_DONTNEED` frees clean cached pages, dirty pages must be synced first, only whole pages; `MADV_COLD`/`MADV_PAGEOUT` (since Linux 5.4), `MADV_POPULATE_READ` (5.14) | the building blocks for a prefetcher and for scan resistance |

Proposals:
- **A. Prefetch ahead.** In `_tasks()`/`_run()` the generator knows the next blocks: before submitting block `i` call `posix_fadvise(fd, offset, length, WILLNEED)` (or `mmap.madvise(MADV_WILLNEED, ...)`) for block `i + D` (D = 2 to 4 blocks; one block is 4096 to 65 536 rows, i.e. 1.5 MB to 25 MB of int8 at 384 dims). Block boundaries should be rounded to 4 KiB. On Linux this raises the effective queue depth above `workers x read-ahead window`. macOS has no `posix_fadvise`; use `fcntl(F_RDADVISE)` or just rely on the mmap read-ahead there (dev machine only). Alternative with the highest ceiling: one I/O thread doing large `preadv` into a ring of page-aligned buffers (also enables `O_DIRECT`), at the cost that the kernel receives copies instead of mapping. Files: `src/fse/_store/_search.py` (`_tasks`, `_run`), the mapped file handles in `_store/_layout.py:216`. Effort S for the advice variant, M for the ring. Exact: yes (reads only). Effect: **[unverified]**; measure with a cold cache (`purge`/`drop_caches`) on a store of 2x RAM, tracking MB/s against `fio --rw=read --bs=1M --iodepth=16` on the same file as the ceiling.
- **B. Scan resistance.** A scan of 30 to 300 GB through the page cache evicts everything else, including a hot sidecar, other stores, and the process's own working set. After a block is finished call `posix_fadvise(DONTNEED)` for it (clean pages only, page-aligned), or `MADV_COLD` (Linux 5.4+), or read with `O_DIRECT`. Expose as an option (`cache="keep"|"drop"`) because a store that fits in RAM wants the opposite. File: `_search.py`. Effort S. Exact: yes.
- **C. Amortization and loop order.** Already right: for each row block all query slices follow each other (`_tasks`, 247-253), so a block is read from disk once and served to up to 256 queries in cache. For an I/O-bound store the cost per scan is `bytes / bandwidth` regardless of the number of queries; the kernel path costs roughly `rows x dim` MACs per query. So up to the number of queries where compute time equals scan time, extra queries are free [derived]: e.g., 300 GB at a hypothetical 3 GB/s is 100 s per scan; at a hypothetical 50 GB/s of kernel throughput per query-pass it takes 6 s per query, so ~16 queries per scan are "free" (both numbers are placeholders; measure). knowhere/Milvus do the opposite (one full pass per query, 3.1). A cross-caller **shared scan** (several `search()` calls coalesced into one pass; "Cooperative Scans", Zukowski, Heman, Nes, Boncz, VLDB 2007, pp. 723-734, shows bandwidth sharing between concurrent scans reduces I/O and execution time, per its abstract) is the server-side version; for a library it is simply "pass all pending queries in one `search`", already supported. No change needed beyond documenting it.
- **Cancellation:** knowhere calls `checkCancellation(op_context)` at the start of each task (`flat.cc:102`). A check between blocks in `_run` would bound the latency of an abandoned scan of a 300 GB store (a scan is minutes). Effort S. Not about speed.

### 5.2 Layout details worth copying (alignment) [derived from DiskANN]

DiskANN guarantees that a record never straddles a 4 KiB sector (`nnodes_per_sector = 4096 / max_node_len`) so each random read is one aligned I/O. fse's rows are int8 of `dim` bytes in an npy file whose data offset is whatever the npy header gives (`_npy_inplace.py` pads the header to a fixed offset; I did not check that it is 4096-aligned). For a **scan** this does not matter; for **random rescoring reads** (proposals D, E) it does: with 384-byte rows ~10.7 rows share a page, and a row that straddles two pages costs two page reads. Padding the data offset to 4096 and gathering by page is enough; padding rows to divide 4096 would waste space (384 B does not divide 4096; 512 B would). Do not change the row stride; sort survivors by row id and read page-aligned runs.

### 5.3 Two-stage design without becoming an ANN database (D, E, F)

The pattern both projects use: stage 1 cheaply scores everything from a small in-memory structure; stage 2 re-reads the **full stored rows** of the survivors and rescoring uses the existing kernel, so the final scores are bit-identical to the contract. Whether the final top-k is also identical depends only on whether stage 1 can lose a true top-k row.

Cost model [derived] for a store of S bytes and N rows, device with sequential bandwidth `B_seq` and random-read bandwidth `B_rand` at deep queue, survivors `s`, page 4 KiB: a plain scan takes `S / B_seq`; the two-stage path takes `sidecar_bytes / mem_bw` (RAM) `+ s x 4 KiB / B_rand`. With `B_rand ~ B_seq` (a fast NVMe at queue depth > 32 is the regime where this holds; on slower drives it is worse) the rescoring wins only if `s < N / rows_per_page`, i.e. fewer than ~1 in 10 rows for 384-byte rows. So a pruning rate **above ~90 %** is the entry ticket for exact rescoring from disk; from there each further 10x reduction in survivors is nearly free.

### 5.4 A provable bound for fse (D) [derived; the numbers are a toy]

Setting (extends survey section 1). For an int8 store, `cos(q, row_i) = dot(c_i, q_hat) * inv_norm_i` with `inv_norm_i = 1/||c_i||`. Let the sidecar hold an approximation `a_i` of `c_i`, with `e_i = c_i - a_i` and per-row `r_i = ||e_i|| / ||c_i||` stored (float16, rounded up). Then for the true real-number cosine

`| cos_i - dot(a_i, q_hat)/||c_i|| | <= ||e_i||/||c_i|| * ||q_hat|| = r_i`   (Cauchy-Schwarz; `||q_hat|| = 1`)

and, if the integer sidecar is multiplied with a **quantized query** `s*q_int` instead of `q_hat`, add `eps_q = ||q_hat - s*q_int||` (computed once per query). Add a small `delta` for the float32 rounding of the kernel's `dot16` (a standard `gamma_d` bound, order 1e-4 for d = 384) so the upper bound `U_i = est_i + r_i + eps_q + delta` bounds the **float32 contract score**. A row may be dropped only if `U_i < floor` with a strict inequality (ties are decided by row id, so a pruned row cannot be the tie winner).
The floor must be a valid lower bound on the final k-th best score: after any exact rescoring of >= k rows, the k-th best exact score among them is such a bound; start by rescoring the sidecar's top `k'` (any heuristic choice is fine for correctness, it only affects speed), then stream the scan with the running floor (this is exactly how fse's `candidates.floor` already works), and fetch the survivors in row order. The result is exact for any `k'`: the heuristic multiplier of DiskANN/knowhere becomes a performance knob, not a correctness knob. This is the **VA-file** scheme (Weber, Schek, Blott, VLDB 1998, pp. 194-205: approximation file scanned first, vectors fetched only if the lower bound beats the current k-th best; the paper's conclusion, per the abstract, is that clustering/partitioning methods degenerate to a scan in high dimension and the approximation-based VA-file is best when dimensions > ~6) [abstract-level only; the PDF is a scanned image and I could not read the algorithm text, so the bound formulation is mine].

Where the bound is weak [toy, `scratchpad/toy_bound.py` run once with `.venv` python, 20 000 synthetic anisotropic unit vectors, d = 384, 50 queries taken from the data, k = 10, `survivors` = fraction of rows with `U_i >= exact 10th best`]:

| Sidecar | mean bound `r_i` | max abs error observed | survivors | 
|---|---|---|---|
| 1 bit/dim (sign, optimal scale) | 0.71 | 0.61 | 100 % |
| 2 bit/dim (uniform, my naive quantizer) | 0.95 | 0.57 | 100 % |
| 4 bit/dim (uniform per row) | 0.20 | 0.07 | 22 % |
| PCA prefix 96 of 384 dims + tail norm | tail 0.60 | | 68 % |
| PCA prefix 192 of 384 dims + tail norm | tail 0.43 | | 10 % |

No bound violation occurred (the bound is valid by construction). **These are not results about real sentence embeddings** (synthetic spectrum; queries are data points so the 10th best score is high; the 2-bit quantizer is crude). They show the shape: the worst-case bound is on the order of the quantization residual norm, which is only small when the sidecar keeps most of the information; at 1 bit per dimension (the size that fits next to a 300 GB int8 store: 37.5 GB for 1B rows at 384 dims, 4.8 GB for 100M) the deterministic bound removes nothing. For the 100M x 384 case (38 GB int8) a 4-bit sidecar is 19 GB, which does fit in RAM next to it on a 64 GB machine, and the toy says ~5x fewer survivors than rows; for 1B it does not fit. Also: **for an int8 store a sidecar of the same bytes (the "stage-1 integer scan") saves compute but not I/O** (the survey's observation); the I/O saving needs a sidecar smaller than the store.

Probabilistic alternatives (RaBitQ, 1 bit/dim with a random rotation, error bound holding with high probability, arXiv 2405.12497) give tight bounds at 1 bit but are **not worst-case**; using them would make the mode approximate under fse's rules (never fail silently, bit-identical contract). That is proposal E, and it needs the maintainer's decision: "exact" and "fast on a 300 GB store" cannot both hold with a RAM sidecar below ~4 bit per dimension on this evidence.

fse files for D/E: new derived tensors per shard (names versioned, e.g. a hypothetical `sketch` with `fse.sketch=...@1`; ARCHITECTURE.md forbids reusing persistence names and `_layout.py` demands exactly the known tensors, so a new tensor means a new store/shard format revision), written in `_store/_shard.py:finish` next to `inv_norms`/`scales`; a kernel for the sketch score in `_native_kernel_search.h` and `_native_search.pxi`; the two-stage driver in `_search.py`; conformance tests in `tests/test_conformance*.py` (bit-exactness of the final scores plus a randomized test that no true top-k row is pruned). Effort L (tens of hours incl. the numerical argument and tests).

### 5.5 Exact pruning by clustering (F) [derived; doubtful]

Milvus's clustering compaction and DiskANN's partitioning both rely on rows being grouped. Given `row_ids` (reserved for 2.1) a compaction could reorder rows into k-means clusters and store per block a unit centroid `c_B` and angular radius `theta_B` (RAM: ~1 vector per 64 K rows). For unit vectors the spherical triangle inequality gives `cos(q, x) <= cos(max(0, angle(q, c_B) - theta_B))`, so a block whose bound is below the floor is skipped **unread**. Exact, tiny RAM, no rescoring I/O. But high-dimensional embeddings have large cluster angles; the VA-file paper's conclusion above says exactly this for tree and cluster indexes. Cheap experiment before any build: on a sample of a real store, k-means with ~1000 centroids, compute `theta_B`, and measure the fraction of blocks with bound >= the true 10th best for real queries (offline numpy, S effort). If it is below ~50 % skippable, drop the idea.

### 5.6 Write path (G) [verified facts, derived advice]

fse's ingest: 3-thread pipeline (hash, write, publish), `pwrite`, `F_FULLFSYNC` on macOS, per-shard exclusive rename. Candidates from the sources:
1. **Direct/uncached shard writes.** Milvus's `direct` mode (`O_DIRECT` on Linux, `F_NOCACHE` on macOS; 4 KiB-aligned buffers; final block zero-padded, then `ftruncate`) avoids page-cache growth and dirty-page throttling when the data written is 100+ GB. For fse the shard's final `fsync` is already required, so the `O_DIRECT` variant would still call it (Milvus skips it; do not copy that). Python needs aligned buffers (anonymous `mmap` is page-aligned) and block-multiple lengths; the existing `shrink()` after the last write already truncates. Files: `_container/_npy_inplace.py` (`write_at`, `shrink`), `_store/_shard.py`. Effort M. Effect [unverified]: keeps the cache free for search on the same machine during ingest. fse's architecture note says writing through a mapping cost half the throughput; `pwrite` plus buffered is the current baseline, so any direct mode must be benchmarked against it (`benchmarks/bench_store.py`).
2. **Incremental writeback** (RocksDB `bytes_per_sync`): ask the kernel to start writing back every N MiB so the final sync of a 256 MiB shard is short and does not stall the publish thread. On Linux `sync_file_range(SYNC_FILE_RANGE_WRITE)`; Python has no wrapper (ctypes). The existing design already syncs on a separate publish thread, so the gain is small; only worth it if profiles show the publish thread waiting on the sync.
3. **`fdatasync` instead of `fsync` on Linux** for the vector file (Milvus uses `fdatasync` on non-Apple, `FileWriter.cpp:215-220`): size changes from `shrink` are metadata `fdatasync` must flush anyway [memory of the man page], so the saving is only the mtime/ctime journal commit; negligible against 256 MiB.
4. **Write rate limiter**: a token bucket (Milvus default 256 MB/s average, 512 MB/s burst) is useful only if ingest and search share a device and search tail latency matters. Effort S.
5. **Shard size**: Milvus ~123 MiB to 1 GiB per sealed segment and 16 MiB flush buffers; fse 256 MiB default is within range. For 300 GB that is ~1200 shards, each an mmap and an fd; `VectorStore.open` maps all of them. If fd/mmap counts matter, a compaction that merges tiny shards (Milvus mix compaction) is the tool; for fse it must create a new store or a new generation of shards because shards are immutable and named by first row; not designed yet.
6. **Checksums**: Milvus binlogs carry none that I found, DiskANN neither; fse's xxh3 per tensor is stronger. Keep.
7. **WAL / group commit**: irrelevant without single-row appends.

### 5.7 Things not to copy

- libaio/io_uring machinery for a sequential scan (DiskANN needs it for random 4 KiB reads; for a scan, large reads plus read-ahead hints reach the same bandwidth with far less code). io_uring with registered buffers and `IORING_OP_READ_FIXED` could still be the ceiling, but needs a native module and platform code (Linux only).
- Heuristic `refine_ratio`/`k_factor` as a default of an "exact" mode.
- Per-query full passes (knowhere FLAT), per-chunk independent top-k without a shared floor (Milvus `SearchOnSealed`).
- Skipping `fdatasync` for `O_DIRECT` writes (valid only for re-creatable caches).
- Milvus's own tiered cache and eviction watermarks inside a library.
