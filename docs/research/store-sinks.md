# Research: sharded .npy store, atomic publish, durable-watermark sink, exact top-k (PR 6)

Status legend: [V] verified in a primary source fetched in this session; [U] unverified or inferred.

## 1. Writing .npy through open_memmap / raw mmap from several threads

Facts
- Header: .npy v1.0 header is padded with spaces and ends in "\n" so magic+length+header is a multiple of 64 bytes (ARRAY_ALIGN = 64); v1.0 header max 65535 bytes, v2.0 up to 4 GiB. [V] https://numpy.org/doc/stable/reference/generated/numpy.lib.format.html and https://github.com/numpy/numpy/blob/main/numpy/lib/_format_impl.py (comment: alignment "supports memory mapping ... where mmap() offset must be page-aligned"). The header is fixed at creation, so shape (row count) must be final when the file is created. Data offset is 64-aligned, not page-aligned; np.memmap handles this by mapping from the page below and offsetting.
- open_memmap(mode="w+") writes the header and creates the file at full size; extending a memmap's file gives unspecified content, zero-filled only on POSIX filesystems. [V] https://numpy.org/doc/stable/reference/generated/numpy.lib.format.open_memmap.html, numpy/_core/memmap.py docstring (https://github.com/numpy/numpy/blob/main/numpy/_core/memmap.py)
- MAP_SHARED writes reach the file without msync; msync only controls timing. Access beyond the end of the file gives SIGBUS. [V] https://man7.org/linux/man-pages/man2/mmap.2.html
- ENOSPC on a sparse mapped file surfaces as SIGBUS at page-fault time (a store has no error return); ftruncate only extends, it allocates nothing; even fallocate is no guarantee on COW/compressed/thin-provisioned filesystems. [V as mailing-list evidence, not a spec] search results incl. https://lists.linux.it/pipermail/ltp/2026-September/051548.html and the glibc thread https://sourceware.org/legacy-ml/libc-alpha/2015-05/msg00627.html
- posix_fallocate: after success, writes to the range "are guaranteed not to fail because of lack of disk space"; glibc emulation (when the filesystem lacks fallocate) is slow and not MT-safe ("concurrent writes ... could be overwritten with null bytes"); musl may return EOPNOTSUPP. [V] https://man7.org/linux/man-pages/man3/posix_fallocate.3.html
- Durability: fsync does not persist the directory entry of a new file; fsync the directory too. [V] https://man7.org/linux/man-pages/man2/fsync.2.html. On macOS fsync does not force the drive cache; F_FULLFSYNC does (SQLite: PRAGMA fullfsync, "not recommended" because it slows all I/O). [V] https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html, https://www.sqlite.org/atomiccommit.html
- Windows: FlushViewOfFile starts writeback of dirty pages but does not flush metadata nor wait for the hardware cache; call FlushFileBuffers afterwards. A mapping larger than the file extends the file at CreateFileMapping; mapping objects have fixed size; a zero-length file cannot be mapped (ERROR_FILE_INVALID). [V] https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-flushviewoffile, https://learn.microsoft.com/en-us/windows/win32/memory/creating-a-file-mapping-object
- LMDB (python docs): with writemap=True a filesystem failure such as out of space "will crash the Python process"; on filesystems without sparse files (e.g. macOS) the full map size may be preallocated. [V] https://lmdb.readthedocs.io/en/release/
- safetensors (writer of a mmap-friendly format) writes into a fresh file with an 8-byte length + JSON header; it does not append or grow in place. [V] https://github.com/huggingface/safetensors (README)
- Zarr v3 core spec says nothing about atomicity or concurrent writes. [V as absence] https://zarr-specs.readthedocs.io/en/latest/v3/core/index.html

Recommendation
1. Shards are fixed-size and immutable once published: create `shard-NNNNN.npy.tmp` (or a `.tmp` name in the same directory), write the final header with the final shape (use np.lib.format.open_memmap(mode="w+") or write header yourself and keep the offset), then preallocate real blocks: `os.posix_fallocate` where available (Linux), catch EINVAL/EOPNOTSUPP/AttributeError and fall back to writing zeros with pwrite in chunks (this converts ENOSPC into a Python OSError before any thread touches the map; on macOS/Windows there is no posix_fallocate, so the zero-fill fallback is the portable path, and it also avoids sparse-file surprises). Do not rely on ftruncate alone.
2. Threads write disjoint row ranges directly into the mapping; no locks are needed for disjoint, non-overlapping slices (adjacent rows sharing a page is fine for MAP_SHARED on one process). Never shrink or truncate a file while mapped (SIGBUS on POSIX, error on Windows). Keep the mapping object alive until all workers are done.
3. Make the shard "done" in this order: all workers joined, `mmap.flush()` (msync), fsync the file (macOS: fcntl F_FULLFSYNC, Windows: FlushViewOfFile then FlushFileBuffers), close the map, rename `.tmp` to the final name, fsync the directory. Zero page-fault cost can be hidden by writing rows in order so the OS does sequential writeback.
4. Document that a full disk after fallocate/zero-fill cannot SIGBUS on ext4/xfs/APFS but can on COW/thin filesystems [U for APFS/btrfs/zfs specifics]; do not install a SIGBUS handler, rely on pre-fill.
5. Header: use np.lib.format helpers (never hand-write dicts); data offset is a multiple of 64 so float32/float16/int8 rows are aligned for SIMD loads at row starts only if the row byte size is also a multiple of the alignment you need. Consider padding the row stride is NOT possible in plain .npy (shape must be exact), so do not promise aligned rows.

## 2. Atomic publish of shards and manifest; two appenders

Facts
- rename(2) atomically replaces newpath; renameat2 RENAME_NOREPLACE errors with EEXIST if it exists (filesystem support required). [V] https://man7.org/linux/man-pages/man2/rename.2.html. NFS retransmission can make a successful rename report failure (same page, BUGS). [V]
- SQLite: syncs the journal and also opens and fsyncs the directory containing it so a file "will appear in the directory following a power failure"; it also states that fsync/flush often does not work as advertised. It does not claim rename is atomic. [V] https://www.sqlite.org/atomiccommit.html
- Lance: commit needs only rename-if-not-exists or put-if-not-exists; "exactly one writer succeeds when multiple writers attempt to create the same manifest file"; manifests are immutable `{version}.manifest` files (V2 naming sorts newest first); conflicting transactions are classified rebasable / retryable / incompatible, and an Append conflicts with Overwrite, Restore. [V] https://lance.org/format/table/transaction/
- Delta Lake: log entries `N.json` with contiguous versions; "Writers MUST never overwrite an existing log entry", use atomic filesystem primitives; transaction identifiers (appId, version) are committed atomically with data so a streaming writer is idempotent on retry. [V] https://github.com/delta-io/delta/blob/master/PROTOCOL.md (sections "Creation of New Log Entries" and "Transaction Identifiers")
- Iceberg: every change creates a new metadata file committed by an atomic swap (optimistic, linear history); the local-filesystem rename scheme is deprecated and "unsafe in object stores and local file systems". [V] https://iceberg.apache.org/spec/ (Table Metadata, "File System Tables")
- Confluent S3 sink: file name `<topic>+<partition>+<startOffset>.<fmt>`, deterministic rolling by flush.size gives exactly-once because a retry rewrites the same object name with the same records; a task that fails before upload leaves nothing visible. [V] https://docs.confluent.io/kafka-connectors/s3-sink/current/overview.html
- LMDB: single writer enforced by a lock; sync flags trade durability for speed (metasync=False can undo the last committed transaction). [V] https://lmdb.readthedocs.io/en/release/

Recommendation
- Shard file names are deterministic from content position: `shard-<first_row, zero padded 12-20 digits>.npy` (Confluent pattern). A retry after a crash then recreates the same name with the same rows; publish with `os.link(tmp, final)` (fails with FileExistsError, never overwrites; Delta/Lance "no overwrite" rule) then unlink tmp, with `os.rename` fallback plus an exists-check where hard links are unsupported (FAT, some network mounts) [U which filesystems].
- Manifest: immutable versioned files `manifest-<version 20 digits>.json` (+ optionally a convenience `manifest.json` copy that is replaced via tmp + rename + dir fsync); the latest = highest version. Commit = create version N+1 with link/O_EXCL semantic, so exactly one of two concurrent appenders wins (Lance/Delta pattern); the loser re-reads, sees the new rows, and either re-bases its shards (append never conflicts with append, renumber starting row) or raises a clear error. This is optimistic and needs no lock file; a lock file (fcntl/msvcrt) is a simpler alternative that cannot protect against NFS and stale locks, so prefer the optimistic scheme and say single-process-per-store is the documented default.
- Manifest content: format version, dtype, dim, per-shard {file, first_row, rows, byte size, optional checksum}, total rows, scale file per int8 shard, inverse-norm file, a `committed_rows` value, plus the producer id and "stream position" (see 3) à la Delta transaction identifiers. Readers ignore any shard not listed (orphan tmp or unlisted files are garbage-collected by an explicit call, never silently).
- fsync order: shard data -> dir fsync -> manifest tmp data -> link/rename -> dir fsync. Only after the last step is a row "durable".

## 3. Offset-commit semantics for endless streams

Facts
- KafkaConsumer: manual commit gives at-least-once; "the committed offset should always be the offset of the next message that your application will read" (last processed + 1); committing ahead of processing loses records; storing offsets in the same system as results plus `seek` on restart gives exactly-once. [V] https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html
- Kafka Connect SinkTask: `flush(currentOffsets)` is called before offset commit; `preCommit(currentOffsets)` by default calls flush and returns the map of offsets that are safe to commit; tasks that buffer must return only offsets of records actually written downstream; empty map means "do not commit". [V] https://kafka.apache.org/40/javadoc/org/apache/kafka/connect/sink/SinkTask.html
- Confluent S3 sink: the committed offset advances only when a file is uploaded; a crash after upload but before offset commit re-uploads the same object name (idempotent duplicate). [V] https://docs.confluent.io/kafka-connectors/s3-sink/current/overview.html
- Flink: exactly-once to an external system requires the sink to take part in checkpointing; TwoPhaseCommitSinkFunction: preCommit "must make all of the necessary steps to prepare the transaction", commit on an already pre-committed transaction "will always succeed", `recoverAndCommit` "must ensure that this call will eventually succeed". [V] https://nightlies.apache.org/flink/flink-docs-stable/docs/connectors/datastream/guarantees/, https://github.com/apache/flink (flink-streaming-java TwoPhaseCommitSinkFunction.java)
- Delta streaming sink: records the batch id atomically with the data so replays are skipped. [V] Delta PROTOCOL.md, Transaction Identifiers.

Recommendation (what the library exposes)
- Contract: at-least-once by default, exactly-once achievable by the caller because shard names and row ranges are deterministic and the manifest stores a `committed_rows` count.
- Sink API: `sink.durable_rows -> int` (number of leading rows, in input order, that are published and fsynced; monotonic), `sink.flush() -> int` (publishes the partial shard and returns durable_rows; a short final shard is allowed because shards are immutable and appends add shards), and an optional callback `on_durable(rows: int)` invoked from the writer after the manifest commit, never from a worker thread mid-write (document the thread). The caller keeps its own mapping row index -> (topic, partition, offset); to commit, take offsets of rows [0, durable_rows) and commit last+1 per partition (Kafka rule). Because rows are strictly ordered, a single integer is a sufficient watermark; do not expose per-shard state.
- Keep durable_rows <= rows whose manifest commit finished; rows written into an unpublished shard are not durable even if encoded. Report the watermark in the manifest so a restart can resume: `resume_from = manifest.rows`, the user seeks the consumer to the offset that maps to that row (Kafka "store offsets with results" pattern), which yields exactly-once even if the Kafka commit lagged.
- Backpressure/latency: provide `flush_every_rows` / `flush_every_seconds` so low-traffic streams still advance the watermark; document the tradeoff (more small shards).
- Avoid a two-phase protocol: the single atomic manifest commit is the commit point (Lance/Delta style); an aborted shard is a tmp file that is deleted on next open.

## 4. Exact top-k over float16/int8 on CPU

Facts
- FAISS knn: `distance_compute_blas_threshold = 128000` (nx*d), `query_bs = 4096`, `database_bs = 1024`; below the threshold a sequential path with per-query heaps, otherwise sgemm into a bs_x*bs_y block followed by a result handler (heap) per block. [V] https://github.com/facebookresearch/faiss/blob/main/faiss/utils/distances.cpp and distances.h (I read the source; the block-then-heap structure is visible in exhaustive_inner_product_blas)
- FAISS IndexFlat has a float16 *query* entry (`search_ex` -> knn_inner_product_fp16) with float32 database; fp16 database storage is IndexScalarQuantizer QT_fp16; QT_8bit is a per-dimension trained quantizer, exhaustive "all the indexed vectors are decoded sequentially and compared"; the SQ index uses a per-vector distance computer with OpenMP over queries. [V] https://github.com/facebookresearch/faiss/blob/main/faiss/IndexFlat.cpp, IndexScalarQuantizer.cpp, https://github.com/facebookresearch/faiss/wiki/Faiss-indexes. For cosine, FAISS expects normalized vectors. [V wiki]
- SimSIMD: f16 and bf16 widened to float32 for accumulation (float16 accumulation "loses precision"), i8 accumulated in int32, dot of i8 can reach ±10 million; provides packed many-to-many kernels with precomputed norms; no top-k. [V] https://github.com/ashvardanian/SimSIMD
- USearch: `exact=True` brute-force search; i8 quantization "only valid for cosine-like metrics"; memory-mapped `view`. [V] https://github.com/unum-cloud/usearch. Its claim "up to 20x faster than IndexFlatL2" is a vendor Colab number [unverified independently].

Recommendation
- Blockwise: loop over database blocks (e.g. 4k to 16k rows, sized so the converted float32 block fits L2/L3, FAISS uses 1024 database x 4096 query), convert the block to float32 (float16 -> float32 per block; int8 -> float32 then multiply by row scale), GEMM with the query batch via numpy/BLAS (accumulate float32), then merge. For a block of scores S (q x b): `np.argpartition(-S, k-1, axis=1)[:, :k]` (O(b)), take those k candidates, concatenate with the running (q x k) buffers, and reduce again with argpartition + a final sort of k. This costs O(b + k) per query per block, which beats a heap for k << b. For single-query workloads a native kernel with a bounded heap (FAISS style) avoids the q x b score matrix.
- int8: store codes + one float32 scale per row; score = scale_row * (q . codes) done in float32 after converting codes (exact for |q.code| well inside float32's 2^24 integers for typical dims; i32 accumulation like SimSIMD needs integer queries, which would quantize the query too, so keep queries float32 and codes widened unless a native int kernel is written) [U for the 2^24 bound claim on real data; derived from dim*127*|q|].
- Cosine: store `inv_norm = 1/||x||` (float32, computed from the original float32 vector before quantization, or from the decoded vector if the score must equal the decoded cosine; choose one and document) in a separate .npy; score = (q . x) * inv_norm_row * inv_norm_q, or scale the query norm out since it does not change the ranking. Ranking by dot with row inv_norm folded in needs a multiply per row, cheap next to the GEMM.
- Ties: break by lower row index for determinism (argpartition does not guarantee it; make the merge stable).
- Parallelism: split the database blocks across threads (BLAS releases the GIL), each with its own running top-k, then merge the per-thread results; never use a shared heap.

## 5. Existing "streaming embeddings into sharded npy + manifest" projects

Facts
- clip-retrieval writer: `img_emb/img_emb_<n>.npy`, `text_emb/text_emb_<n>.npy`, `metadata/metadata_<n>.parquet`, batch number zero-padded; written via a buffered `np.save` into BytesIO then `fs.open(..., "wb")` (no tmp+rename); stats are written to a `stats` folder; the number of rows per shard is `write_batch_size` (default 10**6). [V] https://github.com/rom1504/clip-retrieval/blob/main/clip_retrieval/clip_inference/writer.py and README
- embedding-reader: reads folders of .npy (and parquet, or parquet_npy where npy and parquet pair by order, not by name); lists all files and reads metadata at init (count, dimension, byte_per_item); author advises equal file sizes and pieces of ~50MB; ~1 GB/s from NVMe. [V] https://github.com/rom1504/embedding-reader
- autofaiss: reads a directory of .npy in lexicographical order; only IVF indexes can be memory-mapped by FAISS (`IO_FLAG_MMAP`). [V] https://github.com/criteo/autofaiss
- img2dataset: shards named with zero padding (00000.tar), per-shard stats and a parquet status file, resume via `incremental_mode` "incremental/overwrite/extend" with the same shard size and inputs (no explicit done marker documented). [V] https://github.com/rom1504/img2dataset
- sentence-transformers: encode returns an in-memory array; I could not confirm any disk streaming/sharded output in its docs (page truncated). [U] https://sbert.net/docs/package_reference/sentence_transformer/SentenceTransformer.html

Lessons / recommendation
- Pairing by sort order alone (clip-retrieval, embedding-reader) is fragile: a missing or extra file silently misaligns embeddings and metadata. Put explicit `first_row`/`rows` in the manifest and validate contiguity on open.
- No project uses tmp + rename or a manifest of record; a crash leaves a truncated final-named .npy that readers only discover by failing. Our tmp/link + manifest design is stricter and should be called out as such.
- Zero-padded, lexicographically sortable names and equal shard sizes (except the last) are the common convention and what downstream readers (autofaiss, embedding-reader) assume; keep both, and keep standard `.npy` so those tools can read the folder directly. FAISS cannot mmap a flat float32 .npy as an index: it needs the matrix passed via `faiss.IndexFlat.add` (copy) or `np.load(mmap_mode="r")` fed in chunks [U, not tested here].
