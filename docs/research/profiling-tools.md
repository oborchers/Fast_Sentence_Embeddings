Date 2026-10-28. "UNVERIFIED" = not confirmed by a primary source I could read. "LOCAL" = observed on this Mac.

- Only Command Line Tools are active: `xctrace` exists as /usr/bin/xctrace but errors "requires Xcode" (LOCAL). No Xcode.app found in /Applications.

## Q1. CPU on macOS without root
- py-spy: README says "OSX always requires running as root" (Linux depends on how launched); SIP blocks even root for binaries in /usr/bin. https://github.com/benfred/py-spy (README). The "launch the process yourself to avoid root" sentence is Linux-scoped; I found no source that it helps on macOS (UNVERIFIED, README implies no). Reason is task_for_pid: Apple/DTS says the caller must be root (or have the debugger entitlement) and the target needs com.apple.security.get-task-allow (search summary of https://developer.apple.com/forums/thread/701647, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.debugger; the Apple page body itself did not load, so the exact wording is UNVERIFIED).
- py-spy `--native` is NOT supported on macOS: README table marks it only for Linux x86-64/aarch64/ARM and Windows x86-64. https://github.com/benfred/py-spy. So py-spy on a Mac = Python frames only, and needs sudo.
- samply: `samply record ./cmd args` launches the child itself, loads the result in Firefox Profiler with a local server. Attaching to running processes needs one-time `samply setup` (self-signs samply). System binaries cannot be profiled because they block DYLD_INSERT_LIBRARIES; unsigned or locally signed binaries (cargo install, Homebrew) work. https://github.com/mstange/samply (README). README does not mention sudo/SIP/entitlements for the launch case; it is the sudo-free route in practice (mechanism is my inference, UNVERIFIED). Shows native C/Cython frames per thread with symbols; Python frames only via CPython perf trampoline, and on macOS that needs Python 3.15+; "samply can't profile signed Python executables" https://docs.python.org/3/howto/perf_profiling.html. Our uv Python is ad-hoc linker-signed (LOCAL); whether samply accepts it: UNVERIFIED, test it. Below 3.15 on macOS samply shows interpreter C frames (_PyEval_EvalFrameDefault) not Python function names (inference).
- Instruments / `xcrun xctrace record --template 'Time Profiler' --launch -- <cmd>`: syntax confirmed by third-party guides (not Apple docs) plus `--attach`, export via `xctrace export --xpath` (search results, e.g. https://tessl.io/registry/skills/github/steipete/agent-scripts/instruments-profiling). Needs full Xcode (LOCAL: not available here). Sudo-free for launch: UNVERIFIED. Python frames: none, only C frames (UNVERIFIED, inference). Output .trace opens in Instruments GUI, not flamegraph/speedscope without conversion.
- Austin (austin-dist, MOJO output, convertible to FlameGraph/speedscope via austin-python): docs say SIP blocks interpreters under /bin, use venv or non-system Python, sudo still required on macOS; Linux can use cap_sys_ptrace. https://pypi.org/project/austin-tui/1.1.1, https://github.com/P403n1x87/austin. Native frames: README lists "native frame stacks" as a feature; platform scope (austinp is Linux-only) UNVERIFIED.
- Scalene: "works on macOS, Linux, Windows"; separates Python vs native time, "stitched Python + native (C/C++) stacks at every CPU and allocation sample"; supports Python threads and free-threaded 3.13t/3.14t; outputs text/JSON/HTML. https://github.com/plasma-umass/scalene. Whether it needs sudo on macOS: not stated (UNVERIFIED). It is line-level, not per-thread flame graph; sampling relies on signals and is main-thread-centric (UNVERIFIED), so poor fit for GIL-free worker threads.
- NEW: CPython 3.15 ships `python -m profiling.sampling run [--native] [-a/--all-threads] [--flamegraph|--gecko|pstats] script.py`. On macOS it uses task_for_pid and needs one of: root, profiler binary with com.apple.security.cs.debugger entitlement, or SIP off. `--native` marks `<native>` frames (only the call into C, not the C stack inside); `-a` samples all threads; `--mode=gil` available. https://docs.python.org/3.15/library/profiling.sampling.html. Only 3.15, so not a baseline for 3.11 to 3.14.
- Recommendation Q1: on Mac use samply (launch mode) for native frames per thread; accept that Python frames appear only on 3.15. Use py-spy with sudo only when Python-level frames are needed. Skip Austin/Scalene/xctrace.

## Q2. CPU on Linux
- py-spy `--native` works on Linux x86-64/aarch64; `--subprocesses`, `--format speedscope|raw|flamegraph`; launching `py-spy record -- python script.py` avoids root on Linux; in Docker needs SYS_PTRACE (process_vm_readv restricted). https://github.com/benfred/py-spy. No `--threads` claim verified here beyond README; per-thread via `--threads` flag exists in py-spy CLI (UNVERIFIED in this session).
- perf + trampoline: Python 3.12+ `-X perf` / PYTHONPERFSUPPORT=1 / sys.activate_stack_trampoline("perf"); `perf record -F 9999 -g -o perf.data python -X perf script.py`. Needs frame pointers (check `python -m sysconfig | grep no-omit-frame-pointer`); `-X perf_jit` works without them but needs perf > v6.8 plus `perf inject --jit`. Native C frames of the extension need frame pointers or dwarf unwinding in the extension (build flag -fno-omit-frame-pointer; inference). https://docs.python.org/3/howto/perf_profiling.html
- samply on Linux: works with perf_event_paranoid <= 1: `echo '1' | sudo tee /proc/sys/kernel/perf_event_paranoid`. https://github.com/mstange/samply. Python frames via same trampoline.
- GitHub-hosted runners: perf reported failing regardless of settings; unconfirmed fix. https://github.com/actions/runner-images/issues/4974 (search snippet; page not read) . Docs do not mention perf. Containers (RunPod): not researched, UNVERIFIED; expect perf needing --cap-add=SYS_ADMIN/PERFMON or sysctl on host; py-spy needs SYS_PTRACE.
- Recommendation Q2: py-spy record --native --threads as the portable default (ptrace, no perf needed when launching the child, only SYS_PTRACE in containers). Use perf + `-X perf` on boxes where it works, for hardware-level detail.

## Q3. Memory
- memray: Linux and macOS (macOS 11+ on Apple Silicon), Python 3.9 to 3.15, CPython only; wheels on PyPI for Linux and both macOS arches; Linux tested on x86-64/aarch64. https://bloomberg.github.io/memray/supported_environments.html. Latest 1.20.0, Apache-2.0 (PyPI JSON; wheel tag list not read). Free-threaded support: UNVERIFIED.
- No root needed (it injects via its own hooks, not ptrace; inference, UNVERIFIED but nothing in docs asks for root).
- Tracks Python code, native extension modules, interpreter; Python threads and native threads. https://bloomberg.github.io/memray/overview.html
- `--native` adds native stacks (moderate overhead; reports with native frames must be generated on the same machine). `--follow-fork` writes one file per child, incompatible with `--live`. `--aggregate` smaller files, no stats reporter, unusable if killed. `--live`/`--live-remote` TUI. https://bloomberg.github.io/memray/run.html
- Hooked allocators (source): malloc, calloc, realloc, free, valloc, posix_memalign, aligned_alloc, mmap, munmap; mmap64/memalign/pvalloc only on Linux/glibc. mremap not seen in the part read. https://raw.githubusercontent.com/bloomberg/memray/main/src/memray/_memray/hooks.cpp . So malloc from Cython is seen; mmap calls are seen as allocations of the mapped size, but file-backed pages are not RSS-accurate: docs say a profiler cannot see when the OS makes pages resident ("resident memory will only increase once you actually write to that memory"), https://bloomberg.github.io/memray/memory.html. Whether memray flags file-backed vs anonymous mmap: UNVERIFIED. Memray records RSS snapshots over time (changelog mentions VmRSS snapshots; https://bloomberg.github.io/memray/changelog.html, snippet only).
- Flame graphs: `memray flamegraph` (peak), `--temporal` (time slider, usage chart), `--leaks`, `--split-threads` per-thread filter. https://bloomberg.github.io/memray/flamegraph.html
- tracemalloc: only traces Python-allocator/PyMem domains and numpy's tracked allocations; plain C malloc from a Cython module is not seen (my knowledge, not verified this session; UNVERIFIED).
- Scalene memory: own allocator interposition, splits Python vs native, leak detector experimental. https://github.com/plasma-umass/scalene
- Peak RSS: `resource.getrusage(RUSAGE_CHILDREN).ru_maxrss` counts only terminated and waited-for children (https://docs.python.org/3/library/resource.html) and is in bytes on macOS but kilobytes on Linux (https://www.python.org/pipermail/python-bugs-list/2017-May/336429.html). It returns the max over children, not a sum (UNVERIFIED here). `/usr/bin/time -l` (macOS, bytes) and `-v` (GNU, KB) wrap the same counter (UNVERIFIED). For RSS over time, poll psutil `Process.memory_info().rss` plus children every 50 to 100 ms in a sidecar (psutil not verified this session); for mmap-heavy code also record USS/PSS where available.
- Recommendation Q3: memray with `--native` for allocation flame graphs; a small harness script for RSS over time + final ru_maxrss (normalize units).

## Q4. Recommendation
- Dev group (pip wheels): `py-spy` (MIT, pure wheels incl. macosx arm64 and manylinux x86_64/aarch64 in older releases; 0.4.2 file list not confirmed) and `memray` (Apache-2.0). Both compatible with an MIT project. psutil as third (optional).
- System tool: `samply` via `cargo install samply` or Homebrew (license not checked, UNVERIFIED; Apache/MIT upstream per repo is likely). Not a PyPI package.
- Commands (verify flags with --help before documenting):
  - CPU flame graph, Linux: `py-spy record --native --threads -f speedscope -o prof.json -- python benchmarks/x.py`
  - CPU Mac, native per thread: `samply record -- python benchmarks/x.py` (Firefox Profiler; try on uv Python first; add `-X perf` on 3.15 only)
  - CPU Mac, Python frames only: `sudo py-spy record -o prof.svg -- python benchmarks/x.py`
  - Memory: `memray run --native -o m.bin benchmarks/x.py && memray flamegraph --temporal m.bin`
  - Peak RSS over time: harness spawning the benchmark and sampling psutil RSS of the process tree, plus ru_maxrss at the end.

## Q5. Sudo-free py-spy on macOS and sudoers risk
- Mechanism: target needs com.apple.security.get-task-allow and the caller either root or the debugger entitlement (Apple forum/DTS summary above). Community report: ad-hoc re-signing the interpreter with a plist setting get-task-allow=true via `codesign -f -s - --entitlements ent.plist <python>` made debugging work; removing the signature also worked for Austin; arm64 binaries must carry at least an ad-hoc signature. https://discuss.python.org/t/permission-issues-with-observability-tools-and-the-official-macos-installer/19736 (that thread was about Austin and the hardened runtime, not py-spy; py-spy with this trick is UNVERIFIED, and whether root is still required is UNVERIFIED).
- Implications: any local process of the same user could then read the memory of that Python, so do it only on a dedicated profiling interpreter copy, never on the shared uv Python; signature changes break on uv reinstall.
- NOPASSWD for a binary in a user-writable venv: sudoers docs warn that if the user can write the command (or its directory) it can be replaced after the check, so the rule grants root to anything the user can write; also wildcards match whitespace and "ALL can be dangerous". https://www.sudo.ws/docs/man/sudoers.man/ (page read only up to char 100000, so the explicit "must not be writable" rule is my inference).
- Recommendation: do not add a sudoers rule. On Mac use samply (launch mode) and accept a sudo prompt for rare py-spy runs; use CI/Linux for py-spy --native.
