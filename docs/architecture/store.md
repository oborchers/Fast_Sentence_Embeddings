## sentence_vectors 1

Historical M1 timing observations in this document are withdrawn and must not support speed claims. Numerical contracts and implementation descriptions remain valid. Current evidence is in the [comparison guide](../fse-comparison.md).


Binding for every 2.0 module (formerly under "2.0 design").

A store of sentence vectors (`fse._store`), a directory written by `fse.ShardSink` and read by `fse.VectorStore`.

- **`store.json`**, written once when the store is created and never changed: strict JSON, exactly `{"store": "fse_shards", "store_version": 1, "metadata": {...}}` with `fse.kind=sentence_vectors`, `fse.format_version=1`, `fse.transform_version=2`, `fse.encoder` (the fingerprint of the encoder of every row), `fse.dtype` (float32, float16 or int8; one per store) and `fse.output_dim`. It is created in a temporary directory beside the store, synced, and renamed into place without replacing anything, then the parent directory is synced; a store another writer created first is kept and checked. Another store or version raises `UnsupportedArtifactError`.
- **Shards**, each an NpyContainer 1 artifact `shard-<first row>` (the row as at least 16 decimal digits): `vectors` (rows of the dtype), `inv_norms` (F32, from the stored values, see [Numerical contract (`transform_version` 2)](numerical-contract.md#numerical-contract-transform_version-2)) and for int8 `scales` (F32); `doc_ids` is the optional int64 column of [sentence_vectors 2](document-ids.md). Their metadata repeat those of `store.json` and add `fse.created_by`, `fse.quantization=quantize_rows@1` for float16 and int8, `fse.first_row` and `fse.rows`. The optional shard key `fse.durability=none` records a publication without durability confirmation; any other value raises `UnsupportedArtifactError`. The absence of this key means the normal full-durability protocol. Both forms belong to version 1. Shards are immutable; an append adds shards after the last row, nothing is rewritten.
- **Reading** follows the shards from row 0 by looking up the name of the next one (`shard-<rows so far>`), so a shard published while a reader lists the store is either seen whole or not at all, and the rows always run without a gap; every shard must match `store.json` and hold exactly its tensors (the vectors in the dtype of the store, the inverse norms and scales as F32) and exactly its metadata keys, with the optional `fse.durability` key above; a float16 or int8 shard names `fse.quantization=quantize_rows@1` (another well-formed quantization identifier raises `UnsupportedArtifactError`). `store.json` is read whole (at most 64 KiB) with exactly its keys and the integer version 1. Entries starting with a dot (shards being written, or left by a crash) and other names are ignored; remove leftovers only while no writer runs. `VectorStore.open` maps the shards published at that time (a snapshot; "Refresh" below adds the later ones). On every open it hashes every tensor of each tagged shard, including inverse norms and int8 scales, against the checksums obtained from the same manifest open. The hashes cover the mapped tensors, without reopening the manifest or tensor paths. It also checks their values as `verify` does, in blocks of at most 1 MiB of tensor data. Failed opens release their mappings even when the caller retains the exception and traceback. A successful check never promotes a tagged shard to trusted: every later open checks it again. Untagged shards are mapped without hashing. Opening cost therefore includes reading all tagged tensor bytes. `store.opened` records their byte count and verification time.
- **Gaps.** Every reader and sink opening lists canonical shard names, including untagged stores. A canonical name is `shard-` followed by the row's decimal digits, padded to at least 16 digits exactly as `shard_name` writes it. A name outside the followed chain below its end is an overlapping orphan and raises `CorruptArtifactError`. A name after the end is a gap unless a re-check finds the next expected shard: a concurrent writer has then extended the chain, and the reader keeps its original snapshot. Corruption errors name the shard, its first row and `fse.repair_store(path)`. Dot entries and noncanonical names remain ignored.
- **Writing.** A sink starts no thread when it is constructed or opened. Its write and hash threads start at the first commit, and its publish thread at the first finished shard. Close a sink that takes rows, preferably through a `with` block: its started threads live until `close()`, with no finalizer. A thread-start failure is a shared writer failure, raised by the triggering call and reported by later sink calls; closing still removes unpublished temporary shards. If a custom signal handler interrupts `Thread.start()` before the new thread identifies itself, the start outcome stays unknown. No work has been handed to it. `close()` can return before its delayed bootstrap, which then ends by itself without taking work or touching the sink, shards or files. The standard SIGINT handler is deferred until the start outcome is known. The default `durability="full"` follows the sync protocol below. The ShardSink writes a shard in `.shard-<first row>.writing-<hex>`: `vectors.npy` gets the header of the full shard (by default the largest multiple of 16,384 rows within 256 MiB of vectors, at most 2**20 rows). The worker of a task writes its rows into a buffer of the task, which the window of the runtime bounds; the commit hands them to three threads of the sink, each behind a bounded queue (at most 16 pieces waiting and 64 MiB of rows waiting and running, except that one larger piece passes alone to an idle thread, so a full queue makes the calling thread wait): `fse-shard-write` writes them into the file at their offset (`pwrite`; a full disk raises an OSError there, which the calling thread raises at its next call of the sink, and the work after it is dropped), `fse-shard-hash` feeds the checksum of the vectors in row order, and `fse-shard-publish` publishes the finished shards (below), so the syncs of one shard do not stop the writing of the next; a task that crosses the end of a shard is split over the shards at its commit. One thread writes on purpose: two or four write threads into the same shard were not faster (`bench_length.py`, sentences, SIF float32 into a store at 10 workers, 1.33 GB in pieces of about 12 MB: median 0.59 s with one, 0.61 to 0.82 with two, 0.58 to 0.78 with four, M1 Pro at a load of 2.6 to 5.5), because each thread then spends about as long in `pwrite` into the fresh pages of the one file as the single one did, and the drive's durable write rate (with `F_FULLFSYNC`, at most 3.4 GB/s measured, so 0.39 s for these rows) bounds such a run anyway; gathering pieces into larger writes gains nothing either. The hash thread is kept on purpose too: `benchmarks/bench_store_fused.py` folds it into the write thread (a benchmark-only `FusedShardSink`: one piece per commit that writes and then hashes, the hand-on of a finished shard after it in the same thread, one queue of 16 pieces and 64 MiB; a conservative approximation of a merged design, since it keeps the `written` counter and `wait_written`). With vectors and manifests bit-equal, 500,000 sentences at 10 workers into shards of the default size, 7 alternating pairs against an A/A control, the median wall time of fused over split was 1.13 for float32 (7 of 7 pairs slower; A/A ratios 0.94 to 1.48) and 1.13 for int8 (7 of 7 slower; A/A 0.93 to 1.15), 1.09 for float16 (mixed pairs, within A/A 0.86 to 1.44), and 1.11 for the 1.33 GB case of `bench_length.py` (3 pairs, A/A 0.92 to 1.17; `Hasher` alone needs 0.56 s for those 1.33 GB, 2.4 GB/s, about as long as the whole write). In shards of 1,024 rows, where the syncs dominate, there was no difference (medians 1.00, 0.97 and 0.97 for float32, float16 and int8, within A/A), and the peak RSS of the process (which includes preparing the corpus, so it does not isolate the buffers of the sink) differed by at most 2 %. That is more than the 2 % the simplification would have to stay under, so the three threads stay (M1 Pro, load average 2.9 to 4.9 at the start and the end of each round, 31.10.2026). When `close` runs in the main thread and SIGINT has Python's default handler (`signal.default_int_handler`), an interrupt (Ctrl+C) meanwhile is only noted: its handler abandons all three threads at once, so each finishes the piece it runs and drops the rest; further interrupts are noted too, and one KeyboardInterrupt is raised after every thread has ended (an event each sets as its last step, since an interrupted `Thread.join` of Python 3.11 and 3.12 can report a running thread as ended) and the temporary directories of the shards not published are removed. A shard whose publication was running is published if all its rows were written (else dropped), so `published_rows` and, under "full", `durable_rows` can still grow until `close` raises, and not after. There is no time bound: a piece that blocks (a write to a drive that hangs) keeps `close` waiting. With another handler, or from another thread, nothing is deferred. The queues hold no counters: the waiting pieces and the one running, under one condition, are their state, so an interrupt of the calling thread at any point leaves a piece queued or not. Writing through a mapping of the file from the workers instead cost about half the throughput (page faults on fresh file pages and a mapping per task: 1.04 against 1.96 million int8 rows per second at 10 workers on an M1 Pro, `bench_store.py`), and needed a zero-filled preallocation so a full disk could not end the process with SIGBUS. A shard whose rows are all committed is finished at once: a shard that ends early is shrunk to the header of its rows at the same data offset, the file is synced, the inverse norms, scales and manifest are written and synced, and the directory is renamed into place without ever replacing one, not even an empty one (`renameat2` with `RENAME_NOREPLACE` on Linux, `renamex_np` with `RENAME_EXCL` on macOS, `MoveFileExW` without replacing and with `MOVEFILE_WRITE_THROUGH` on Windows), then the store directory is synced (Windows has no directory sync, so its rename writes through). Only then `durable_rows` grows. On macOS `fsync` reaches only the drive cache, and `F_FULLFSYNC` does an `fsync` and then asks the drive to flush all its buffered data (fcntl(2)), which costs milliseconds. So a shard makes two: the files, the manifest and the first sync of the temporary directory are plain `fsync`s, the sync of that directory after the manifest is in place is the full one that makes all of them durable before the rename, and the sync of the store after the rename is the second (`write_manifest(..., staged=True)`; before, a shard made six or seven). Elsewhere every sync is the `fsync` it was. `seal` ends the current shard early, so a stream can make its rows durable before a shard is full; `publish` publishes what is finished; `flush` does both and needs every reserved row committed.
- **Publication policy.** `ShardSink(..., durability="none")` writes shards without file or directory syncs. Store creation still uses the full protocol. A failure to confirm its rename can still raise `PublishedNotDurableError` before the sink opens. Each such shard carries `fse.durability=none`. Exclusive publication is unchanged, including write-through renames on Windows. `published_rows` counts the leading rows this run has published under either policy. `durable_rows` counts only confirmed full publications and stays zero under "none". `publish` and `flush` still return `durable_rows`. A full publication whose final store sync fails counts as published, but not durable. Closing reports `dropped_rows = committed - published`, including errors and interrupts. Neither later full syncs nor successful verification promote a tag. Every reader open therefore rehashes all tagged tensors; a none sink opening checks structure and gaps without hashing. A full sink refuses a tagged prefix. To continue that store, explicitly choose "none" or write a new store. The only supported policies are "full" and "none".
- **Errors and concurrency.** The three sink threads share the first recorded failure. Internal handovers do not mark it as reported. The caller receives that original exception once, then a RuntimeError chained to it. A thread still finishes its queued work unless that thread itself fails or is abandoned. This keeps writes alive until shutdown can safely remove unpublished shards. Leaving a ShardSink (`close` or its context) publishes the committed rows and drops the rest, also after an error (maintainer decision). A failed sync of the store after the rename of a shard raises `fse.PublishedNotDurableError`: the shard is published and complete, its rename not confirmed durable. A full-durability sink refuses to append behind any tagged shard, without hashing it: its new rows cannot be promised durable if earlier rows remain unconfirmed. It may append to an untagged store as before. Two writers that append at the same time race for the name of the next shard: exactly one rename succeeds, the other raises a FileExistsError naming the rows it already published, and removes its temporary data. The crash model is the local filesystem: a process that dies leaves the published shards as a valid prefix and its temporary directories, which readers ignore; durability against power loss rests on the syncs above; The power-loss model assumes that each persisted rename is atomic, leaving the old entry or the new entry. Its contract is limited to local APFS, ext4 and XFS configurations that provide this property; network filesystems and other persistence models are not covered. [ALICE, section 2.2](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-pillai.pdf) explains why filesystem persistence properties must be stated. Verification at open detects damage already present then. It does not detect a device write error after opening, including pages later evicted and re-read from disk; `VectorStore.verify()` provides a separate re-check.
- **Search.** `VectorStore.search(queries, k)` runs block by block in worker threads on the stored rows, through the inverse norms, without a normalized float32 copy, for blocks of rows and of queries that hold at most about 4 MiB of scores. `mode="exact"` uses the backend's `cosines` (the contract) and gives the ids and bits of the reference on the cpu backend. `mode="blas"` decodes each block to float32 (at most 16 MiB per task) and multiplies with BLAS: close to the contract, not bit-defined, so ties and nearly equal scores may order differently; it is faster for many queries, since BLAS uses the matrix units of the CPU (Accelerate on Apple silicon) and the contract fixes the order of every sum. For a few queries the kernel is as fast or faster, since every row is read once and need not be decoded. `mode="auto"`, the default, takes the contract for at most 8 queries and BLAS above (equal at 8 to 12 on 859,346 rows), so its bits depend on how many queries are asked at once; reproducible results need `mode="exact"` (maintainer decisions). Each block keeps the candidates of every query at or above its floor, the k-th best score merged so far, by the order of `top_k` (the larger score first, equal scores, -0.0 equal to 0.0, by the smaller row), which is total, so merging the blocks in any order gives the same ids. Every query is checked before any block is searched. `score(weights, bias)` gives the linear score with one or many weight vectors, with the same modes. `verify` hashes every shard and checks its values (finite scales and inverse norms of at least 0, finite float rows, int8 codes within +-127). A store cannot be closed while it is searched. With `max_per_doc=1` the same scan keeps only the best row of each document per block and merges them by document, see [document-ids.md](document-ids.md). **int8 prefilter.** An exact search (`mode="exact"`, or `"auto"` up to 8 queries) of an int8 store may skip rows that a provable bound rules out (`_store/_prefilter.py`; the bound and its proof are in [numerical-contract.md](numerical-contract.md), "int8 prefilter (no new arithmetic)"). The domain is narrow: 1 to 8 queries, `k` up to 100, 256 to 1024 values per row, at least 65,536 rows, no `max_per_doc`, no `rows=` and no `doc_ids=` (a selection gathers its rows first, which the prefilter does not pay for, so such a call takes the search of the previous paragraph, code for code), and a backend whose prefilter variant is enabled (`CpuBackend.prefilter_variant()`: built into the binary, runnable on the CPU and listed in `_PREFILTER_ENABLED`, three separate facts). Enabled is `neon-sdot`, so the path is taken on arm64 CPUs with the dot-product extension, for a store and for a view of several stores and shards; `avx2` and the portable kernel are not enabled (the AVX2 variant waits for DR-288), and the numpy backend never takes it. Phase 1 runs `backend.int8_pass` over the blocks of the store on the search threads. The main thread merges the k largest estimates of every query into a running threshold, which a later block reads when it starts; an older threshold is lower, which costs time but never a row. Phase 2 hands the survivors of every query, the rows with `fl(a + E) >= fl(T_a - E)` for the final k-th estimate `T_a`, as a CSR set to `_rescore.exact_sets`, the exact path of `rescore`. The set depends on the store and the query only, not on the threads, and the ids and score bits are those of the search without the prefilter. Whatever is outside the proven domain takes the whole call to the search of the previous paragraph, with its bits and its errors: a query whose normalized norm is not finite and at most 1.002 (`query_range`), a stored row whose inverse norm is not finite, is negative or disagrees with its codes (`unsafe_row`), a block that keeps more rows than its buffer holds (`overflow`) and survivors beyond `max(64 * k, 65,536)` per query after the running threshold cut them (`budget`). A call that enters the prefilter logs `store.prefilter`; memory is bounded by the buffers of the passes (at most 512 KiB per task), the survivors of the main thread (at most 8 MiB for 8 queries) and the 16 MiB of rows per task of `exact_sets`, and it is freed before a fallback. There is no new API and no new persistence name.
- **External indexes.** [External indexes on fse shards](../external-indexes.md) shows how FAISS, USearch and hnswlib take the rows of `iter_batches` and how `rescore` gives their hits the exact score.
- **Rescoring.** `VectorStore.rescore(queries, candidates, /, k=10, *, workers=None, max_per_doc=None, pool=None)` gives, for every query, the best `min(k, |C|)` rows of its own candidate set `C` (the positions of `candidates` without `-1` and without duplicates), bit for bit as `search(query, k, mode="exact", rows=sorted(C))`; with `max_per_doc=1` the best `min(k, documents)` documents, each by its best row, as the same search with `max_per_doc=1`. It has no `mode`: it always computes by the contract. `candidates` is an int64 array `(m,)` for one query vector or `(queries, m)` for a matrix, or a flat list; masked arrays, uint64 (a key above the int64 range would become `-1` and so a gap), other dtypes and lists of lists are rejected with `TypeError`, a wrong shape and values below -1 or at or above the row count N of the snapshot with `ValueError` naming the first place, all before a row is read. The values are checked against N of the snapshot the call takes under the active-use guard, so a call keeps the rows it started with and a position published later needs `refresh()`. A matrix result is as wide as the longest hit list, filled up on the right with ids `-1`, scores `-inf` and document IDs `-1`; a single query is not filled up (`DocumentSearchResult` for a store with document IDs). Every query is one task (`_rescore.exact_sets`, the internal CSR form without padding): its privately owned CSR section is sorted in place and deduplicated with a boolean mask. Public candidate arrays stay unchanged. Ascending parts are gathered with `_take.gather_sorted` in the stored dtype together with the inverse norms, scored by `backend.cosines` with one query column, and ordered by `_search.order_key` and the position. A set that does not fit `_TASK_BYTES` (16 MiB of gathered rows) is cut into parts of ascending positions whose best `k` rows (documents) are reduced the same way; that is exact because the order is total. `store.rescore` records each call (DEBUG: `queries`, `k`, `pairs`, `read_rows`, `workers`, `max_per_doc` when set).
- **Reading rows.** `get_vectors` and `get_doc_ids` read a range and copy it. `take_vectors(rows, /)` and `take_doc_ids(rows, /)` read an ordered list of store positions: a list or an int64 array of one or two dimensions, so `SearchResult.ids` works as it is. The result has the shape `rows.shape + (dim,)` or `rows.shape`, in the order asked, duplicates kept (unlike `search(rows=)`, which is a set), and is a new writable array. Negative positions raise `ValueError` with the place of the first bad one; they are never counted from the end, because a padded result such as that of faiss holds `-1`. `rows` is positional-only so a keyword can be added later. The positions are sorted once (stable), grouped by shard and read in blocks of about 16 MiB (one row if a row is wider) on the calling thread, then put back where they were asked; the bits of a row are those of `get_vectors`, whatever else is asked with it. Besides the output (`4·n·dim` or `8·n` bytes, no budget, as for `get_vectors`) it holds `O(n + S)` bytes of workspace for `n` positions and `S` shards, and one block; the time is `O(n log n + S log n + S)`. Keep `rows` unchanged until the call returns. `iter_batches(block_rows=, start=, stop=)` yields `fse.VectorBatch` with read-only views of the mapped shards in the stored dtype (int8 as `QuantizedRows`, whose float32 rows are `codes.astype(np.float32) * scales[:, None]`, the bits of `get_vectors`), at most `block_rows` rows (default 65,536) and never over the end of a shard. The batch also holds `inv_norms`, the read-only float32 view of the stored inverse norms of its rows, which stays readable after `close()` like the other views. `VectorBatch.normalized()` returns a new, writable, C-contiguous float32 array `(n_rows, dim)` whose elements are `float32(stored) * inv_norm`, for an index that takes float32 rows (FAISS, hnswlib); an int8 row uses its codes without the scale, because the inverse norm comes from the codes and the scale cancels out. In the default IEEE environment (round to nearest even, subnormals kept, no flush to zero) the bits do not depend on the block; under another rounding mode or flush to zero of the calling thread the result is only approximate, because only native code sets that environment. The rows are approximately unit length (the stored inverse norm is already rounded to float32), a zero row stays zero, and this is neither `normalize@1` nor a value of the numerical contract: no computation of fse uses it. The call checks the batch by hand (dtype, shape, row count, inverse norms finite and not negative, no broadcasting) and raises `ValueError` or `TypeError`; it holds `4·n_rows·dim` bytes for the output plus numpy's fixed ufunc buffer and `O(n_rows)` bytes of temporary flags for the check of the inverse norms, and reads no store. `VectorBatch` is new in 2.1 and its pickles are not promised across versions. The views and a suspended generator keep the mappings open, which locks the files on Windows; drop the views and call `close()` on the generator (or use `contextlib.closing`) when you stop early. After `VectorStore.close` the next block raises `RuntimeError`, also before the first.
- **Refresh.** `VectorStore.refresh()` and `ScoreStore.refresh()` take the shards published since the snapshot into the store itself and return the number of new rows (an int, 0 if there are none); there is no other object to switch to. Shards are immutable, so the old list stays valid: a refresh builds `old + new` and replaces the list under the lock of the store. It checks that `store.json` still equals the root of the snapshot and that the last shard of the snapshot has the manifest fingerprint it had when it was mapped (`Shard.fingerprint`, a private field filled by `open_shard`); otherwise it raises `RuntimeError("the store changed below its snapshot; open it again")`. It then follows the chain from the end of the snapshot with the summary of the last old shard as the shard before (the same `follows` as open, `verify` and repair), hashes the new tagged shards only, and lists the directory for gaps and orphans over old and new. A gap, an orphan or a break of the chain raises `CorruptArtifactError`; the rows stay as they were and the mappings of the failed attempt are released. A refresh needs no repair first, but nothing is promised against `repair_store` running meanwhile (it stays offline): a repair that changed the last shard is recognized, one that changed an earlier shard is not. One lock serializes refreshes. Every public read takes the shard list and the row count once, when it is called (`search`, `score`, `get_*`, `take_*`, `iter_batches`, `ScoreStore.iter_batches` and `predict_batches`, and the run of a head over a store), also a generator before its first block, so `stop`, the threshold plan and the rows of one call come from the same state; a refresh meanwhile reaches only later calls. Views have no `refresh`. `store.refreshed` and `scores.refreshed` record each call (DEBUG).
- **Closing.** `VectorStore.close` raises `RuntimeError("the store is in use ...")` while a search, score, read or refresh runs, because searches and scores run in worker threads over the shard list of the store, and the reads of `get_*` and `take_*` copy out of the mappings under the same guard. `iter_batches` holds the guard only while it takes its snapshot of the shards (at the call); its views keep their own mappings, so a suspended generator does not block `close`. `ScoreStore.close` never raises: a `ScoreStore` reads only in the calling thread, checks the store block by block and returns views that hold their own mappings.

## Concurrency

`pool=` limits computation threads. Each sink with committed rows adds up to three dedicated I/O threads outside that pool (see [Runtime, Sink threads](runtime.md#sink-threads)). Keeping them separate prevents a cycle where sink work waits for pool places held by an encode call waiting for the sink.

What several threads of one process may do with one `VectorStore`, one `ScoreStore` or one view at the same time, and what they cost; from "Processes" on, what several processes may do with one store.

- **Allowed at once.** Any number of threads may call every public read of one object at the same time: `search`, `rescore`, `score`, `take_*`, `get_*`, `iter_batches` and `verify` of a `VectorStore`, and `get_*`, `iter_batches` and `predict_batches` of a `ScoreStore`, also on a view, also while another thread runs `refresh`. Each read takes the shard list and the row count once when it is called (see "Refresh"). The list is replaced, never changed, and the mapped arrays are read-only, so a read neither sees a half-made list nor waits for other reads. `refresh` checks and maps the new shards without the lock of the store, then joins the old and the new list and swaps it under that lock. The lock is held only for that join and swap or to count a read. Refreshes are serialized by a second lock, taken before the first, so no two threads take them in the opposite order. The native kernels release the GIL. The merges of block results run in Python. The safety does not rest on the GIL but on immutable lists and arrays and on the references each call holds. Free-threaded CPython is not supported ([process.md](process.md)).
- **Bits.** A read in one thread gives the bits of the same call made alone, whatever runs in other threads: `search` with `mode="exact"`, and with `mode="auto"` for at most 8 query vectors per call; `score` with `mode="exact"`, and with `"auto"` for at most 8 weight vectors per call; the int8 prefilter; `rescore`, `take_*`, `get_*`, `iter_batches` and every read of a `ScoreStore`. `mode="blas"`, and `"auto"` above 8 vectors per call, promise neither bits nor ids, in one thread or in many (ties and nearly equal scores may order differently): their scores stay close to the exact ones and their results valid. `tests/test_store_vectorstore_concurrent.py`, `tests/test_scores_scorestore_concurrent.py` and `tests/test_store_view_concurrent.py` check this with many threads against a serial run (functional evidence, class correctness).
- **Refresh during reads.** A running read and a generator made before keep the rows they started with. Every later call sees the new rows. `refresh` does not wait for running reads, and reads do not wait for it.
- **Close during reads.** `VectorStore.close` (also of a view) raises `RuntimeError("the store is in use ...")` while a search, score, rescore, `take_*`, `get_*`, `verify` or `refresh` runs in its guarded part, which reads the shards, or while `iter_batches` takes its snapshot; it does not wait. Before and after that part a close can succeed: the checks of the arguments, the read of `store.json` by `verify`, the padding of a `rescore` result and the final copy of `get_*` below. A call that reaches its guarded part after a close raises `RuntimeError("the VectorStore is closed")`. A service therefore stops taking requests, lets the running calls end and then closes. A suspended `iter_batches` generator does not block `close`, and its next block raises. `get_*` makes its final copy after the guard: under the guard it gathers the parts of the range, one per shard (decoded float32 copies for `get_vectors`, views of the mapped int64 IDs for `get_doc_ids`), and `np.concatenate` joins them after the guard is released. A `close` can therefore succeed during this final copy. The views hold references to the mapped arrays, which keep the mappings open until the copy ends, so the result is whole. `ScoreStore.close` never raises: a `get_*` call that has taken its snapshot ends with the rows of that snapshot, and a generator raises `RuntimeError` at its next block.
- **Threads per call.** Without `pool=`, a `search`, `score` or `rescore` with more than one task runs in its own `ThreadPoolExecutor` with `workers` threads (default `usable_cpus()`), so N concurrent calls start up to N times `workers` threads. Calls with `workers=1` or a single task run in the calling thread (`rescore` makes one task per query).
- **Workers and pools.** `search`, `score` and `rescore` take the keyword-only `pool=` (an `fse.Pool`, the last keyword), as does the store mode of a head (`predict`, `predict_proba`, `decision_function`, `predict_batches` of a `Classifier` or `Regressor` given a `VectorStore`, which took `pool=` before and ignored it). With a pool the tasks run on the threads of the pool, at most `workers` at once (default `pool.workers`), and the call makes no threads of its own. Where a call is bit-defined (`mode="exact"`, `"auto"` for at most 8 vectors, the int8 prefilter, `rescore`, the store mode of a head), its ids, scores and document IDs are the bits of the call without a pool; `mode="blas"` and `"auto"` above 8 vectors stay close to the contract without a promise of bits or ids, as without a pool. `workers` above `pool.workers` is a `ValueError`, a closed pool a `RuntimeError`, a wrong type is refused by the argument check, all before a row is read. A service that shares one pool between its requests therefore runs at most `pool.workers` tasks at once on the threads of the pool, however many calls run; a call of one task runs in its own calling thread besides them (see below), so many one-query `rescore` calls are bounded only by the calling threads. The protocol is that of the runtime (runtime.md, "Pool") with one difference: a call takes one of the pool's `max_tasks` places for each task before it is submitted and gives it back when the task ends, not when its result is taken. The results it has not taken yet are bounded by its own window (`2 * workers` tasks), so `max_tasks` bounds the waiting and running tasks of all calls, and C concurrent calls keep together at most `C * 2 * workers` finished results (their sizes and why this differs from encoding: runtime.md, "Pool", Store calls on a pool). So the blocks a `predict_batches` stream of a store holds between two `next` take no place, and a consumer may call `search` or `encode` on the same pool between two blocks. A call that finds no place free takes a finished result of its own first and waits for a place only when it has none, so no call waits for a place it holds itself; tests run with fewer places than threads and many calls at once. A call that runs as one task (`workers=1`, one block, a `rescore` of one query) runs in the calling thread and takes no place; with a pool and more than one worker it still counts as inside the pool, so a call on the same pool from within it or from within a task on the pool is a `RuntimeError`, and so is one from a sink or a commit of an encoding call on that pool (runtime.md, "Pool"): it could wait for places its outer call holds; `workers=1` is always allowed there. The sink of the store mode of a head, and any code between two blocks of its stream, runs outside the call's tasks and holds no place, so it may use the pool. An error, a prefilter that gives up (it hands the pool on to the exact search) or a stream that is closed, collected or ends by an error cancels the call's own tasks that have not started, waits for its own running ones and leaves the pool open; the tasks of other calls are not waited for. `tests/test_store_vectorstore_pool.py` and `tests/test_store_search_run.py` check these properties (class correctness, no speed claim).
- **Memory per call.** There is no byte budget shared by concurrent calls (maintainer decision): the memory of a process is about the sum over the calls that run, so a service bounds it by the number of concurrent calls. `score` allocates its whole result, `4 · rows · vectors` bytes, in the calling thread before the first block; the limit on tasks in flight does not bound that. `search` holds, per task, the scores of one block (about 4 MiB; `mode="blas"` also the decoded rows, at most 16 MiB) for at most `2 · workers` tasks in flight, and the candidates of every query. `rescore` holds its owned CSR input for the call and one stored-row copy per running task, plus position, selection and winner buffers (see "Rescoring workspace" below). `get_*` holds about twice its output: the copied parts of every shard and the joined result. `take_*` holds its output, `O(n + S)` bytes of workspace for `n` positions and `S` shards, and one block of about 16 MiB (see "Reading rows"). The int8 prefilter adds its buffers (see "Search").
- **BLAS threads.** `mode="blas"` multiplies with the BLAS of numpy, which may run threads of its own. fse does not limit them (threadpoolctl is not a dependency). How concurrent BLAS calls share these threads depends on the BLAS and its build, and together with the threads of fse they can exceed the CPUs. A service sets the number of BLAS threads when it starts, before numpy is imported: `VECLIB_MAXIMUM_THREADS` (Accelerate on macOS), `OPENBLAS_NUM_THREADS` (OpenBLAS) or `OMP_NUM_THREADS` (OpenMP builds).
- **async.** Every read blocks its thread. An async service calls it in a worker thread (`anyio.to_thread.run_sync`, or Starlette's `run_in_threadpool`), never on the event loop.
- **fork.** Store and view objects are not safe across `fork`: the child inherits their locks and their count of running reads as they were at the fork, so a lock held by another thread then stays held, and a positive count makes `close` raise. Open the stores in each process after the fork, for example in the startup of the application rather than before a server forks its workers (gunicorn `--preload`, a `multiprocessing` pool with the start method `fork`), and do not use inherited stores, views or generators. Stores and views cannot be pickled (`TypeError`); pass the path and open it in the process. Every open hashes the tagged shards again (see "Reading").
- **Processes.** One writer process (a `ShardSink`) and any number of reader processes may use one store at the same time; each process opens the store itself (see "fork"). A reader sees a shard only once it is published, renamed whole into place: `refresh` adds the shards published since the snapshot, and a shard published while a reader follows the chain or lists the directory is either in its snapshot or added by its next `refresh` (see "Gaps"). Readers take no lock across processes and do not wait for the writer or for each other. Two writers in one store race for the name of the next shard (see "Errors and concurrency"), so write one store per producer and read several as one with `open_view`. `tests/test_store_vectorstore_processes.py` checks this with one writer process and three reader processes: after every publication, while the writer stands still, the long-lived store of each reader after `refresh` and a second open in each reader give the same rows, search results and tagged shards as a serial open, bit for bit, with `durability="full"` and `"none"`; a second test lets the writer process publish between the walk of the chain and the check of the gaps (functional evidence, class correctness, for `VectorStore`).
- **Cost of an open per process.** Every `VectorStore.open` maps every shard and hashes all tensors of every tagged shard (`durability="none"`) again, in every process: N processes that open a store with tagged shards read those bytes N times when they start. The record `store.opened` reports this cost for each open as `unsynced_shards`, `verified_bytes` and `verify_seconds` ([logging.md](logging.md)). A successful check never promotes a tag (see "Publication policy"), and fse has no option to trust shards that another process verified (maintainer decision). Two ways keep the cost low. Write the store with `durability="full"`, the default: its shards carry no tag and are not hashed when they are opened. The tag of a shard never changes later, and a full writer refuses to append behind a tagged shard, so for a store written with `"none"` this means a new store. Or open the store once per process and then call `refresh`, which hashes only the new tagged shards.
- **Page cache and RSS.** The shards are mapped read-only, so the processes that read one store share its pages in the page cache of the operating system: the rows are in memory once, not once per process. The resident set size (RSS) of each process counts the mapped pages it has touched, the shared ones too, so the sum of the RSS of the processes overstates their memory; on Linux, the proportional set size (`Pss` in `/proc/<pid>/smaps_rollup`) counts each shared page once in total. The hash of an open touches every page of the tagged shards, and a search every page of the rows it reads. Copies (`get_*`, `take_*`, results) are private memory of each process.
- **Windows.** Windows does not delete a file that a process holds open or maps ([DeleteFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew)). Removing a store or its old shards after a rotation therefore raises `PermissionError` at the first tensor file (`.npy`) that some process still maps through a store, a view, or an array or generator of them: close them in every process first, and drop such arrays. An open store does not protect the rest: `store.json` and the manifests are read through short-lived handles, so a recursive removal can delete them and part of the tree before it fails. Appending is not affected, because a writer adds shards and never touches published ones. `repair_store` runs only while no writer and no reader runs. `tests/test_store_vectorstore_processes.py` checks the refusal with a reader process on Windows, and `tests/test_store_mapped_files.py` checks on every platform, through an emulation, that a `ScoreStore` and the views of both kinds release their maps when they are closed.

## Shared shard base

The machinery of `sentence_vectors` does not depend on what a row holds, so it is shared by the kinds of rows a shard store can have (DR-162, Scores und Vorhersagen dauerhaft speichern). The base changes no byte and no check of `sentence_vectors`: the tests pin the complete bytes of the stores a `ShardSink` writes, their fingerprints, log events and the classes and messages of the errors.

- **Columns** (`fse._store._columns`). A shard is a directory of one `.npy` file per tensor. A `StreamColumn` is a tensor that grows with the rows: its file is created at the first write with the header of the full capacity, each commit writes its rows at their offset (`pwrite`) and feeds the checksum in row order, finishing cuts it to the rows committed and syncs it. A `MemoryColumn` is one small value per row, filled through views by the workers and written once when the shard is published. A `ConstantColumn` is a tensor without rows, the same in every shard and not cut when a shard ends early. The columns of a shard finish in the order of its list, which is the order of the syncs. `ShardBase` publishes such a list; `ShardWriter` is the shard of sentence vectors (`vectors`, optional `doc_ids`, `inv_norms`, for int8 `scales`), and `IdColumn` is a `StreamColumn` that also gathers the statistics of the IDs.
- **Sink base** (`fse._store._base_sink`). `ShardSinkBase` holds the reservation of rows over shards (with a buffer of its own for a task that crosses the end of a shard), the three threads with their shared first failure, `seal`, `publish`, `flush` and `close` with its deferred interrupt, and the clean-up of the shards not published. A family supplies its shard writer, the buffer of a split task, the target as the sink protocol hands it out and its log events; `ShardSink` does this for sentence vectors and keeps its events (`store.sink_opened`, `store.shard_published`, `store.sink_closed`) and the thread names.
- **Kinds** (`fse._store._kind`, `_kinds`, `_vectors_format`). A `Kind` reads the metadata of `store.json` (`parse_root`), opens a shard against it (`open_shard`), checks the values of one shard (`check_values`), recognizes well-formed future identifiers before any repair (`check_identifiers`) and answers the chain. The table `fse._store._kinds` is closed. It holds `sentence_vectors` and `prediction_scores` ([scores.md](scores.md)). `kind_of_root` reads `fse.kind`: a text that names a kind of the table selects it, a root without a text `fse.kind` is read by `sentence_vectors` with the checks and messages it always had (the keys of the metadata first), and a text that names no kind of the table is an `UnsupportedArtifactError` (before the shared shard base, a foreign kind with keys of its own was a `CorruptArtifactError`). `VectorStore.open` and `ShardSink` on a score store, and `ScoreStore.open` and `ScoreSink` on a vector store, raise `UnsupportedArtifactError` naming the right class. `store.json` is read up to 64 KiB, and up to 1 MiB for `prediction_scores`, which lists its heads and their labels; a larger file is a `CorruptArtifactError`, and one over 64 KiB that names no score store keeps the message "larger than 65536 bytes".
- **Chain check.** Two valid shards can still be wrong as neighbours. A kind gives each shard a small, bounded `summary` (read from the mapped tensors and the manifest, without hashing) and says through `follows(previous, current)` why a shard cannot follow the one before it, or `None`. Snapshot (`VectorStore.open`, `ShardSink`), `VectorStore.verify` and `repair_store` run the same sequence. A breach is the damage of the later shard: opening names it and its first row and points to `fse.repair_store(path)`, and repair moves that shard and its tail into the quarantine like any other damaged shard. The preflight of repair still inspects every canonical entry first, so an unsupported later shard leaves the store untouched. `sentence_vectors` has no chain rule: its summary is `None` and every shard follows every other.

## Repairing a damaged tail

`fse.repair_store(path) -> int` is an explicit offline operation. Run it only while no writer and no reader runs. It checks every canonical shard, including untagged full-durability shards, using structure, mapped checksums and bounded value checks. It keeps the verified prefix and returns its row count. A successful repair does not promote tagged shards: their metadata stays unchanged, and later reader opens still verify them.

Before creating or moving anything, repair inspects every canonical entry, including orphans and entries after the first damaged shard. An unknown container, quantization identifier or durability value raises `UnsupportedArtifactError` without mutation. Malformed artifacts determine the damaged tail; operational I/O errors propagate. A well-formed unknown quantization identifier is unsupported, including an unknown family. Invalid identifier syntax remains corruption.

The first damaged chain shard and every later chain shard move aside, along with every canonical orphan. If only orphans are present, the complete verified chain stays. Dot entries remain untouched. If nothing must move, repair creates nothing.

Repair creates `.broken-<hex>` and fully syncs the store directory. It then exclusively renames moved entries into that directory in descending row order. After every single rename it fully syncs the destination directory, then the store directory, before starting the next move. Windows uses its existing write-through exclusive rename and has no directory-sync primitive. Nothing is deleted or overwritten. An error stops the operation and preserves its partial work. After full preflight, rerunning repair syncs existing quarantine directories and the store, even when no moves remain. This completes a final rename interrupted before its syncs. Old quarantine contents stay untouched. `store.json` and store version 1 never change.

A reader or appender encountering an incomplete repair can refuse an original damaged shard or a gap. The gap check prevents an append from reconnecting an old tail. Tests cover every process-crash boundary, modeled power loss, and appending before a repair rerun. The sync sequence is tested directly. As an independent guard, gap checking keeps crash states safe even when intermediate repair syncs are removed in a test. A combined mutation removing those syncs and gap checking demonstrates old rows relinked after a new append.

Stores with document IDs use [document-ids.md](document-ids.md) for their version-2 schema, filtering and API. All durability and repair rules above apply to both columns. Ordinary stores without document IDs remain version 1.

## Resume stores

`ShardSink(path, encoder, resume=True)` and `Encoder.encode(texts, sink=sink, shard=(i, n))` continue a stopped run (DR-248, Vektor-Stores wiederaufnehmen und feste Partitionen schreiben). The store has the mode `source_rows@1` ([document-ids.md](document-ids.md), "Resume mode `source_rows@1`"); a store without the mode is not resumable, and a resumable store is opened with `resume=True` only (`ValueError` both ways).

- **Sources.** A source that can be read again: a list, tuple or numpy array of `str`, token lists (the external tokenizer), a path of a text file, or a `StringSource`, `TokenListSource` or `FileSource`. A stream and an Arrow text column are refused with a `TypeError` before anything is read; a stream is read once, and a stopped run cannot read it twice.
- **Partitions.** `shard=(i, n)` takes the source rows `[a_i, b_i)` with `B = ceil(N / 16384)`, `a_i = 16384 * floor(i * B / n)` and `b_i = min(N, 16384 * floor((i + 1) * B / n))`: whole blocks of 16,384 rows, contiguous, disjoint and complete. A part can be empty. Each process writes a store of its own; two writers in one store fight for the name of the next shard. The rule freezes with 2.1.
- **Run.** `encode` checks the arguments (nothing of the source is read), opens the source, hashes all of it, and lets the sink compare the identity with the store. A different source, partition, encoder, dtype or ID mode is a `ValueError` before any row is reserved, with no change of the store. A new store is made at that point (`ShardSink(resume=True)` creates nothing). The sink verifies the published shards (tagged ones are hashed, also under `none`) and, under `full`, syncs the store directory once: a shard whose rename an earlier run left unsynced is then confirmed before it counts. A failed sync is a `PublishedNotDurableError` before any reservation. The rows after those the store holds, up to the end of the part, are encoded through a window onto the source; `ShardSink.first_row` is the number of rows kept. A store that holds its whole part is left alone and `encode` returns.
- **Bits.** The rows are those of an uninterrupted run, bit for bit. Gate A: with the same build, durability, shard size and a stop between whole shards, `store.json`, the manifests and the `.npy` files are byte-identical to a run in one piece. Gate B: after a stop at any point (during a write, after `seal`, in `flush`, with a shortened shard) and a replay with other workers and task boundaries, the rows equal those of the run in one piece and of `fse._reference`; no row is missing or doubled; tags stay as they were.
- **Other entries.** `encode_batches` and `predict_batches` take a sink made with `resume=True` only with `positions=True` (below, "Stream positions") and refuse it otherwise, and every entry but `Encoder.encode`, the `predict` of heads and those two refuses it; `shard=` without such a sink is a `ValueError`. `Heads.predict`, `Classifier.predict` and `Regressor.predict` resume a score store, a vector store or both in one call ([scores.md](scores.md), "Resuming a run").
- **After a crash.** The temporary directories `.shard-*.writing-*` of an unfinished shard stay in the store; they are ignored, and removing them is up to the owner. `Encoder.encode(..., lengths=)` reports the rows run by that call, and its `first_row` is their row in the source.

## Stream positions

`ShardSink(path, encoder, resume=True)` and `Encoder.encode_batches(batches, sink=sink, positions=True)` resume an endless stream that can be read again from a position (DR-252, Unendliche Streams an einer wiederlesbaren Position fortsetzen). The store has the mode `source_position@1` ([document-ids.md](document-ids.md), "Resume mode `source_position@1`"). A store of one resume mode is not resumed by the other call: `encode(texts, sink=, shard=)` and `predict(..., shard=)` write `source_rows@1`, and `positions=True` writes `source_position@1`; the wrong one is a `ValueError` that names both modes. A sink made with `resume=True` is refused by `encode_batches` without `positions=True`, and `positions=True` needs such a sink.

- **Batches.** Each batch is `(texts, position)`, or `(texts, doc_ids, position)` with `doc_ids=True`. `position` names the first record of the batch (maintainer decision of 2026-11-06: only start positions, one per batch). Empty batches are allowed and change nothing. A sink takes one run.
- **Resuming.** `sink.source_position` is `(P, skip)`. The caller seeks to `P` and gives the batches again, with any batch size and any `workers`. The first `skip` records of the replay are dropped (no tokenizing, no writing); the batch that holds the end of them is cut, a batch the store holds completely is reported with `n_rows = 0`, and every later record is written as the run that never stopped writes it, bit for bit. A list, a tuple or an Arrow column cuts by slicing; an Arrow batch that must be cut is read into a list of its texts, once. A stream that ends before it delivered the `skip` records is a `ValueError` at the end of the iteration (closing the iterator earlier is allowed).
- **Results.** One result per batch of the stream: `first_row` is the replay row of its first computed record (the replay rows count the records from the seek), `n_rows` the records computed, `durable_rows` the replay rows that are durable: the least over the sinks of the rows the sink held when it attached plus the rows it published since, but at most the records delivered so far, and 0 if a sink does not sync. A consumer commits its input up to the record of the replay row `durable_rows - 1`. With Kafka that is the offset of that record plus one; the consumer keeps the map of replay row to record, because offsets can have gaps ([recipes/09-fse-behind-kafka.ipynb](../../recipes/09-fse-behind-kafka.ipynb)). The store stays the truth for a restart.
- **An existing store** is compared with the sink, verified (tagged shards are hashed, also under `none`) and, under `full`, its directory is synced once before the first batch is read, as for `source_rows@1`. A new store is made with the first non-empty batch.
- **Rotation.** One store per section of the stream (a day, a partition): `flush()` and `close()` at a batch boundary, and the next batch of a new sink makes the next store. After a restart the newest store of the stream continues; a crash between two stores appends to the older one. The caller orders the sections by name. Several stores are read as one by `open_view`, in the order given.
- **Limits.** Only a source that delivers the same records in the same order from `P` on resumes: one Kafka partition per store, one Kinesis shard, one log file with byte offsets. A compacted or rewritten log does not. A live stream with no replay stays with `encode_batches` as in 2.0 (at least once) or needs a buffer that can be read again in front of it. fse does not check what `P` means, so the caller puts topic, partition and cluster into `P` and checks them when it seeks. The temporary directories `.shard-*.writing-*` of a crash stay as in "Resume stores".
- **Errors.** A batch that is not a tuple of the right size, a position that is no `str` or has no 1 to 65,536 bytes, and document IDs that do not fit the batch are named with the batch (`batch k`) before a store is made.

## Sign bits

A store of sentence vectors may hold, beside each shard, the **sign bits** of its rows (DR-265, Vorzeichenbits als Begleitdatei je Shard lesen und mit fse.add_sign_bits nachrüsten; part of DR-255, Binäre Vorsuche mit exaktem Nachrechnen als Opt-in anbieten). They are the input of the binary search (below). The rule is `sign_bits@1` ([numerical-contract.md](numerical-contract.md#sign-bits-sign_bits1)), the reference `fse._reference_bits`.

- **Companion artifact.** `sign_bits-<first row>` (the row in at least 16 digits, as a shard name) is an NpyContainer next to `shard-<first row>`, with the tensor `sign_bits` (uint8, shape `(rows, ceil(dim / 8))`, dimension 0 in the highest bit of byte 0, padding bits 0). Its metadata holds exactly `fse.kind=sign_bits`, `fse.format_version=1`, `fse.bits=sign_bits@1`, `fse.encoder`, `fse.dtype`, `fse.output_dim`, `fse.first_row`, `fse.rows`, `fse.shard_fingerprint`, `fse.created_by` and, for an artifact written with `durability="none"`, `fse.durability=none`, besides the checksum and the fingerprint of the container. It is not a tensor of the shard, so shards, `store.json` and their fingerprints do not change and an existing store gets bits without rewriting an immutable shard. Only stores of sentence vectors have them; a score store ignores the entries.
- **Binding.** The artifact belongs to the shard whose manifest fingerprint is `fse.shard_fingerprint`. The first row, the rows, the encoder, the dtype and the dimension must equal those of the shard. Anything else is `CorruptArtifactError` that names the artifact, its first row and `fse.repair_store(path)`. An artifact of an unknown `fse.format_version`, an unknown `fse.bits` rule or a container this fse does not read is `UnsupportedArtifactError`; it is never skipped. A later rule gets its own prefix, and within `sign_bits-` only version 1 exists.
- **Missing bits are valid.** A shard without the artifact is a valid shard: the bits derive from its vectors by the same rule. v2.0.0 reads a store with bits as before and passes over the entries.
- **Orphans.** An artifact of no shard of the snapshot is damage if it lies below the end of the snapshot. One at or after the end whose shard is published now belongs to a writer that published the shard after the snapshot, and the snapshot passes it over: a writer always publishes the bits after the shard. Without such a shard it is an orphan and `CorruptArtifactError`.
- **Reading.** `open` and `refresh` list the entries, check the binding and structure, map the artifact read-only (`Shard.sign_bits`, private; the `tensors` of a shard stay as they were) and hash it if it is tagged `fse.durability=none`. A view takes the field with its shards. `refresh` also attaches the bits that appeared for the shards of the snapshot since (`store.refreshed` field `added_sign_bits`). `store.opened` records `sign_bits_shards` and `sign_bits_bytes`. `verify` hashes every artifact, checks that its padding bits are 0 and recomputes its bits from the vectors in blocks of at most 1 MiB.
- **`fse.add_sign_bits(path, *, durability="full", workers=None, pool=None) -> int`** writes the artifact of every shard that has none and returns their number. The store is opened and checked first, so damage raises before anything is written. An untagged shard is not hashed when it is opened, so the backfill hashes the vector bytes it reads (blocks of at most 16 MiB, in row order), derives the bits from exactly those bytes, and publishes only if the hash equals the checksum of the manifest of the shard; otherwise it raises `CorruptArtifactError` and publishes nothing. The artifact is written in `.sign_bits-<first row>.writing-<hex>` and renamed into place without replacing anything. A writer that lost the rename to another one checks the artifact in place and goes on if it is valid. An interrupted run leaves valid artifacts; a rerun does the rest and gives the same bytes as an uninterrupted run. `durability="none"` skips the sync of the store directory and tags the artifacts; the artifact of a shard tagged `durability="none"` is tagged in any case, so it is not durable before its shard is. `store.sign_bits_added` records the call. It is a function, like `repair_store`: it needs no open store, and a reader does not write.
- **Backfill pool.** `fse.add_sign_bits(..., pool=pool)` uses the shared pool runner and task places, with at most `workers` shards running at once. The default is `pool.workers`; a larger count raises `ValueError`, a closed pool raises `RuntimeError`, and an invalid type is refused before the store is read. One shard still enters the pool runner when `workers > 1`, so a nested call on the same pool is refused. With `workers=1` work stays inline. Failed calls cancel their pending tasks and wait for their running tasks, leaving other calls and the pool open. Without a pool the existing `fse-sign-bits` executor and cancellation behavior stay unchanged.
- **Repair.** `repair_store` inspects the artifacts with the shards, before any move. The sign bits of a moved shard move before the shard, in the descending order of rows; bits that are not the valid bits of a kept shard (bound to another shard, damaged, different from the vectors) and orphans move alone. A crash between the two moves of a pair leaves a shard without bits, which is valid. Unknown formats stop the repair before any change. `store.repaired` records `moved_sign_bits`.
- **Writers of v2.0.0.** Its `repair_store` moves shards only and its append writes shards without bits. A bits artifact left behind there is, for this version, an orphan or bound to another shard (`CorruptArtifactError`), and `repair_store` of this version moves only that artifact.
- **`ShardSink(sign_bits=True)`** (DR-266, Vorzeichenbits beim Schreiben mit ShardSink(sign_bits=True) mitschreiben; default False, and without the switch the bytes written are those of before) writes the artifact of every shard it publishes. Each shard being written holds a `BitsColumn` (`_bits_writer`), an array of `ceil(dim / 8)` bytes per row: `ceil(dim / 8) / (dim * itemsize)` of the vector bytes of the shard, which is 1/32 for float32, 1/16 for float16 and 1/8 for int8 when `dim` is a multiple of 8 (computed, not measured). The commit of the rows, in the hash thread and in row order, derives their bits from the codes it was handed by the rule of `fse._reference_bits`; the runtime and the write thread are unchanged. The bits are published as a step of their own in the publisher thread, after the shard is renamed and its rows are counted (`published_rows`, `durable_rows`, `store.shard_published`): `ShardBase.publish_extras` writes `.sign_bits-<first row>.writing-<hex>`, binds it to the shard as it is on disk (`open_shard`) and renames it into place without replacing anything (`publish_bits`). The durability is that of the sink: under `full` the store directory is synced for the rename, under `none` it is not and the artifact is tagged `fse.durability=none` (the container still syncs the files of the artifact, as for `add_sign_bits`). The artifact has the bytes `fse.add_sign_bits` writes for the same shard (a test compares them).
  - *Failures.* A failure of the bits is an error of the sink, raised like a failure of a shard, but never changes the rows already counted: the shard stays published, `published_rows`, `durable_rows` and the position of a store of the mode `source_position@1` are those of the shard, later shards are dropped, and the temporary directory of the bits is removed (a removal that fails is reported like the other failed cleanups of a sink). A failed rename leaves a valid shard without bits. A failed sync after the rename is a `PublishedNotDurableError` that names the artifact; the shard itself counts as durable. A failure while the bits are derived is a failure of the commit: the shard is not published, as for any failure of the hash thread. A rename lost to a concurrent `add_sign_bits` is no error if its artifact is valid and holds the bits of this sink (then the sink did not publish them, `sign_bits_shards` does not count it, and the artifact keeps the durability its writer gave it), and a `CorruptArtifactError` if it is damaged or differs. A stop or Ctrl+C between the shard and its bits leaves a valid store; bits of a shard are never published before it.
  - *Resume.* A sink made with `resume=True` and `sign_bits=True` writes the bits that the published shards it keeps lack, when `encode` or `encode_batches` attaches its source and the store is verified: the same checked backfill as `add_sign_bits` (the vector bytes are hashed against the checksum of the shard while the bits are derived; a mismatch is a `CorruptArtifactError` and publishes nothing), with the durability of the sink, one shard at a time. A store resumed after any stop, including one between a shard and its bits, so has the bytes of an uninterrupted run (gate A). A sink that only appends does not read the store whole and leaves the bits of its prefix to `add_sign_bits`; a resume without the switch writes no bits. Shards with and without bits may mix.
  - *Log.* `store.sink_opened` records `sign_bits` and `store.sink_closed` records `sign_bits_shards`, the artifacts this sink published, only for a sink made with the switch; a resume that backfills emits `store.sign_bits_added`. No timing was measured for the write cost of the bits in this version; it follows in a window the maintainer assigns.
- **Binary search.** `search(queries, k, mode="binary", oversample=None, ...)` (DR-267, Binäre Suche mit search(mode="binary", oversample=) anbieten; part of DR-255) ranks rows by their sign bits and scores only the best ones exactly (`_store/_binary_search.py`). Stage 1 computes, in numpy and in blocks of rows, the Hamming distance `popcount(bits XOR query bits)` of every selected row to every query (`fse._reference_bits.hamming`, no `np.bitwise_count`) and keeps the `m = min(oversample * k, selected rows)` rows with the smallest distance per query, a tie going to the smaller position. The key of a row is `(distance << 41) | position`, so the order is total and the candidates `C` of a query depend on neither the blocks nor the threads (at most 2**41 rows). The bits of a query come from its float32 values by the rule `sign_bits@1`, before any normalization. Stage 2 is `_rescore.exact_sets` on those candidates, the exact path of `rescore`. So the result is `search(query, k, mode="exact", rows=sorted(C))` bit for bit, ids and score bits; when `m` reaches the selected rows it is `search(mode="exact")` with the same selection. What is not bit-defined is only recall: the exact search may find a row that stage 1 dropped.
  - *Arguments.* `oversample` is a positive integer and needs `mode="binary"` (`ValueError` otherwise, before anything is read); the default is `DEFAULT_OVERSAMPLE = 40` in `_binary_search.py`, the one factor that reached a recall of 0.95 for both models in the K-probe of DR-255. It is provisional until DR-264 (Recall der Varianten und Kosten der Bitsuche gegen den int8-Vorfilter messen) fixes it and a second corpus confirms it. `"binary"` is not a mode of `score`, and `"auto"` never chooses it. `rows=` and `doc_ids=` limit stage 1 to the selection. `workers=` and `pool=` apply to both stages (threads `fse-binary` and `fse-rescore`), as for the other modes; the bits do not depend on them. A result has the shape of a rescore result: a matrix of queries is padded once, with the widest list of the whole call (ids `-1`, scores `-inf`), a single query is not padded.
  - *Documents.* `max_per_doc=1` is allowed: stage 2 returns the best row of each document among the candidates, so a document whose rows all fell out of stage 1 is lost, and the result holds the best `k` of the documents that stage 1 reached, not of all documents. A store with document IDs labels the hits as in `search`.
  - *Missing bits.* A shard without its artifact is not an error: its bits are derived from its rows for the call (the same rule, so the same bits as the artifact), and the first call on a store object logs one `store.bits_derived` WARNING, which names no path. Stores with and without bits per shard, and views whose members differ, work. Deriving costs reading the vectors of that shard in numpy; `fse.add_sign_bits(path)` writes the artifacts once.
  - *Memory.* A stage 1 task holds the distances of a block of rows with a block of queries (rows times queries at most 2^18, 1 MiB of int32), the keys it keeps (at most as many int64, 2 MiB) and the temporaries of one query column (rows * 8 bytes); the reference runs on sub-blocks whose table has at most 2^18 entries (1 MiB), bits are derived on at most 2^20 values at a time (a bool matrix of 1 MiB), and bits gathered for a selection stay within 16 MiB (`R * ceil(d / 8)`, 1 MiB for 8 queries at d = 256). The keys of a block of queries are merged on arrival into one buffer of `m + rows` keys that is partitioned in place, so merging allocates no array of the size of the buffer. The candidates of a group of queries are bounded by `CANDIDATE_BYTES` = 64 MiB at `CANDIDATE_ENTRY_BYTES` = 24 bytes per candidate (the buffer 16, the result being added 8; while the set is written, the buffer 16 and the positions 8): a call with more candidates runs in groups of up to 256 queries one after the other (each group reads the bits again), and a call whose single query does not fit raises `ValueError` that names `oversample`, before a row is read. Stage 1 also retains up to `2 * workers` completed task results until collected, each `8 * min(m, block_rows) * group_queries` bytes. Count those separately from running task workspace and the candidate buffer. At m = 520,000 and eight queries the groups have five and three queries, with block limits 52,428 and 65,536 rows respectively. Stage 2 holds an owned CSR of `8 * group_queries * m` bytes, then the workspace below per running query. Group size, rather than the total query count, bounds the candidate buffers. Resident mapped pages depend on the store size and page cache as well.
  - *Scope.* A `VectorStore` and a view of them only; a score store has no similarity search. No new persistence name. No timing was measured: the cost of stage 1 against the int8 prefilter is the question of DR-268 (Kosten der binären Suche messen und über einen nativen Popcount-Kern entscheiden). The asymmetric rank (`query_bits=4`) is DR-269 (Asymmetrische Anfragekodierung query_bits=4 für die binäre Suche anbieten).


### Rescoring workspace

The allocation model distinguishes call-owned input from additional running-task workspace.
Let m be candidates without gaps, u unique positions, d dimensions, s bytes per stored value,
p = max(1, floor(16 MiB / (d*s + 20))) rows per part, S shards, and h = min(k, u).
The public candidate input is borrowed; `rescore` builds its own CSR of 8 times the total
candidate count in bytes. Building it also uses a one-byte mask per input entry and query
offsets. Binary search and the int8 prefilter supply freshly owned CSR arrays too.
`exact_sets` may reorder each disjoint query section in place.

| Allocation per running query | Before | After |
| :--- | :--- | :--- |
| Unique positions | `np.unique`: version-dependent workspace and result capacity (logical size 8u) | In-place sort, m-byte mask; 8u-byte copy only with duplicates |
| Stored vectors of a part | 2*p*d*s transient bytes | p*d*s bytes |
| Gather position order and ordered positions | 16p bytes per column | None |
| Shard starts, search boundaries and their conversion | O(S) per gather | O(S) per gather |
| Local shard indices | 8p bytes | 8p bytes, released after each shard block |
| Inverse norms | Output 4p plus gather indices and temporary 4p copy | Output 4p, no second value copy |
| Document IDs with `max_per_doc=1` | Output 8p plus gather indices and temporary 8p copy | Output 8p, no second value copy |
| Cosine scores | 4p bytes | 4p bytes |
| Ungrouped part selection | About max(24p, 16p + 12*min(k,p)) bytes plus small sort workspace | Same |
| Winner merge | O(h) positions, scores, optional labels, ordering and selection | Same |
| Winner document IDs without grouping | General gather on score-ordered winners, O(h + S) | Same |

The deduplication mask dies before gathering. Without duplicates the sorted section is a
view of the call-owned CSR. With duplicates its compact copy lives through the query.
For the CPU backend the dominant additional workspace is
max(m, p*d*s + O(p + S)) without duplicates, or
max(m + 8u, 8u + p*d*s + O(p + S)) with duplicates, plus O(h) winners and merge buffers.
Multiply running-task workspace by active workers, not by all queries. Keep the CSR,
finished results and final padded output separate. Grouped selection has its own O(p)
document-ordering workspace. The NumPy reference backend additionally converts int8 and
float16 rows to float32 (4*p*d bytes), with further arithmetic temporaries in `dot16`.
These CPU workspace formulas therefore do not bound the reference backend. Neither is
a strict total RSS limit.

`gather_sorted` assumes ascending unique positions and validates the whole range before
accessing tensors. It uses `np.take(..., out=..., mode="clip")` on each shard block with
matching source and output dtypes. The validated indices cannot clip. [NumPy documents](https://numpy.org/doc/1.26/reference/generated/numpy.take.html)
that `mode="raise"` always buffers `out`; using it would restore the second row copy.
The general `gather` remains necessary for score-ordered winner IDs and public `take_*`.

## Views

`VectorStore.open_view(paths, *, encoder=None, backend="cpu")` and `ScoreStore.open_view(paths, *, heads=None, name=None, backend="cpu")` read several stores as one (DR-251, Mehrere Stores als eine Sicht lesen). Nothing is merged on disk. Shards are immutable, so a view is the list of the shards of its members with `first_row` moved by the rows of the members before it (`dataclasses.replace`); every read of a store (search, score, `take_*`, `get_*`, `iter_batches`, `predict_batches`) runs on that list unchanged. `mode="exact"` is therefore bit-identical to one store (BLAS blocks follow the shards, so `blas` and `auto` above 8 queries differ in the last bits, as between two shard sizes) that holds the same rows, and equal scores keep the order of the smaller position, also across a boundary between members. Positions are the concatenation of the members.

- **Opening.** `paths` is a list or tuple of paths, not empty, none twice (the same directory by another name counts as twice). Each member is opened as `open` opens it (`encoder`, `heads`, `name`, `backend` apply to every member). A member that fails to open, or does not fit, closes all that were opened and releases their mappings (`clear_exception_frames`).
- **What members must share.** `info.check` between every member and the first: encoder, dtype, dimension and the document-ID mode; for scores also the heads, their model, columns, labels and the paths they ran on (mixed dtypes are refused: int8 rows hold their own scales, but a view reads one dtype). For scores the chain across a boundary: the first shard of a member must follow the last shard of the member before it by `follows`, so the thresholds are equal (an empty member is passed over). Members of the mode `source_rows@1` also need the same execution fingerprint. The position chain of `source_position` stays inside each member and is not compared across them.
- **Order.** Members of the mode `source_rows@1` must be parts of one source: same source fingerprint, form and number of rows, same `n`, each part `i` at most once (twice is a `ValueError`; another source or another `n` too). Maintainer decision of 2026-11-06: parts may be missing or unfinished, because producers may still run. The view takes the members in the order of `i`, whatever the order of `paths`. Only if all `n` parts are there and each holds its whole part are the positions rows of the source and `source` is `{..., first_row: 0, rows: N, shard: [0, 1]}`; otherwise the positions are the concatenation in the order of `i`, `source` is `None`, and `members` names `i` and the rows of each member. Such a partial view is a snapshot: a view has no `refresh`, so open it again to see new rows. Members without a source keep the order given and the positions are their concatenation; a mix of members with and without a source is a `ValueError`. Stores of the mode `source_position@1` also keep the order given, with no claim on a source (`source` is `None`); a mix of them with stores of the mode `source_rows@1` or of no mode is a `ValueError`.
- **Readers.** `paths` (tuple, in the order of the positions; one path for a store that is no view), `members` (a tuple of read-only mappings with `path`, `first_row`, `rows` and `source`, and for the mode `source_position@1` also `position`, the `(P, skip)` of the member), `source` (a read-only mapping `mode`, `fingerprint`, `form`, `first_row`, `rows`, `shard`, or `None`; a view of all finished parts has `first_row` 0, `rows` N and `shard` `[0, 1]`; any other view has `None`) and `locate(ids)` (two int64 arrays of the shape of `ids`: the index into `paths` and the row in that store; a negative position or one beyond the rows is a `ValueError`). `path` is `None` on a view. Pairing: two stores written from the same source (`source` not `None`, mode `source_rows@1`, equal) have the same source row at the same position for the first `min(len)` rows, and are paired completely if their lengths are equal. `None == None` says nothing, and neither does a store without a source.
- **Life cycle.** A view has no `refresh` (`ValueError("a view does not refresh; open it again")`; a closed view raises `RuntimeError` first). `verify` verifies each member over its own path and then the chain across the boundaries; it counts as a running read, so `close` of a `VectorStore` view raises while it runs. `close` closes every member. `store.view_opened` and `scores.view_opened` record each open (INFO), after the `store.opened` or `scores.opened` of the members.
- **Network drives.** Reading works but lies outside the crash contract (local APFS, ext4, XFS): clients can cache directory lists, so a view of stores that are still written should be opened again, not assumed current. An exact search maps the files; on a network drive it is fast only with a warm page cache or a local copy, and no figure is claimed without a class descriptive measurement. Write one store per producer.
