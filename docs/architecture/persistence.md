## Identifiers and versions

Binding for every 2.0 module (formerly under "2.0 design").

Aggregations, steps and tokenizers are written `"<name>@<version>"` (name `[a-z][a-z0-9_]*`, version a decimal integer without leading zeros), for example `weighted_mean@1`, `normalize@1`, `fse_words@1`. `transform_version` versions the shared rules in [Numerical contract (`transform_version` 2)](numerical-contract.md#numerical-contract-transform_version-2), the identifier versions the rules of one operation. Any change of the arithmetic the CPU defines bumps the matching version (a device implementation within the tolerance contract does not); from the first 2.0 release on, an identifier is never removed or given another meaning within 2.x. Before it, identifiers that are no longer needed are removed, not reserved (maintainer decision of 29.10.2026): `remove_components@1` and `project@1` went with fit, and an artifact that names them is refused like any unknown one. Reading an artifact with an unknown name, version or `transform_version`, or a disallowed step list, raises `UnsupportedArtifactError` (a `ValueError`) that names the supported ones; nothing is skipped.

## Identities

Binding for every 2.0 module (formerly under "2.0 design").

- A **row id** is the int64 position of a sentence in its source, from 0.
- A **shard** is a contiguous range of rows; 2.1 splits sources with `shard=(i, n)` at multiples of 16,384 rows.
- A **checksum** is `xxh3-128:` and the 32 lowercase hex digits of XXH3-128 with seed 0 (in the canonical big-endian form, as `xxhash.xxh3_128().hexdigest()` gives it) of bytes fed in order; a tensor's checksum is that of its little-endian C-order bytes, and a tensor without elements has the checksum of no bytes, `xxh3-128:99aa06d3014798d86001c324468d497f`. `fse._container._hash` is the only module that computes one and the only one that imports a hash library (`hash-importers` of the guardrails); it streams (`update` releases the GIL for large inputs), takes bytes, C-contiguous memory and C-contiguous little-endian arrays only, and the containers feed it in chunks. Values are compared as whole strings, the algorithm included.
- A **fingerprint** is the checksum of the UTF-8 bytes of the canonical JSON (keys sorted, separators `,` and `:`, no whitespace, non-ASCII characters unescaped) of `{"fingerprint": 1, "metadata": {...}, "tensors": [[name, dtype, shape, checksum], ...]}`: the metadata without `fse.created_by`, `fse.fingerprint` and the `fse.checksum.` keys; the tensors sorted by name, with the dtype code (such as `"F32"`), the shape as a list of integers and the checksum of the tensor. It describes the content, not the container, so every container gives the same fingerprint. A pre-release of 2.0 hashed the same document with sha256; its values are not read. The test vector (`tests/test_container_common.py`): tensors `vectors` F32 `[[1, -0.0], [0.5, 2]]`, `vocab.bytes` U8 of `"aé"`, `vocab.offsets` I64 `[0, 1, 3]` with metadata `fse.kind=word_vectors`, `fse.format_version=1`, `fse.dim=2`, `fse.dtype=float32` give `xxh3-128:8011e82efda8fabff21969cbaad4fae3`, and with `fse.note=é` added `xxh3-128:9e1f9e8737c4b9c190d5600af20953e0`.
- **What the hashes guarantee.** Checksums and fingerprints identify content against accidents: damaged, truncated or changed files and data that changed since they were checked (with 128 bits, a chance collision needs about 2**64 artifacts). They are no authentication: xxh3 promises neither collision resistance nor second-preimage resistance, so someone who can write a file can make different content with the same checksums and fingerprint, and no security-relevant binding may rest on them, such as a store's `fse.encoder`, a Vocabulary's fingerprint or the `expected` checksums of `save` and `quantize`. Anyone who can write a file could always recompute its values anyway, as no key is involved; the files are free of pickle and read strictly, so a forged file gives wrong data, not code execution. Authenticity needs a trusted reference: a cryptographic hash of the whole file from a trusted source, or a pinned revision; a hash computed from the file itself authenticates nothing. The Hub loader (`fse._hub`, [Model2Vec models and from_pretrained](hub.md#model2vec-models-and-from_pretrained)) takes this from the Hub: registry artifacts must be LFS files, whose sha256 (`lfs.sha256`) a commit pins; a missing `lfs.sha256` is rejected, and a cached file is checked against it at its first trusted use.
- An encoder holds its table; stored vectors reference their encoder by fingerprint; opening them with a mismatch raises. 2.1 adds the fingerprint of the source for resuming.

## Persistence names replace class paths

Binding for every 2.0 module (formerly under "2.0 design").

Saved 2.0 artifacts contain no Python class paths. Their persistence API is the set of strings in [Artifacts](formats.md#artifacts) and [Identifiers and versions](#identifiers-and-versions): `fse.kind` values, identifiers, dtype codes, tensor and metadata names. From the first 2.0 release on, these are never renamed or reused with another meaning; before it, names that are no longer needed are removed, not reserved, and artifacts of a pre-release that hold them are refused (maintainer decision of 29.10.2026). The public Python API is `fse.__all__`; private modules (with a leading underscore) may move freely.

## Migration

Binding for every 2.0 module (formerly under "2.0 design").

2.0 has no pickle loader and no converter of 1.x models: 2.0 models are finished tables, made of word vectors (`fse.gensim.from_gensim`, `Encoder.from_word_vectors`) or, for SIF and uSIF, by the offline notebook with the 1.1.0 recipe (word weights, the uncentered removal of principal components, folded into the table, then quantized), which follows before the release and is checked against the 1.1.0 results of the README. The hub will carry such finished models.
