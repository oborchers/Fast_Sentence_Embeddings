## Backends

Binding for every 2.0 module (formerly under "2.0 design").

Both backends implement linear head operations. A backend implements one contract (`fse._backends`) and is chosen by name from a fixed set (`"cpu"`, `"numpy"`); there is no plugin registry and no `"auto"`:

- `prepare(pool, steps)`: once per encoder and backend, what it needs on that backend (the kernel's parameters); `pool` holds the word rows, scales, weights (ones for a finished table) and FastText rows, `steps` the postprocessing steps (none or `normalize@1`).
- `rows(batch, prepared, out)`: stages 2 to 4 of one batch into `out`, the aggregation and then the postprocessing step on the rows of that batch, so every worker applies it to the finished rows of its own task. The cpu backend pools into `out` and normalizes there in place (`postprocess_pooled`: neither the copy nor the finiteness check of `postprocess`, as pooling raises for every row that is not finite). An error leaves part of `out` written: a task writes only its own target, and the runtime commits it only after the task succeeded, so a sink that keeps its targets to itself never publishes such rows.
- `score(stored, scales, weights, bias)`: the scores of stored rows.
- `inverse_norms(stored)`, `cosines(stored, inverse, queries)` and `scores(stored, scales, weights, bias)`: the search of the vector store on stored float32, float16 or int8 rows without a float32 copy: the inverse norm of every row, and the cosine with many queries or the linear score with many weight vectors as a (rows, vectors) array, column by column the rule of one vector. Every query is checked before any is used; errors name the query or weight vector and the row, in that order. The cpu backend computes them in the kernel (`_native_kernel_search.h`) in its own floating-point environment; the inverse norms of 8 rows at a time, each with its own float64 sum in index order, so the bits are those of one row at a time while the chains of dependent additions overlap (2.4 times as fast for float32, 3.2 times for int8 on an M1 Pro).
- `store(rows, codes, scales, first_row)`: stage 5 of finished float32 rows into float16 or int8 codes (and one scale per row for int8) by `quantize_rows@1`, in the worker that made them, so a compact storage dtype costs no work in the calling thread. The cpu backend stores each row in one pass in the kernel (`_native.store_rows`, in its own floating-point environment); within one call the first row that is not finite raises, else for float16 the first row beyond +-65504.
- `logits(rows, weights, bias, out, first_row)` and `outputs(logits, kind, link, out, first_row)`: stage 4b of `linear@1` on the host. `logits` scores float32 pooled rows with A and b (the rule of `score`), or adds b once to the pooled rows of a folded table, in place; `outputs` turns finished logits into the probabilities of a link or the label indices, adding no bias. Errors name the row from `first_row`. The cpu backend runs both in the kernel, the numpy backend in `fse._reference_head`.
- `text_rows(text, span, after_encode, lookup, workspace, prepared, out)`, optional (`text_rows` in the capabilities, the cpu backend): stages 1 to 4 of a range of text in one call, with the rows, bits and errors of `rows` on the batch `lookup.encode` makes of it, in the order of those calls (`after_encode`, the source's own check after encoding, runs before the errors of `out` and the later stages). The cpu backend runs it as `_native.pool_text` in one section without the GIL; the runtime uses it for every task of a source with `encode_with` (all text sources), and the other backends and the heads keep `rows` on a `Batch`.
- `capabilities()`: the word dtypes, aggregations, steps, FastText, the largest dimension, whether it has `text_rows`.

Arguments and outputs are host numpy arrays, checked the same way by every backend (shape, dtype, C order, writability, no overlap with the inputs). The kernels and the cpu backend set the floating-point environment of their thread themselves; the numpy backend is the oracle of the tests, not a production backend, and like `fse._reference` computes in the environment of its thread. Before reading any input, the runtime checks that the backend can run the encoder and raises otherwise, naming the backend and what it cannot run; it never falls back silently. The conformance suites run every backend through its contract and compare every backend with the reference bit for bit, for every dtype, step list, FastText, source and worker count, including empty, long and unknown-word sentences and subnormal values; a new backend is done when it passes. accumulate and dot16 are kernel primitives, not contract operations, and are tested on the kernels directly.
