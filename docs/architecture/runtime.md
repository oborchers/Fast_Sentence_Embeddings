## Runtime

Historical M1 timing observations in this document are withdrawn and must not support speed claims. Numerical contracts and implementation descriptions remain valid. Current evidence is in the [comparison guide](../fse-comparison.md).


Binding for every 2.0 module (formerly under "2.0 design").

`fse._runtime` runs encoding on one executor (`run`):

- **Uniform inputs.** Every finite text batch in `encode_batches` and `predict_batches` may be a list, tuple, one-dimensional NumPy text array or Arrow string column. The same element and dimension checks apply before conversion. This also holds inside document-ID and stream-position tuples, including a batch sliced while resuming stores of different lengths. Local file parameters accept `str` and `os.PathLike[str]`; model references distinguish local path objects from string Hub identifiers. Stores, sinks and views retain TypeError for invalid path types, while validated loaders retain ValidationError.

- **Tasks.** A source is scanned into chunks, one task each: about `TASKS_PER_WORKER` (2) per worker, `ceil(bytes / (2 * workers))` bytes each within 64 KiB and 1 MiB (`fse._text._scan.default_chunk_bytes`), and at most 16 MiB of finished rows (`TASK_ROW_BYTES`) and the rows the window leaves a task. A task took the GIL back at about ten points (its native stages and the numpy checks around them): at one worker that cost about 19 µs, with 10 threads that hand the GIL around about 0.2 to 0.34 ms of CPU and more wall time (M1 Pro), so the default rule of 8 tasks per worker made WikiText (2.4 MB) 29 tasks of about 1 ms that waited for the GIL in 46 % of their samples; two tasks per worker leave room to balance cores of different speed. The automatic plan (`chunk_bytes=None`, more than one worker, not inline, not a stream) also splits its tail: the last `workers` chunks are each cut into two parts of about equal rows (`_Buffered.split_tail`, in the calling thread before any task runs, by `prefix` and the rows, so a file needs one newline search per cut), because the workers that finish last would otherwise idle while the last whole chunks run (DR-180). A chunk is cut only if both parts keep the minimum chunk size (64 KiB), so a source of chunks near that size is not split. The cuts are a function of the chunks and the workers alone, the chunks stay contiguous, in row order and non-empty, an explicit `chunk_bytes` keeps its cuts, and the rows, the errors and the GIL budget of a task do not change (only the tasks differ in number and size). On the cpu backend a task now runs its stages 1 to 4 in one section without the GIL (`text_rows`, `_native.pool_text`), with no numpy call that releases it; storage into float16 or int8 adds one section (`store_rows`) and its overlap checks, inverse norms one more. On an M1 Pro the workers then wait for the GIL in 10 % of their samples instead of 36 % (WikiText, 10 workers), and potion-base-8M encodes WikiText 1.25 times and MASSIVE 1.05 times as fast at 10 workers, with the same bits. `tests/test_runtime_gil.py` holds these budgets per task exactly: it counts the sections fse enters (every one on the task path increments `_native._test_nogil_sections` right before it, which a check of the Cython source enforces) and every call of a numpy function, ufunc (and ufunc method) and ndarray method, blocking call and lock in a task, and fails when one more appears. No CPython API counts GIL acquisitions (`PyEval_SaveThread` and `PyEval_RestoreThread` are what `Py_BEGIN_ALLOW_THREADS` expands to, and the GIL's switch counter is private), so ndarray operators and methods in Cython code are invisible to it; the source check forbids them, `with gil` and `except *` in `_native_task.pxi`, and requires `noexcept` of every cdef function its nogil blocks call, directly or through each other (without it Cython checks for an exception after each call, and a void function takes the GIL back for that). `out` overlaps an array only if both hold bytes, as `np.may_share_memory` says. Sources from about 20 MiB at 10 workers get chunks of 1 MiB, as before. A chunk holds at most its bytes plus its last sentence, and a sentence (up to 2**30 bytes) is never split, so a task of one long sentence takes as long as that sentence. Besides its rows a task holds its batch (4 bytes per token id and FastText bucket, at most `max_ngrams` buckets per unknown word, 8 per sentence and unknown word for the offsets) and the workspace of its thread (about `2 n + 32` bytes for the candidates of its longest sentence of n bytes and 16 bytes per token of it), which the thread reuses; at most the window's tasks hold them at once. A stream is read in collections of up to 65,536 sentences, each scanned into 8 tasks (`STREAM_TASKS_PER_COLLECTION`: a collection is not the whole input) with rows counted from the start of the stream.
- **Inline.** A source of at most 64 KiB, and `workers=1`, run in the calling thread without any computation thread; with the default workers such inputs are within 8 % of `workers=1` ([`bench_runtime.py latency`](https://github.com/oborchers/Fast_Sentence_Embeddings/blob/5d176f46703931c72fcde196d156426c4964620c/benchmarks/bench_runtime.py), removed; withdrawn measurement).
- **Text scans on a pool.** Before encoding, a file, encoded-string or Arrow source is scanned on the same pool and uses its task places. No `fse-text` executor is created with `pool=`. Scans with one worker or less than 1 MiB run inline, and verified string lists skip validation. The batch iterators `encode_batches` and `predict_batches` without `pool=` also scan on their iteration pool. `StreamSource` collections still scan inline. Chunks and error order stay the same.

- **Pool.** A `Pool(workers=None, *, start=False, max_tasks=None)` is a set of `workers` threads (`fse-worker`) that runs the tasks of any number of calls, one after the other or at once; every method that tokenizes text (the ten of "Length reports" below) takes the keyword-only `pool=`, the last of its keywords, and so do `VectorStore.search`, `score` and `rescore` and the store mode of a head, and `fse.add_sign_bits` (store.md, "Concurrency", whose calls give a place back when its task ends rather than at the commit), and `workers=` then may not exceed `pool.workers` (a `ValueError`; a closed pool is a `RuntimeError`, a wrong type is refused by the argument check, all before the source is read). A call on a pool runs at most `workers` tasks at once; a pool of more threads is shared. A call that runs inline (`workers=1`, or a source of at most 64 KiB) runs in its calling thread and uses neither the threads nor the places of the pool. A call on a pool from inside a call or a task of the same pool (a sink that encodes on it) is a `RuntimeError`: it would wait for places its outer call holds. The default for computation threads stays "no computation thread outlives a call": a call without `pool=` makes a pool for itself and closes it before it returns, and a stream (`encode_batches`, `predict_batches`, with or without sinks and `positions=True`) makes one for its iteration, so every batch runs on the same threads, and closes it when the iteration is exhausted, fails, is closed or is collected (`fse._runtime._pool.streaming`); threads start with the first task that needs them, never when a model or an iterator is made. A pool the caller passes is the caller's: `close()` (or the `with` block) waits for the running tasks and ends the threads, a pool that is dropped ends them when it is collected, and an exit of the interpreter joins them before `atexit` handlers (`ThreadPoolExecutor`). `start=True` starts every thread when the pool is made, for a server whose first call must not wait. `max_tasks` (default `2 * workers`) is the pool's own limit on tasks that are running, waiting or finished and not yet committed, over all calls at once: a call takes a place before it reads the next task of its source and gives it back after the commit, and waits for one only while it holds none (a call that holds places commits first, so the calls that wait are never the ones that hold them). It bounds tasks, not memory: each call keeps its window of rows (`WINDOW_BYTES`), so N calls on one pool can hold N windows; there is no shared byte budget (maintainer decision in DR-254, Gleichzeitige Suche aus mehreren Threads und Prozessen auf einem Store absichern; store.md, "Concurrency", Memory per call). An error or interrupt of a call cancels its own tasks that have not started, waits for its own running ones and is raised; it neither cancels nor waits for the tasks of other calls. A place of a task that still runs when its call ends (a second interrupt ends the wait) returns to the pool when that task ends, and a finished task is dropped with its rows as soon as it has finished, never kept until the call ends. Every `close()` waits until the threads have ended. A child of `os.fork` forgets the threads and the places of its parent (`os.register_at_fork`, `after_in_child`) and starts new threads at its first call; a `fork` made by third-party C code that does not call the hooks leaves the pool as it was. A task never calls `run` on the pool it runs on, so no task waits for another task of its pool. Bits, the order of the commits and the error that is raised do not depend on the pool. **Store calls on a pool.** `search`, `score`, `rescore`, `add_sign_bits` and the store mode of a head (`fse._store._search_run`) count a place differently: a task holds it from before it is submitted until it ends, and its finished result, until the call takes it, holds none. For them `max_tasks` therefore bounds the tasks that wait or run over all calls, not the finished results: each call keeps at most `2 * workers` of them (its window), so C concurrent calls hold together at most `C * 2 * workers` finished results. The size of a result: for search the candidates of the block, at most `min(k, rows of the block)` per query of its query block (up to 256 queries) at 20 bytes each (int64 query and row, float32 score; 28 with `max_per_doc=1`), so a large `k` makes a result large (16 queries, 65,536 rows and `k` of at least that give 20 MiB); for `rescore` one hit list per query, 12 bytes per hit (20 with document IDs), and the call collects every list of its queries anyway; `score` writes into its output and keeps no result; a block of `score_blocks` (the store mode of a head) holds at most 2**20 float32 scores (4 MiB) and the outputs derived from them (at most as large again), except that a block has at least one row, so a head of more than 2**20 outputs exceeds this by its one row; a pass of the int8 prefilter holds the rows it kept and their bounds (at most its buffers of 512 KiB), with `rows=` the int64 positions of its block (up to 512 KiB more) and the float64 heap of the `k` best estimates of every query. The scores of a block (about 4 MiB, with `mode="blas"` also its decoded rows, at most 16 MiB) live only while its task runs. This differs from encoding on purpose: an encoding call commits its results itself, in its calling thread, without returning to the caller between two tasks, so holding a place until the commit never waits on code outside the call. A `predict_batches` stream of a store gives its blocks to the caller's code by `yield`; if a finished block held its place across that `yield`, a consumer that calls `search` or `encode` on the same pool between two blocks would wait for places that only its own next `next()` would give back, and hang. Returning the place at the end of the task removes that wait, and the window of the call still bounds what it keeps; `tests/test_store_vectorstore_pool.py` searches on the pool of a stream between two of its blocks with `max_tasks=1`. The public surface is the constructor, `workers`, `max_tasks`, `closed`, `close()` and the `with` block; the methods that submit tasks and hand out places are internal (`submit` would bypass `max_tasks`).
- **Threads.** Otherwise the tasks run on a `Pool` (`fse._runtime._pool`, public as `fse.Pool`), with one workspace per thread; the native routines release the GIL and set the floating-point environment of their thread themselves, so a worker that inherited flush-to-zero gives the same bits. The tasks are taken, and each task's output rows reserved (`Sink.target`), in the calling thread; results are committed in task order in the calling thread, so a sink needs no locks.
- **Window.** At most `2 * workers` tasks are in flight or waiting to be committed, and their rows take at most 512 MiB (`WINDOW_BYTES`; with many workers a task holds fewer rows; every row counts its target, the float32 rows before a float16 or int8 target is stored, and with `normalize` 12 bytes per value (`STEP_ROW_BYTES`): normalize runs in place, but without this term its tasks were up to twice as large and the peak RSS of a stream at 10 workers grew by 65 to 140 MiB for at most 10 % throughput on an M1 Pro, because the rest of a task grows with its rows too, so the term stays): a slow sink slows the source, and memory stays bounded by the window and one collection of a stream.
- **Storage.** A sink with a `dtype` of float16 or int8 reserves codes (and int8 scales); the worker of a task pools into a float32 buffer of its thread and stores the rows with the backend's `store`, so the calling thread only commits. On an M1 Pro float16 and int8 output run at 0.91 to 1.03 of float32 for 1 to 10 workers ([`bench_runtime.py store`](https://github.com/oborchers/Fast_Sentence_Embeddings/blob/5d176f46703931c72fcde196d156426c4964620c/benchmarks/bench_runtime.py), removed; withdrawn); in 1.1, int8 output ran at about 0.33. The window counts the stored target of a row besides its float32 rows; it bounds the rows in flight, not a result that joins all rows.
- **Sinks.** A sink (`fse.Sink`) takes the rows of a run: `target` and `commit` in the calling thread, in row order, each row once; a target is valid only until its commit. Optional parts: `dtype`, `inverse_norms` (the target ends with a float32 vector the worker fills with the inverse norm of every stored row, so a store computes none in the calling thread; the window counts it), `encoder_fingerprint` (the fingerprint of the only encoder it takes), `flush()` after the last commit of a successful run, `publish()`, which every `*_batches` call (`encode_batches`, `predict_batches`) calls after the rows of every batch are committed and before it reads `durable_rows`, and `durable_rows`, the leading rows of the run that are durable, and `has_doc_ids` (exactly `True`: the sink stores one document ID per row, `encode` then needs `doc_ids=` and `encode_batches` `doc_ids=True`, and every commit is `commit(first_row, rows, doc_ids=ids)` with a read-only int64 vector of one ID per committed row; other values are ignored. A call without IDs gives a sink of your own with `True` the rows without IDs, as in 2.0; a shard sink of fse in ID mode is refused then, before any batch is read). A sink takes one run; a second run into it starts again at row 0, which it refuses. `Pipeline.infer` numbers the rows of a sink from `first_row`, so the batches of a stream continue the rows of a run. `Encoder.encode(texts, sink=)` commits to a sink and returns nothing; `encode_batches(batches)` encodes a stream batch by batch, each a finite list (as a queue consumer polls them), and gives one `EncodedBatch` per batch once its rows are finished: its rows without a sink, else the sink's `durable_rows`, so a consumer confirms its input only up to there (at least once: after a crash it reads again from the last confirmed offset). That count is a snapshot after the sink's `publish`: the sink's `flush` runs after the last batch, so after a successful full iteration the sink's own `durable_rows` says what is durable (for a full-durability ShardSink every row), and the last batch may report fewer. Stopping early does not flush; the owner of the sink closes it. With `ShardSink(durability="none")`, batch and sink `durable_rows` stay zero and cannot acknowledge durable input. The sink's `published_rows` still tracks visible rows. `MemorySink` keeps the rows of a run in memory and has no `durable_rows`.
- **Row bases of a resumed run.** `Encoder.encode(texts, sink=, shard=)` into a sink made with `resume=True` has three kinds of row. The *source row* `q` is the position in the source (`0` to `N - 1`). The *store row* `s` is the position in the store: `s = q - a` for a part that starts at `a`. The *run row* `r` is what `target` and `commit` see, from 0. With `L` rows in the store the run goes over the window `[a + L, b)` of the source, and `r = q - a - L`, `s = sink.first_row + r`. `LengthReport.first_row` of such a call is the source row where the window starts. Errors of the run name the run row.
- **Row bases of two resumed stores.** `predict` into a vector store and a score store that hold `m` and `M` rows (`m < M`) runs two phases ([scores.md](scores.md), "Resuming a run"). Phase 1 covers the source rows `[a + m, a + M)` and phase 2 `[a + M, b)`; run rows are counted over both from 0, so phase 2 starts at run row `M - m`. The shorter store sees those rows as they are; the longer one sees them moved by `-(M - m)`. `LengthReport.first_row` is the source row `a + m`.
- **Replay rows of a stream.** `encode_batches` and `predict_batches` with `positions=True` have three kinds of row besides the store row. The *replay row* counts the records the stream delivers after the seek to `P`, from 0 (`EncodedBatch.first_row` and `HeadsBatch.first_row` are replay rows). The *run row* is the row the pipeline numbers (`Pipeline.infer(first_row=)`): the records computed so far into the store that holds the fewest rows. The sink counts its own rows; `Shifted` moves the run row to them. For a store that holds `L` rows after an anchor at row `R`, the records of the replay below `d = L - R` are dropped and replay row `r >= d` becomes store row `R + r`. `durable_rows` is in replay rows: at most the records delivered, and for each sink at most `d` plus the rows published since it attached.
- **Errors.** Before a run starts, invalid arguments and eager input conversion raise immediately. Lists, tuples and numpy collections are validated when joined, so an invalid later string or token can raise before an earlier row reaches pooling or normalization. This differs from a stream, which reports input errors after the rows before them. Once input conversion succeeds, the error raised does not depend on the task boundaries or the number of workers: of all rows of a run, the error of the earliest failing row in row order is raised, and for one row the error of its earliest failing stage (1 the scan and tokenizing, 2 and 3 pooling, 4 the steps, 4b a head, 5 storage). The stages of a task run one after the other over all its rows, so a task that fails is run again on shorter prefixes of its rows, by bisection, until the shortest failing prefix is found (`fse._runtime._errors.earliest`, every `ValueError` of a task); every row is a pure function of its sentence, so that prefix fails at its last row, in the first stage that row fails in. This costs nothing until a task fails, and then about log2 of its rows runs of its prefixes. The scan of a source does not raise before the first task: its tasks end before the first invalid sentence, and the scan's error follows them in order, so an earlier row that fails in a later stage is raised first; no row behind an invalid one is encoded. Messages name the row of the run (the batch of `encode_batches` from its first row), never the position within a task. A head stores the vectors it returns (stage 5) only after its own stage 4b, so for one row the head's error comes first. Only rows of successful tasks are committed, in order; the size of the committed part before an error is not part of the contract and may depend on the task size and the workers. Tasks after a failed one are skipped where they have not started, and once a task has failed nothing more is read from the source. Every argument of `infer` is checked before the source is read. A bad sentence or an error of a stream's iterator is raised after the tasks before it. An error of the sink (reserving or committing rows) or an interrupt cancels what has not started, waits for running tasks and is raised. No thread outlives a call.

- **Heads.** A linear head runs in the worker of every task, after stages 1 to 3, as stage 4b (`fse._runtime._head`): the `HeadPipeline` reads the rows of one pipeline of the encoder, the pipeline of the folded table (made at the first prediction on a backend: every word and ngram row scored with A, in blocks of 16,384 rows over the usable CPUs) for a head on raw means, else the encoder's full mean with the head's step. The worker pools into a buffer of its thread (into the target itself for the logits of a folded head; a task whose heads read only the folded table pools in one section without the GIL, stages 1 to 4 as `Pipeline.pooled_task`, and a failed task is run again on the path with a `Batch`, which raises the error of its row with the names of the heads; every check of that path compares arrays by their byte bounds, `fse._backends._base_checks.overlaps`, never with `np.may_share_memory`, which releases the GIL; `tests/test_runtime_gil_heads.py` holds these budgets), computes the logits with the backend's `logits` and their outputs with `outputs`, so the sentence vector never leaves the worker. With the vectors (`return_vectors=True`), one pooling gives both where the head reads the encoder's own rows (the flags agree); a head whose flag overrides its encoder pools the vectors a second time on the encoder's pipeline. The window counts the rows the head reads (with the step term when it normalizes), the logits, the output target and, with the vectors, their target as the encoder's pipeline counts it. Outputs go to float32 sinks without inverse norms; a sink that names an `encoder_fingerprint` must name the output identity (`output_identity(output)`, the fingerprint of `{"model": the model's fingerprint, "output": "decision" | "proba" | "values"}`), since a model's fingerprint does not tell its decisions from its probabilities; labels go to no sink and come from `predict_batches`. A `ShardSink` takes the vectors of `return_vectors=True` but no head outputs, as a store records the fingerprint of an encoder. `sink=` keeps this role and gives no document IDs, exactly as in 2.0: a shard sink of fse with `doc_ids=True` is refused before any batch is read, with the way to pass it, and a foreign sink with `has_doc_ids=True` takes the rows without IDs. To write the vectors, the scores and the document IDs, a single head takes the keywords of `fse.Heads.predict_batches` and runs the same code (below): `vector_sink=`, `score_sink=` (a `ScoreSink(path, model, name=...)`) and `doc_ids=True`. They exclude `sink=`, need texts (a `VectorStore` input is refused: the outputs of a store come from `predict_batches(store)` and go to `sink=`), and report the minimum of the `durable_rows` of their sinks.

  What the `sink` of `predict_batches` takes depends on `return_vectors` (`Regressor.predict_batches` is the same):

  | `batches` | `return_vectors` | the `sink` takes | `outputs` | `vectors` |
  | :--- | :--- | :--- | :--- | :--- |
  | texts | False | the outputs (`decision`, `proba`, `values`; not labels) | None with a sink | None |
  | texts | True | the vectors of the encoder (any `output`, also labels) | the outputs | None with a sink |
  | VectorStore | False | the outputs (not labels) | None with a sink | None |
  | VectorStore | True | raises ValueError | | |

  The keywords `vector_sink`, `score_sink` and `doc_ids` are for texts and exclude `sink`:

  | keyword | takes | needs |
  | :--- | :--- | :--- |
  | `vector_sink` | the vectors of the encoder (a `ShardSink` or any `fse.Sink`) | `return_vectors=True` |
  | `score_sink` | the scores of this head (a `fse.ScoreSink(path, model, name=...)`) | nothing; the outputs stay in the batch |
  | `doc_ids=True` | `(texts, doc_ids)` batches, stored with the rows | a sink with `doc_ids=True` for every sink given |

  For texts, a sink of the wrong width gets a message that names this role.

- **Groups of heads.** `fse.Heads` scores several heads of one encoder in one pass (`fse._runtime._heads`, planned by `_heads_plan`). There is one runtime of heads: a lone `Classifier` or `Regressor` is a group of one (`fse._runtime._head` is the thin shell that keeps its interface, its sinks and errors without head names), so a head has the same code and bits alone and in a group. The worker of a task tokenizes it once (stages 1 and 2) and pools what the heads read, once each: the folded rows of all heads on raw means as one table of K_F columns (the folded tables of the heads side by side, folded together once on first use, held in the group's cache beside the single-head caches of the models), the full rows for the heads on normalized means with one `normalize@1`, and with the vectors the raw rows that give them (one pooling, then `normalize@1` of a copy where the encoder normalizes or a head reads normalized means; at most one pooling of the full table). A group of folded and normalized heads without the vectors pools twice over the same batch (a combined kernel would need a profile that shows the second pooling to matter). Pooling is defined per value, so each column of the shared table has the bits of the table of that head alone. Each head then computes its logits and outputs in keyword order with the functions of its own path, copying the columns of the shared table into a contiguous buffer for its logits (a lone folded head pools into its target). The window sums the rows of all readers, the copies, the logits and outputs of every head, so it keeps the 512 MiB target of `WINDOW_BYTES` with the existing exception that a task holds at least one row; the shared table, the full results of `predict` and the folds of an error path are outside it. Errors: the earliest failing row, as for one head; with several heads, pooling errors name the heads whose columns fail (found by pooling the failing row again with the folded table of each head alone), errors of the full table name the heads that read it and the vectors, logits and links name the head. A group fails as a whole, as a single call of that head would. A group has no store mode and no sink of its outputs other than a `ScoreSink`; `Heads.predict` and `predict_batches` return their results in memory. `predict_batches(return_vectors=True, vector_sink=...)` writes the vectors of the encoder to a sink and, with a `score_sink`, both in one pass to two folders ([scores.md](scores.md), "Vectors and scores in one run"); the runtime is unchanged. `predict_batches(score_sink=...)` also writes the scores of every head to a score store ([scores.md](scores.md)): a head may give a second output (the stored one) into a scratch target of its task, and the finished rows of each task are handed in the calling thread, in task order, to a tee that copies them into the columns of the sink matrix. The memory of a row counts the second outputs, the matrix of the sink and the document IDs (`HeadsPlan.row_bytes`); without a score sink the sum, the targets and the worker code are those of a group without one.

A `Pipeline` holds an encoder on one backend (prepared once, before any input is read) and is immutable, so several threads may call `infer` at once; a server that encodes many small requests in parallel sets `workers=1` per request. An `Encoder` builds its `EncodeSpec` once, the `VocabTable` of its vocabulary once (`Vocabulary`, shared by all its pipelines and passes), and one `Pipeline` per backend on first use.

## Defaults

Binding for every 2.0 module (formerly under "2.0 design").

Defaults are part of the API and chosen for speed: `workers` is the number of usable CPUs (`fse._cpus.usable_cpus`: an explicit `PYTHON_CPU_COUNT` or `-X cpu_count`, else the CPUs of the process affinity limited by the CPU quota of its Linux cgroup and every visible ancestor, rounded up (the quota is read once per process); `PYTHON_CPU_COUNT` thus also sets the default workers; small inputs run inline in the calling thread), and new encoders made by `Encoder.from_arrays` and `Encoder.from_word_vectors` end with `normalize` by default, so the cosine of two rows is their dot product; a pretrained model keeps the rule of the model (`normalize="model"` in `Encoder.from_pretrained`, see [the Hub contract](hub.md)), and `normalize=True` or `False` sets it. A server that encodes many small requests in parallel sets `workers=1`.

- **Length reports.** `lengths="summary"` or `"per_row"`, `count_truncated=True` and `on_truncation="raise"` are keyword-only on the ten methods that tokenize text (`Encoder.encode/encode_batches`, `Heads.predict/predict_batches`, `Classifier.predict/predict_proba/decision_function/predict_batches`, `Regressor.predict/predict_batches`) and checked the same way by `LengthSettings.of` before a text is read (a wrong type is a `TypeError`, a wrong value a `ValueError`, both name the method). **Return rule:** without sinks, `Heads.predict`, `Classifier.predict` and `Regressor.predict` with `return_vectors=True` return `(result, vectors)`, or `(result, vectors, fse.LengthReport)` when `lengths` is set. The vectors are the encoder's float32 rows, bit for bit as in `predict_batches(return_vectors=True)`; raw-mean heads then run unfolded. Standalone heads and `VectorStore` inputs refuse this switch, as does `Regressor.predict(sink=...)`. Vectors take `4*n*dim` bytes, about `8*n*dim` at peak when the row count is unknown because chunks coexist with the joined array. Use `predict_batches` for large or unbounded sources. Otherwise a 2.0 return type (array, mapping, `None` with a sink) becomes `(result, fse.LengthReport)` when `lengths` is set, a batch of `*_batches` becomes the pair `(batch, report)` of the 2.0 batch types (`EncodedBatch` and `PredictedBatch` gain no field), and the 2.1 `HeadsBatch` gets the field `lengths`. Without the keywords nothing is recorded, no return changes and no byte of a result differs. The workers record the cuts in their native workspaces (`fse._native.Workspace(watch, raise_cut, store_rows)`) and the calling thread adds each task, in commit order, to a `LengthCollector`; the report is the same for any number of workers, task size and backend. `"summary"` keeps only sums; `"per_row"` holds 19 bytes per row (35 with `count_truncated`) in the report, 17 (33) per row of a task until its commit, which `HeadsPlan.row_bytes` and the pipeline count once in the window. A task copies its record with the GIL held, with `np.empty` and a loop and no numpy call that could release it (`tests/test_runtime_gil.py`). A stream of unknown length doubles its arrays while it grows, so its peak is up to three times the final report: use `"summary"` for large streams. `on_truncation="raise"` raises `fse.TruncationError(ValueError)` with `row`, `cut` and `limit` for the earliest row the rule would cut, in the order of Errors above (invalid UTF-8 or a pooling error of an earlier row wins; with a sink the rows before it may be committed); without a report it records nothing but the first cut. A `VectorStore` input holds finished rows: the keywords raise `ValueError` before a row is read. `LengthReport.empty` means `tokens == 0`; a row of zeros has other causes too (a table row of zeros, an int8 row whose scale is 0, FastText with no bucket, contributions that cancel), so use `~vectors.any(axis=1)` for those.

### Sink row arguments

The public `MemorySink`, `ShardSink` and `ScoreSink` use the same row argument
checks, including vector and score sinks passed to `Heads`. `target(first_row,
n_rows)` accepts Python `int` and NumPy integer scalars, excluding booleans.
`commit(first_row, rows)` applies the same check to `first_row`. Wrong types
(including floats, infinity, NaN and NumPy time durations) raise `TypeError`; negative or oversized
integers raise `ValueError`. Checks precede allocation, shard reservation and
commit state changes. Validated integers become Python integers before arithmetic.

Let `M = np.iinfo(np.intp).max`, the platform's maximum array index. Both arguments
must be in `[0, M]`, and `first_row + n_rows` must not exceed `M`. For shard stores,
the stored starting offset plus that end must also fit. A target's total byte
size must fit in `M`: `n_rows <= M // row_bytes`. `row_bytes` includes the codes,
int8 scales, inverse norms and document IDs that the sink holds for each row.
This representability limit does not promise enough available memory or disk
space for every accepted request. A target that spans shards allocates its own
buffer before reserving any shard rows, so an allocation failure leaves the
reservations unchanged. Targets that fit one shard still use its buffers directly.
Zero-row targets are allowed.

### Sink threads

`pool=` bounds computation threads, not sink threads. Each `ShardSink` or `ScoreSink` adds up to three I/O threads of its own. The write and hash threads start at the first commit, and the publish thread at the first finished shard. Constructing, inspecting or opening a sink starts none. Once started, they live until `sink.close()` (or the end of its `with` block). Close every sink that takes rows, even when a computation runs inline. There is no finalizer. Sink work stays outside the pool: otherwise a sink could wait for a pool place held by an encode call that waits for the sink to drain.
