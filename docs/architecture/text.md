# Text sources

Scope: outside the former "2.0 design" section.

`fse._text` turns text into batches (stages 1 and 2). A source holds its sentences as one UTF-8 buffer: strings in memory with their offsets, or the memory-mapped lines of a file. `encode` takes texts in memory as a list, tuple or one-dimensional numpy array either of str or of lists or tuples of str (`fse._encoder._inputs`): the first row decides which, a row of the other kind raises with both rows named, and the tokenizer is checked before any row; a path and a stream are passed to it directly. (`fse.Corpus`, which held such a source for the passes of fit, was removed with fit: converting a list of str costs about 3 ms for 400,000 sentences since the native join.) Strings and token lists (the external tokenizer) are joined into that buffer in one native pass, a string as its UTF-8 (`join_strings`) and the tokens of a sentence separated by one space (`join_token_lists`): it reads exact lists, tuples and str through borrowed pointers, checks every str (no lone surrogate; a token also non-empty and without a code point of W) and writes its UTF-8 at once, in parts of at least 4,096 sentences that up to 8 native threads run while the calling thread holds the GIL and waits. No Python code can run during the pass (no calls, no references dropped, no Python object allocated, and no other Python thread gets the GIL; this is why the extension refuses to compile for free-threaded Python, `Py_GIL_DISABLED`), and every str object, scattered in memory, is read once: that read is what the pass costs. 85.7 million WikiText tokens take 0.65 s on an M1 Pro (2.1 s in one thread, 11 s in Python), and 400,000 strings of 20 tokens 3 ms instead of the 70 ms of `str.encode` per string, so `Encoder.encode` of such a list takes 0.64 of its former time on the cpu at 8 workers (every StringSource, so a list or tuple of str passed to `encode`; a `StreamSource` still encodes each string in the calling thread); a second pass to size the buffer first doubled the time, prefetching the next tokens gained nothing measurable; a buffer grows into a new block with a copy, not with `realloc`, because on macOS the blocks of a freed chain of large reallocs stayed resident and the RSS grew by about the joined bytes on every call. Other types (subclasses, which may override `encode` or `split`, a numpy array, a legacy string of 3.11) and every invalid str go through the Python path, which raises the errors in their order: for strings the type and then the UTF-8 of each sentence in turn, for token lists the types and tokens of all sentences first, then the UTF-8 of every sentence. A buffer of a successful native join is valid UTF-8 by construction (it reads only exact, ready str, copies ASCII, writes every other code point in its shortest form, fails on a surrogate, and CPython keeps code points at most U+10FFFF; it writes the offsets itself, from 0 to the length of the data), so it is marked verified, its offsets are made read-only, and it is not scanned again: that saves 1.8 ms of the 10 ms of WikiText at 10 workers before the first task (M1 Pro). Every other buffer (the Python path, `StringSource.encoded` and so every collection of a stream, a file, an Arrow column) is scanned; a broken proof would still be caught, because every tokenizer reports invalid UTF-8 (also behind a cut) and `TextLookup.encode` checks the offsets of every range. `scan` validates the UTF-8 of every other sentence in threads without the GIL and cuts the source into chunks of about 64 KiB to 1 MiB (at most `MAX_CHUNK_ROWS` sentences): strings and token lists from their offsets (`fse._text._plan.offset_cuts`: k = max(ceil(bytes / chunk_bytes), ceil(sentences / chunk_rows)) pieces that start at the first sentence at or after `j * bytes // k`, so where the rows bind the pieces follow them instead of each being split again (that made a stream of short sentences 51 tasks instead of 39 and 7 % slower at 10 workers), and a piece of more rows still split into parts of about equal rows, so a chunk holds at most `chunk_bytes` plus its last sentence, and the targets inside one sentence are skipped, so the work is one step per cut), the lines of a file and Arrow rows by the scan itself (a chunk ends after the sentence that reaches `chunk_bytes`, and the rest of a scan range joins the next one); `encode` turns one chunk into a Batch with a `TextLookup` (the tokenizer, the `VocabTable` built from the vocabulary bytes of the word vectors, and the FastText buckets) and a `Workspace`, the buffers one worker reuses. `make_vocabulary` builds the `VocabTable` of word vectors once as a `Vocabulary`; every lookup of the same words in the same order (checked by `WordVectors.vocabulary_fingerprint`, the fingerprint of `vocab.bytes` and `vocab.offsets` alone) can share it, so an encoder builds it once for all its backends and passes. `fse._text_file.FileSource` reads the lines of a file. Every sentence is one row, empty ones included. Tokens are matched to the vocabulary by their exact UTF-8 bytes, so with `fse_words@1` a word with uppercase letters or whitespace (such as `New_York` in GoogleNews) is never matched. `tools/make_unicode_tables.py` generates the lowercase tables from `UnicodeData.txt`; both generated files are checked in and compared with each other in the tests. With `wordpiece@1` the encoder's `TokenizerSpec` (`fse._tokenizer_spec`: the identifier, its parameters, `fse.unknown` and the length rule, immutable) goes through `EncodeSpec` and the `Pipeline` to `make_lookup`, which builds a `WordPieceState` once from it and the vocabulary: the `VocabTable` of all tokens, a byte trie of all tokens (`_native_wordpiece_trie.h`, a static double array built at load from the vocabulary bytes in about 14 ms and 0.7 MiB for potion-base-8M, 32 ms and 1.6 MiB for potion-base-32M; never persisted) with the node of the continuation prefix, and the added tokens; a sentence is then split at the added tokens, normalized and pre-tokenized into a buffer of the `Workspace` and matched word by word, without the GIL. The native path has fast paths that give the ids of the plain rules: the scan for added tokens jumps to the bytes they start with (`memchr` for one such byte); ASCII bytes are normalized through 128-byte tables derived from the composed Unicode table when the module loads (8 printable bytes lowercased at once), but only while no combining marks wait in a run (an ASCII byte ends a run, a removed one does not), and pre-tokenized by a class table (8 bytes of a-z and 0-9 skipped at once); the length rule counts 8 ASCII bytes at a time and still validates the whole sentence; the code points of a word are counted only when it has more bytes than the word limit; a word is first one lookup of the `VocabTable`, and after a miss each piece is the longest token the trie reads from the root or the prefix node at a code-point boundary, which is what the greedy loop of lookups returns. The module refuses to build a state when the Unicode table gives an ASCII byte a shape the tables cannot hold. A private switch (`_generic`, for the tests, never persisted) takes the plain rules for every step, and the tests compare both paths; on an M1 Pro the fast paths make the tokenizer alone 2.16 (WikiText-103) and 1.71 (MASSIVE) times as fast at one thread, and `Encoder.encode` of potion-base-8M 1.64 and 1.37 times at one worker.

**Arrow string columns.** `fse._text._arrow.ArrowSource` reads a column that any producer exports through the Arrow PyCapsule interface (`__arrow_c_stream__`, else `__arrow_c_array__`; https://arrow.apache.org/docs/format/CDataInterface/PyCapsuleInterface.html), so fse needs no pyarrow: pyarrow arrays and chunked arrays, pandas 3 Series (`large_string`), Polars Series (`string_view`, whatever schema is requested) and Hugging Face datasets in Arrow format (`string`, chunks of 1,000 rows, memory-mapped). `encode` and the heads check for the protocol before the collection rules, every batch of `encode_batches` may be such a column, and its rows come from the source, not from `len()`; a producer that cannot export (pandas without pyarrow) is read as a stream with a warning, and a `datasets` Column, which exports nothing, raises with the Arrow-format path. No schema is requested. The native part (`_native_arrow.pxi`, `_native_arrow_column.pxi`, `_native_arrow.h`) moves the arrays out of their capsules in the calling thread, with the GIL, and owns them until `ArrowSource.close` at the end of the call, when each is released once, with the GIL (never while a scan or encode reads it); the stream is read whole when the source is made, so its rows are known and the scan checks every row before the first is encoded. It reads `utf8` (`u`), `large_utf8` (`U`) and `utf8_view` (`vu`) where they are: a row is `(pointer, length)` from its int32 or int64 offsets or from its 16-byte view (inline up to 12 bytes, else a variadic buffer, index and offset). Rows are numbered across the chunks, and a chunk of the runtime may span many Arrow chunks, so the runtime plans an Arrow source like a `StringSource`, and its batches and rows are those of the same texts as a list, bit for bit (the conformance suites take Arrow columns as input classes). It refuses tables (naming their string columns), binary, dictionary-encoded and extension columns, and ends the column at its first null (reading the validity bitmap whatever the null count says): the rows before it are the column, nothing after it is read, and its error, which names its row, is raised after the rows before it, like an invalid sentence of the scan. Before it forms a pointer from a value it checks: the formats, children, dictionaries and capsule names; lengths, array offsets and every sum and product of them against `INT64_MAX`, `SIZE_MAX` and `PY_SSIZE_T_MAX`; the required buffers; the null count (from -1 to the length; without a bitmap only 0); the first and last offset of a chunk; the sizes of the view buffers (read with `memcpy`); and, per row as it is read, offsets within the data up to the chunk's last offset, and views within their buffer's stated size; then the UTF-8 as for every source. Offsets or views that are not aligned are copied once into an aligned buffer and logged; the text is never copied. **The producer's obligations**, which the C Data Interface leaves to it and no consumer can check: every buffer is at least as large as its layout implies (the bitmap, the offsets or views up to `offset + length`, the data up to the last offset, each view buffer of its stated size), and no buffer changes while fse reads it. Under these obligations fse never reads outside a buffer; a producer that breaks them gives an error or wrong rows that fse cannot detect.

`fse._stream.StreamSource` takes sentences from any iterable (a queue consumer, a crawler, log lines) and is read once. The runtime reads it in the calling thread, a collection of at most `chunk_rows` sentences (65,536) or about `chunk_bytes` (8 MiB) at a time, and only when its window of tasks has room, so a slow sink slows the source and memory stays bounded by one collection and the window. A sentence that is no str or has no UTF-8 form, and an error of the iterator, are raised after the rows before them were committed, with the row number counted from the start of the stream. The iterator is never read from another thread. One thread reads a stream, so a stream gives at most what that thread can collect: about 2.8 million sentences per second on a 16-vCPU EPYC (`bench_runtime.py stream`), the same as a StringSource up to about 8 workers and 0.8 to 0.9 of it at 16; a native reader may lift this later.
